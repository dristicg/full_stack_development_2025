# Django Forms — Built-in & ModelForms

## 1. Why Django Forms

**Definition:** Django Forms is a built-in framework that handles the generation of HTML form fields, server-side validation of submitted data, and conversion of that data into Python-native types, all through a single Python class.

### 1.1 Limitations of Raw HTML Forms (Recap)

A raw HTML `<form>` (as used earlier in a project's Add/Edit Student pages) has real gaps:

- No automatic server-side validation — an empty or malformed field only gets caught if the developer manually checks `request.POST` values.
- No automatic type conversion — everything read from `request.POST` arrives as a string, requiring manual casting (e.g., `int(request.POST.get('age'))`).
- No built-in error messages tied to fields — displaying "this field is required" next to the right input has to be done by hand.
- Field markup (`<input>`, `<select>`, etc.) must be written manually for every field, every time.

**Important Note for Exam:** Django Forms do not replace HTML `<form>` tags — the `<form method="POST">` element is still written in the template. What Django Forms replace is the manual field markup, validation, and type conversion that would otherwise be written by hand.

### 1.2 Two Types of Django Forms

| Type | Purpose |
|---|---|
| `forms.Form` | A general-purpose form, not tied to any specific model |
| `forms.ModelForm` | A form automatically generated from a Django Model |

## 2. forms.Form and Field Types

**Definition:** `forms.Form` is a Django class, subclassed to define a form, where each class attribute represents one form field, declared using a Django form field type.

### 2.1 Where Forms Are Defined

By convention, forms are written in a file named `forms.py`, created manually inside the relevant app (Django does not generate this file automatically, similar to how `urls.py` had to be created manually inside an app).

### 2.2 Basic Syntax

```python
from django import forms

class StudentForm(forms.Form):
    name = forms.CharField(max_length=100)
    age = forms.IntegerField()
    email = forms.EmailField()
```

### 2.3 Common Field Types

| Field Type | Purpose | Maps to HTML Input |
|---|---|---|
| `CharField` | Short text | `<input type="text">` |
| `EmailField` | Text with email format validation | `<input type="email">` |
| `IntegerField` | Whole numbers | `<input type="number">` |
| `BooleanField` | True/False | `<input type="checkbox">` |
| `ChoiceField` | One value from a fixed set of choices | `<select>` |
| `DateField` | Date value | `<input type="date">` |

### 2.4 Example: ChoiceField

```python
class StudentForm(forms.Form):
    name = forms.CharField(max_length=100)
    year = forms.ChoiceField(choices=[
        ('1', 'First Year'),
        ('2', 'Second Year'),
        ('3', 'Third Year'),
    ])
```

**Important Note for Exam:** Each Django form field type carries its own built-in validation — for example, `EmailField` automatically rejects text that isn't a valid email format, and `IntegerField` automatically rejects non-numeric input. This validation happens without the developer writing any extra code, which is the central advantage over raw HTML forms.

## 3. Rendering Forms in Templates

### 3.1 Passing a Form to a Template

```python
def student_form_view(request):
    form = StudentForm()
    return render(request, 'students/student_form.html', {'form': form})
```

### 3.2 Rendering Options

| Syntax | Output |
|---|---|
| `{{ form.as_p }}` | Each field wrapped in a `<p>` tag |
| `{{ form.as_table }}` | Fields rendered as table rows (requires a `<table>` wrapper in the template) |
| `{{ form.as_ul }}` | Fields rendered as list items (requires a `<ul>` wrapper in the template) |

### 3.3 Example Template

```html
<form method="POST">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">Submit</button>
</form>
```

**Important Note for Exam:** `{% csrf_token %}` is still required even when using Django Forms — the form class handles field markup and validation, but CSRF protection is a separate, template-level requirement for any POST form, exactly as covered earlier.

## 4. is_valid() and cleaned_data

### 4.1 is_valid()

**Definition:** `is_valid()` is a form method that runs all validation rules for every field and returns `True` if all fields pass validation, or `False` if any field fails.

```python
def student_form_view(request):
    if request.method == 'POST':
        form = StudentForm(request.POST)
        if form.is_valid():
            name = form.cleaned_data['name']
            age = form.cleaned_data['age']
            email = form.cleaned_data['email']
            # process the data
    else:
        form = StudentForm()
    return render(request, 'students/student_form.html', {'form': form})
```

### 4.2 cleaned_data

**Definition:** `cleaned_data` is a dictionary attribute available on a form only after `is_valid()` has been called and returned True; it contains the submitted data, already converted into the correct Python types.

**Important Definition (Quotable):** cleaned_data differs from request.POST in that its values have already been validated and converted to proper Python types — for example, a value submitted for an IntegerField arrives in cleaned_data as an actual Python int, not a string, unlike raw request.POST data.

**Important Note for Exam:** `cleaned_data` should never be accessed before calling `is_valid()` — if validation hasn't run, `cleaned_data` may not exist or may be incomplete. Always call `is_valid()` first, inside an `if` check.

## 5. Bound vs Unbound Forms

**Definition:** A form is "bound" when it is instantiated with data (typically `request.POST`), meaning it is tied to a specific set of submitted values and can be validated; a form is "unbound" when it is instantiated without any data, meaning it has no values to validate and is only used to display empty fields.

### 5.1 Example

```python
form = StudentForm()              # Unbound — used to display a blank form
form = StudentForm(request.POST)  # Bound — used to validate submitted data
```

### 5.2 Comparison Table

| Aspect | Unbound Form | Bound Form |
|---|---|---|
| Created With | No data passed | Data passed (e.g., request.POST) |
| Typical Use | Displaying an empty form (GET request) | Validating submitted data (POST request) |
| is_valid() Behavior | Not meaningful to call | Returns True/False based on validation |
| form.is_bound | False | True |

**Important Note for Exam:** This is a very common exam distinction — the same `StudentForm` class is used in both cases; whether it's "bound" or "unbound" depends only on whether data was passed into it when it was instantiated, not on anything about the class definition itself.

## 6. ModelForm

**Definition:** ModelForm is a Django class that automatically generates a form directly from a Model, creating form fields that correspond to the model's fields, without the developer needing to redeclare each field manually.

### 6.1 Why ModelForm Is Useful

- Avoids duplicating field definitions that already exist in the model (e.g., `CharField(max_length=100)` written once in the model, not again in a separate form).
- Automatically keeps the form in sync with the model — if a field is added to the model, the ModelForm picks it up without changes (when using `fields = '__all__'`).
- Provides a `.save()` method that directly creates or updates a model instance from the form's validated data.

### 6.2 Basic Syntax

```python
from django import forms
from .models import Student

class StudentModelForm(forms.ModelForm):
    class Meta:
        model = Student
        fields = ['name', 'age', 'email']
```

**Important Definition (Quotable):** A ModelForm links a Django Form to a specific Model through its Meta class, and Django automatically generates one form field for each model field listed, matching field types (a model's IntegerField becomes a form IntegerField, for example) and inheriting validation rules such as max_length and unique constraints.

---

## 7. The Meta Class in ModelForm

**Definition:** The Meta class inside a ModelForm specifies which model the form is linked to, and which of that model's fields should be included (or excluded) from the generated form.

### 7.1 Meta Options

| Option | Purpose |
|---|---|
| `model` | Specifies which Django Model this form is based on (compulsory) |
| `fields` | A list of field names to include, or the string `'__all__'` to include every field |
| `exclude` | A list of field names to leave out (alternative to listing fields explicitly) |
| `widgets` | A dictionary customizing the HTML widget used for specific fields |

### 7.2 Example Using exclude

```python
class StudentModelForm(forms.ModelForm):
    class Meta:
        model = Student
        exclude = ['id']
```

**Important Note for Exam:** `fields` and `exclude` should not both be used together in the same Meta class — a form should specify one or the other, not both, to avoid ambiguity about which fields are included.

## 8. Saving a ModelForm

### 8.1 Basic Usage

```python
def add_student(request):
    if request.method == 'POST':
        form = StudentModelForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect('student_list')
    else:
        form = StudentModelForm()
    return render(request, 'students/add_student.html', {'form': form})
```

**Explain:** `form.save()` creates a new `Student` row directly from the form's validated data — this single line replaces the manual `Student.objects.create(name=..., age=..., email=...)` pattern used with raw HTML forms.

### 8.2 Saving for an Edit (Existing Instance)

```python
def edit_student(request, student_id):
    student = get_object_or_404(Student, pk=student_id)
    if request.method == 'POST':
        form = StudentModelForm(request.POST, instance=student)
        if form.is_valid():
            form.save()
            return redirect('student_detail', student_id=student.id)
    else:
        form = StudentModelForm(instance=student)
    return render(request, 'students/edit_student.html', {'form': form})
```

**Important Definition (Quotable):** Passing instance=student to a ModelForm tells Django to pre-fill the form with that object's existing data (when unbound) and, if the form is later validated and saved, to update that same existing row rather than creating a new one.

### 8.3 create vs edit — Comparison Table

| Aspect | Add (Create) | Edit (Update) |
|---|---|---|
| Form instantiation (GET) | `StudentModelForm()` | `StudentModelForm(instance=student)` |
| Form instantiation (POST) | `StudentModelForm(request.POST)` | `StudentModelForm(request.POST, instance=student)` |
| Effect of .save() | Creates a new row | Updates the existing row |

### 8.4 save(commit=False) (Brief Mention)

```python
student = form.save(commit=False)
student.some_extra_field = "value"
student.save()
```

**Explain:** `commit=False` builds the model instance from the form's data without saving it to the database yet — useful when extra processing is needed (such as setting a field not present on the form) before the final `.save()` call.
