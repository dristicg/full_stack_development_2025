# Form Validation and Error Handling

## 1. Built-in Field Validation

**Definition:** Built-in field validation refers to the automatic checks Django performs on each form field based on its type and declared arguments, before any custom validation logic written by the developer is run.

### 1.1 Examples of Built-in Validation

| Field Type / Argument | Validation Automatically Applied |
|---|---|
| `CharField(max_length=100)` | Rejects input longer than 100 characters |
| `EmailField()` | Rejects text that is not in a valid email format |
| `IntegerField()` | Rejects non-numeric input |
| `required=True` (default for most fields) | Rejects empty submissions for that field |
| `required=False` | Allows the field to be left empty |

### 1.2 Example

```python
from django import forms

class StudentForm(forms.Form):
    name = forms.CharField(max_length=100, required=True)
    age = forms.IntegerField(required=True)
    email = forms.EmailField(required=True)
    address = forms.CharField(required=False)
```

**Important Note for Exam:** All Django form fields are `required=True` by default, except `BooleanField`, which defaults to `required=False` in practice for checkbox usability reasons — but the safest exam answer is that required behavior can always be explicitly set with `required=True` or `required=False` regardless of field type.

## 2. Widgets — Introduction

**Definition:** A widget is a Django class responsible for rendering a form field as a specific piece of HTML markup; every form field has a default widget, but it can be explicitly overridden to change how the field appears.

### 2.1 Common Widgets

| Widget | Renders As |
|---|---|
| `TextInput` | `<input type="text">` (default for CharField) |
| `Textarea` | `<textarea>` (for multi-line text) |
| `EmailInput` | `<input type="email">` (default for EmailField) |
| `NumberInput` | `<input type="number">` (default for IntegerField) |
| `Select` | `<select>` (default for ChoiceField) |
| `CheckboxInput` | `<input type="checkbox">` (default for BooleanField) |
| `PasswordInput` | `<input type="password">` (masks typed characters) |

### 2.2 Overriding a Widget

```python
class StudentForm(forms.Form):
    name = forms.CharField(max_length=100)
    bio = forms.CharField(widget=forms.Textarea)
    password = forms.CharField(widget=forms.PasswordInput)
```

**Explain:** Without specifying a widget, `CharField` renders as a single-line `TextInput` by default. Passing `widget=forms.Textarea` changes only how the field is displayed — the field's underlying validation (it's still a `CharField`) does not change.

**Important Note for Exam:** A widget controls presentation (how the field looks in HTML); it does not control validation (what values are accepted). These are two separate concerns — a common exam trick is describing a widget change and asking whether validation behavior is affected (it is not, unless the field type itself is different).

## 3. error_messages

**Definition:** `error_messages` is an optional argument accepted by any form field, allowing the developer to override Django's default validation error text with a custom message for specific error types.

### 3.1 Example

```python
class StudentForm(forms.Form):
    name = forms.CharField(
        max_length=100,
        error_messages={
            'required': 'Please enter the student name.',
            'max_length': 'Name is too long — 100 characters maximum.',
        }
    )
```

**Explain:** Without `error_messages`, Django would show a generic default like "This field is required." Customizing it allows more specific, user-friendly text tailored to the actual form.

## 4. Custom Field Validation — clean_<field>()

**Definition:** `clean_<field>()` is a method defined on a Form (or ModelForm) subclass, named after a specific field, that runs automatically during `is_valid()` and allows custom validation logic to be applied to that one field, beyond what the field type checks by default.

### 4.1 Syntax and Example

```python
from django import forms

class StudentForm(forms.Form):
    name = forms.CharField(max_length=100)
    age = forms.IntegerField()
    email = forms.EmailField()

    def clean_age(self):
        age = self.cleaned_data.get('age')
        if age < 15:
            raise forms.ValidationError("Student must be at least 15 years old.")
        return age
```

**Explain, step by step:**
- The method name MUST follow the exact pattern `clean_<fieldname>` — here, `clean_age` corresponds to the `age` field.
- Inside the method, `self.cleaned_data.get('age')` retrieves the value already validated by the built-in `IntegerField` check (so it is guaranteed to already be a proper integer at this point).
- If the custom condition fails, `forms.ValidationError` is raised with a message.
- **The method MUST return the cleaned value at the end** (even if no error was raised) — this returned value becomes the final value stored in `cleaned_data['age']`.

**Important Note for Exam:** Forgetting to `return age` at the end of a `clean_<field>()` method is one of the most common mistakes — without it, the field's value in `cleaned_data` would silently become `None`, since Python functions return `None` by default when no explicit `return` is written.

## 5. Cross-Field Validation — clean()

**Definition:** `clean()` is a method that can be overridden on a Form (or ModelForm) subclass to perform validation that depends on multiple fields together, rather than checking a single field in isolation.

### 5.1 Why Cross-Field Validation Is Needed

- Some validation rules cannot be expressed by checking one field alone — for example, "the end date must be after the start date" requires comparing two fields together.
- `clean_<field>()` methods each only have access to their own field; `clean()` has access to the entire `cleaned_data` dictionary built up so far.

### 5.2 Example

```python
class EnrollmentForm(forms.Form):
    start_date = forms.DateField()
    end_date = forms.DateField()

    def clean(self):
        cleaned_data = super().clean()
        start = cleaned_data.get('start_date')
        end = cleaned_data.get('end_date')

        if start and end and end < start:
            raise forms.ValidationError("End date cannot be before start date.")

        return cleaned_data
```

**Explain, step by step:**
- `cleaned_data = super().clean()` — calls the parent class's `clean()` method first, which returns the dictionary of already-validated individual fields; this is compulsory to preserve normal field-level validation.
- Both fields are checked together (`end < start`) — something impossible to check from within a single `clean_<field>()` method.
- The method must return `cleaned_data` at the end, same principle as `clean_<field>()` needing to return its value.

**Important Definition (Quotable):** clean_<field>() validates one specific field in isolation, while clean() validates relationships between multiple fields together; both must return their respective cleaned values, and both run automatically as part of is_valid().

### 5.3 Comparison Table

| Aspect | clean_<field>() | clean() |
|---|---|---|
| Scope | One specific field | All fields together |
| Naming | Must match `clean_` + exact field name | Always named exactly `clean` |
| Access to Other Fields | No (only its own field) | Yes (full cleaned_data dictionary) |
| Must Return | The single field's cleaned value | The entire cleaned_data dictionary |
| Typical Use Case | Field-specific business rule (e.g., minimum age) | Rules comparing two or more fields (e.g., date ranges) |

## 6. Raising ValidationError

**Definition:** `ValidationError` is a Django exception class raised inside custom validation methods to signal that a value has failed validation; when raised, Django automatically attaches the error message to the relevant field (or to the form as a whole, for errors raised in `clean()`).

### 6.1 Import

```python
from django import forms
# or
from django.core.exceptions import ValidationError
```

**Explain:** `forms.ValidationError` is simply Django's `django.core.exceptions.ValidationError`, made conveniently accessible through the `forms` module — both imports raise the exact same exception class.

### 6.2 Where Errors End Up

| Raised In | Error Appears Under |
|---|---|
| `clean_<field>()` | That specific field's error list |
| `clean()` | "Non-field errors" — not attached to any single field |

---

## 7. Displaying Errors in Templates

### 7.1 Automatic Error Display

When using `{{ form.as_p }}` (or `as_table`/`as_ul`), Django automatically inserts error messages next to the relevant field if the form was submitted with invalid data.

### 7.2 Manual Error Access

```html
{% for field in form %}
    <p>
        {{ field.label_tag }} {{ field }}
        {% if field.errors %}
            <span style="color: red;">{{ field.errors }}</span>
        {% endif %}
    </p>
{% endfor %}

{% if form.non_field_errors %}
    <div style="color: red;">
        {{ form.non_field_errors }}
    </div>
{% endif %}
```

**Explain:**
- `field.errors` — accesses errors specific to that one field (would include anything raised in that field's `clean_<field>()` method, plus built-in validation errors).
- `form.non_field_errors` — accesses errors raised in `clean()`, since those aren't tied to any single field.

**Important Note for Exam:** `non_field_errors` is the exact mechanism through which a `ValidationError` raised inside `clean()` becomes visible to the user — it will NOT appear next to any individual field, since it describes a relationship between fields, not one field's own value.

## 8. Hands-On: Rebuilding the Project's Forms with Validation

This section applies everything from today directly to the Student Portal's Add/Edit Student forms.

### 8.1 The Form — `students/forms.py`

```python
from django import forms
from .models import Student

class StudentForm(forms.ModelForm):
    class Meta:
        model = Student
        fields = ['name', 'age', 'email', 'department', 'courses']
        widgets = {
            'courses': forms.CheckboxSelectMultiple(),
        }

    def clean_age(self):
        age = self.cleaned_data.get('age')
        if age < 15:
            raise forms.ValidationError("Student must be at least 15 years old.")
        return age

    def clean_email(self):
        email = self.cleaned_data.get('email')
        qs = Student.objects.filter(email=email)
        if self.instance.pk:
            qs = qs.exclude(pk=self.instance.pk)
        if qs.exists():
            raise forms.ValidationError("A student with this email already exists.")
        return email
```

**Explain the new pieces:**
- `widgets = {'courses': forms.CheckboxSelectMultiple()}` — since `courses` is a ManyToManyField, this widget renders it as a list of checkboxes automatically, replacing the manual `{% for course in courses %}` checkbox loop written earlier by hand.
- `clean_email`'s `if self.instance.pk:` check — this handles the edit case correctly: when editing a student, their own existing email shouldn't be flagged as a duplicate of itself. `self.instance.pk` exists only when editing (since `instance=student` was passed in); it's `None` when creating a new student.

### 8.2 The View — `students/views.py` (Replacing the Manual add_student)

```python
from .forms import StudentForm

def add_student(request):
    if request.method == 'POST':
        form = StudentForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect('student_list')
    else:
        form = StudentForm()
    return render(request, 'students/add_student.html', {'form': form})


def edit_student(request, student_id):
    student = get_object_or_404(Student, pk=student_id)
    if request.method == 'POST':
        form = StudentForm(request.POST, instance=student)
        if form.is_valid():
            form.save()
            return redirect('student_detail', student_id=student.id)
    else:
        form = StudentForm(instance=student)
    return render(request, 'students/edit_student.html', {'form': form})
```

**Explain what got eliminated:** compared to the earlier manual version, there is no more `request.POST.get('name')`, no manual `int(...)` casting, no manual `request.POST.getlist('courses')`, no manual department-ID assignment, and no manual duplicate-email checking logic scattered in the view — all of it now lives inside the form class itself.

### 8.3 The Template — Simplified

```html
{% extends 'students/base.html' %}
{% block title %}Add Student{% endblock %}
{% block content %}
    <h1>Add New Student</h1>
    <form method="POST">
        {% csrf_token %}
        {{ form.as_p }}
        <button type="submit">Add Student</button>
    </form>
{% endblock %}
```

**Explain:** the entire hand-written `<input>`/`<select>`/checkbox markup from earlier is now replaced by a single `{{ form.as_p }}` — and it automatically includes error messages next to each field whenever validation fails.
