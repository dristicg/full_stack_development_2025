# User Authentication


## 1. Django's Built-in Authentication System

**Definition:** Django's authentication system is a built-in framework (part of `django.contrib.auth`) that handles user accounts, passwords, permissions, and login sessions, without requiring the developer to build any of this functionality from scratch.

### 1.1 Where It Comes From

- Recall from Chapter 2, Day 2: `django.contrib.auth` is one of the default entries already present in `INSTALLED_APPS` when a project is created — authentication is available immediately, with zero extra installation.
- The authentication system relies on Django's sessions framework to keep a user "logged in" across multiple requests, since HTTP itself is stateless (recalled from Chapter 2, Day 1).

**Important Note for Exam:** A commonly asked question is "why is authentication possible across multiple stateless HTTP requests?" — the answer must mention that Django stores a session identifier (typically in a cookie) after login, which is sent back on every subsequent request, allowing the server to recognize the same logged-in user.

---

## 2. The User Model

**Definition:** `User` is Django's built-in model (found in `django.contrib.auth.models`) representing a registered user account, including fields for username, password (stored in hashed form), email, and permission-related flags.

### 2.1 Key Fields on the User Model

| Field | Purpose |
|---|---|
| `username` | Unique identifier used to log in |
| `password` | Stored as a hashed value, never as plain text |
| `email` | User's email address |
| `is_active` | Boolean — whether the account is currently enabled |
| `is_staff` | Boolean — whether the user can access the Django admin site |
| `is_superuser` | Boolean — whether the user has all permissions, bypassing individual permission checks |

**Important Note for Exam:** Passwords are never stored as plain text in Django — they are stored using a one-way hashing algorithm. This is why an admin cannot "look up" a user's password; it can only be reset to a new value, never retrieved.

### 2.2 Recap — createsuperuser

`python manage.py createsuperuser` (already used earlier in the project) creates a `User` record with both `is_staff=True` and `is_superuser=True`, granting full admin access.

## 3. authenticate()

**Definition:** `authenticate()` is a Django function that verifies a given username and password against the stored user records, returning the matching `User` object if the credentials are valid, or `None` if they are not.

### 3.1 Syntax

```python
from django.contrib.auth import authenticate

user = authenticate(request, username=username, password=password)
```

**Important Note for Exam:** `authenticate()` only checks whether the credentials are correct — it does NOT log the user in. Logging in (establishing the session) is a separate step, handled by `login()`, covered next. This distinction between checking credentials and establishing a session is a frequently tested exam point.

---

## 4. login() and logout()

### 4.1 login()

**Definition:** `login()` is a Django function that takes a request and a validated `User` object, and establishes a logged-in session for that user, allowing them to remain authenticated across subsequent requests.

```python
from django.contrib.auth import authenticate, login

def login_view(request):
    if request.method == 'POST':
        username = request.POST.get('username')
        password = request.POST.get('password')
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)
            return redirect('home')
        else:
            return render(request, 'students/login.html', {'error': 'Invalid credentials'})
    return render(request, 'students/login.html')
```

**Explain the two-step process, since it's the most-tested sequence in this topic:**
1. `authenticate()` checks the username/password combination — returns a `User` object or `None`.
2. `login(request, user)` is only called if `authenticate()` succeeded — this is the step that actually creates the session.

### 4.2 logout()

**Definition:** `logout()` is a Django function that ends the current session, logging the user out and clearing their session data.

```python
from django.contrib.auth import logout

def logout_view(request):
    logout(request)
    return redirect('home')
```

**Important Note for Exam:** `logout()` takes only `request` as an argument — unlike `login()`, it does not need a `User` object, since it simply ends whichever session is currently active on that request.

### 5.1 login.html

```html
{% extends 'students/base.html' %}
{% block title %}Login{% endblock %}
{% block content %}
    <h1>Login</h1>
    {% if error %}
        <p style="color: red;">{{ error }}</p>
    {% endif %}
    <form method="POST">
        {% csrf_token %}
        <label>Username:</label><br>
        <input type="text" name="username" required><br><br>
        <label>Password:</label><br>
        <input type="password" name="password" required><br><br>
        <button type="submit">Login</button>
    </form>
{% endblock %}
```

**Explain:** `type="password"` masks the typed characters in the browser — this is purely a display concern (like the `PasswordInput` widget from Day 2); the actual security comes from HTTPS in transit and hashing in storage, not from this attribute alone.

### 5.2 URL Setup

```python
path('login/', views.login_view, name='login'),

```

## 6. Registration via UserCreationForm

**Definition:** `UserCreationForm` is a built-in Django ModelForm (found in `django.contrib.auth.forms`) that provides a ready-made form for registering a new user, including username, password, and password confirmation fields, along with built-in password validation.

### 6.1 Why Use UserCreationForm Instead of a Custom Form

- Automatically includes password confirmation (matching check) without the developer writing that logic manually — this is essentially a pre-built `clean()` cross-field validation, exactly like the pattern covered on Day 2.
- Automatically applies Django's password strength validators (length, similarity to username, common password checks).
- Automatically hashes the password before saving — the developer never handles plain-text passwords directly.

### 6.2 Basic Usage

```python
from django.contrib.auth.forms import UserCreationForm
from django.contrib.auth import login

def register_view(request):
    if request.method == 'POST':
        form = UserCreationForm(request.POST)
        if form.is_valid():
            user = form.save()
            login(request, user)
            return redirect('home')
    else:
        form = UserCreationForm()
    return render(request, 'students/register.html', {'form': form})
```

**Explain:** This follows the exact same ModelForm pattern from Day 1 — `is_valid()`, then `.save()` — except here, `.save()` returns the newly created `User` object directly, which is then immediately passed into `login()` so the user doesn't have to separately log in right after registering.

### 6.3 Template

```html
{% extends 'students/base.html' %}
{% block title %}Register{% endblock %}
{% block content %}
    <h1>Register</h1>
    <form method="POST">
        {% csrf_token %}
        {{ form.as_p }}
        <button type="submit">Register</button>
    </form>
{% endblock %}
```

**Important Note for Exam:** `UserCreationForm` is a ModelForm, so `{{ form.as_p }}` works exactly as it did for `StudentForm` in Day 1 — same rendering syntax, same automatic error display, just a different underlying model (`User` instead of `Student`).

## 7. The @login_required Decorator

**Definition:** `@login_required` is a Django decorator applied to a view function that restricts access to that view to only authenticated (logged-in) users; unauthenticated users attempting to access it are automatically redirected to the login page.

### 7.1 Syntax

```python
from django.contrib.auth.decorators import login_required

@login_required
def student_stats(request):
    stats = Student.objects.aggregate(
        total=Count('id'),
        avg_age=Avg('age'),
        max_age=Max('age'),
        min_age=Min('age'),
    )
    return render(request, 'students/student_stats.html', {'stats': stats})
```

**Explain:** By placing `@login_required` directly above a view function, that entire view becomes inaccessible to anyone not currently logged in — they are redirected before the view's own code ever runs.

### 7.2 Checking Login Status in a Template

```html
{% if user.is_authenticated %}
    <p>Welcome, {{ user.username }}</p>
    <a href="{% url 'logout' %}">Logout</a>
{% else %}
    <a href="{% url 'login' %}">Login</a>
{% endif %}
```

**Explain:** `user.is_authenticated` is available in every template automatically (via Django's built-in context processor, already listed in the `TEMPLATES` setting since Chapter 2, Day 4) — no need to pass it manually through context.

## 8. Redirect Behavior and LOGIN_URL

**Definition:** `LOGIN_URL` is a setting in `settings.py` that tells Django where to redirect an unauthenticated user when they attempt to access a view protected by `@login_required`.

### 8.1 Setting It

```python
# settings.py
LOGIN_URL = 'login'
```

**Explain:** This value should match the `name` given to the login URL pattern (`name='login'`, from Step 5.2's `urls.py` entry) — Django resolves this name into the actual URL path at request time.

### 8.2 What Happens Without LOGIN_URL Set

- Django falls back to a default path, `/accounts/login/`, which will not exist unless a URL pattern is defined there — leading to a 404 error when an unauthenticated user is redirected.
- Setting `LOGIN_URL` explicitly to match the project's actual login URL name avoids this mismatch entirely.

### 8.3 The next Parameter (Brief Mention)

When `@login_required` redirects an unauthenticated user, it appends a `?next=/original/path/` query parameter to the login URL, so that after a successful login, the user can be sent back to the page they originally tried to access.

```python
def login_view(request):
    if request.method == 'POST':
        username = request.POST.get('username')
        password = request.POST.get('password')
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)
            next_url = request.POST.get('next') or 'home'
            return redirect(next_url)
    return render(request, 'students/login.html')
```

**Important Note for Exam:** The `next` parameter is what allows a "log in, then return to the page you wanted" flow — without handling it, a user redirected to login would always land back on a fixed page (like `home`) rather than the page they were originally trying to reach.
