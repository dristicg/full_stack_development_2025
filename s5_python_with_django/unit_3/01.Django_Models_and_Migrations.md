# Django Models and Migrations

---

## 1. Introduction to ORM

**Definition:** ORM (Object-Relational Mapping) is a programming technique that allows developers to interact with a relational database using object-oriented code, instead of writing raw SQL queries directly.

### 1.1 The Core Idea

- In a relational database, data is stored in tables, rows, and columns.
- In Python, data is naturally represented using classes and objects.
- ORM acts as a translator between these two worlds: a Python class maps to a database table, a class attribute maps to a table column, and an instance of that class maps to a single row of data.

**Important Definition (Quotable):** An ORM maps database tables to Python classes, table rows to Python objects, and table columns to class attributes, allowing developers to perform database operations using Python syntax rather than SQL.

### 1.2 Django's ORM

Django comes with its own built-in ORM, which is one of its most powerful features. It is part of Django's "batteries-included" philosophy already introduced in Chapter 2.

---

## 2. Why Django Uses ORM

### 2.1 Advantages of Using ORM Instead of Raw SQL

- **Database-agnostic code:** the same Python code can work across different databases (SQLite, PostgreSQL, MySQL, Oracle) with minimal changes, since Django's ORM generates the correct SQL dialect internally.
- **Security:** Django's ORM automatically escapes query parameters, protecting against SQL injection attacks.
- **Productivity:** developers write less code and avoid repetitive SQL statements for common operations (create, read, update, delete).
- **Readability and maintainability:** Python-based queries are easier to read, debug, and refactor than long SQL strings scattered across a codebase.
- **Integration with Django's other features:** models defined via ORM automatically integrate with Django's admin interface, forms, and migrations system.

**Important Note for Exam:** A commonly asked question is "why is ORM preferred over raw SQL in Django?" — the answer should cover at least security (SQL injection protection) and portability (database-agnostic) as the two strongest points.

## 3. Defining a Model Class

**Definition:** A Django Model is a Python class that defines the structure of a database table; it is created by subclassing `django.db.models.Model`, and each class attribute represents a field (column) in that table.

### 3.1 Where Models Are Defined

- Models are written inside the `models.py` file of a Django app (this file is auto-generated when an app is created using `startapp`, as covered in Chapter 2).

### 3.2 Basic Syntax

```python
from django.db import models

class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()
    email = models.EmailField()
    date_of_admission = models.DateField()

    def __str__(self):
        return self.name
```

### 3.3 Key Points About Model Classes

- Every model class must inherit from `models.Model`.
- Django automatically adds a primary key field named `id` to every model, unless a different primary key is explicitly defined.
- The `__str__()` method is not compulsory but is strongly recommended; it defines how an object of this model is displayed as text (for example, in the Django admin interface).

**Important Definition (Quotable):** Every Django model automatically receives an auto-incrementing primary key field named id, unless the developer explicitly defines a different field as the primary key using primary_key=True.

## 4. Common Field Types

Each field in a model corresponds to a specific column type in the database, and Django translates it into the appropriate SQL data type automatically.

| Field Type | Purpose | Example |
|---|---|---|
| `CharField` | Short text, requires max_length | `models.CharField(max_length=100)` |
| `TextField` | Long text, no length limit needed | `models.TextField()` |
| `IntegerField` | Whole numbers | `models.IntegerField()` |
| `FloatField` | Decimal numbers | `models.FloatField()` |
| `DecimalField` | Precise decimal numbers (e.g., currency) | `models.DecimalField(max_digits=10, decimal_places=2)` |
| `BooleanField` | True/False values | `models.BooleanField(default=False)` |
| `DateField` | Date only | `models.DateField()` |
| `DateTimeField` | Date and time | `models.DateTimeField()` |
| `EmailField` | Text field with email format validation | `models.EmailField()` |
| `URLField` | Text field with URL format validation | `models.URLField()` |

**Exam Tip:** A very common short-answer question is to differentiate between `CharField` and `TextField`. Key distinction: `CharField` requires `max_length` and is meant for short text (like names, titles), while `TextField` has no fixed length limit and is meant for large blocks of text (like descriptions, comments).

---

## 5. Field Options

Field options are additional arguments passed to a field that control its behavior, validation, and database-level constraints.

| Option | Purpose |
|---|---|
| `max_length` | Maximum number of characters allowed (compulsory for CharField) |
| `null` | If True, allows the database column to store NULL (empty at the database level) |
| `blank` | If True, allows the field to be empty in forms/validation (this is a Django-level check, not a database-level one) |
| `default` | Specifies a default value if none is provided |
| `unique` | If True, ensures no two rows can have the same value in this field |
| `choices` | Restricts the field to a fixed set of predefined values |
| `primary_key` | If True, marks this field as the primary key instead of the default auto id |

### 5.1 null vs blank

| Aspect | null | blank |
|---|---|---|
| Level | Database-level | Django form/validation-level |
| Effect | Allows the column to store NULL in the database | Allows the field to be left empty during form validation |
| Typical Usage | Used for non-string fields (IntegerField, DateField) where "no value" needs to be NULL | Used to allow optional fields in forms |

**Important Definition (Quotable):** null is a database-level setting that determines whether a column can store NULL, whereas blank is a Django-level validation setting that determines whether a field is allowed to be empty during form validation; they serve different layers and are often used together for optional fields.

### 5.2 Example Using Field Options

```python
class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField(default=18)
    email = models.EmailField(unique=True)
    address = models.TextField(null=True, blank=True)
```

## 6. Migrations Concept

**Definition:** A migration is Django's way of propagating changes made to models (adding a field, deleting a model, etc.) into the database schema; migrations are essentially version control for the database structure.

### 6.1 Why Migrations Are Needed

- Models are defined in Python, but the actual database table does not exist until Django is told to create it.
- Every time a model is changed (a field added, removed, or modified), the underlying database table must be updated to match — migrations automate this process instead of requiring manual SQL commands.
- Migrations also allow the database schema's history to be tracked over time, similar to how Git tracks code changes.

**Important Note for Exam:** A model class alone does NOT create a database table. The table is only created after migrations are generated and applied. This is a very common conceptual question — many students incorrectly assume the table exists as soon as the model is written.

## 7. makemigrations and migrate

These are two separate, sequential commands, and understanding the difference between them is one of the most important exam points in this chapter.

### 7.1 makemigrations

**Definition:** `makemigrations` is a Django management command that inspects the current state of the models and generates migration files describing the changes needed to bring the database schema in sync with the models.

```bash
python manage.py makemigrations
```

- This command does NOT touch the database itself.
- It only creates migration files (Python files) inside the `migrations/` folder of the relevant app.

### 7.2 migrate

**Definition:** `migrate` is a Django management command that applies pending migration files to the actual database, executing the necessary SQL to create, alter, or delete tables and columns.

```bash
python manage.py migrate
```

- This command actually modifies the database.
- It reads the migration files generated by `makemigrations` and executes the corresponding SQL.

### 7.3 Comparison Table

| Aspect | makemigrations | migrate |
|---|---|---|
| Purpose | Generates migration files based on model changes | Applies migration files to the actual database |
| Touches Database? | No | Yes |
| Output | Python migration files in migrations/ folder | Actual tables/columns created or altered in the database |
| Order of Use | Run first | Run second, after makemigrations |

**Important Definition (Quotable):** makemigrations is a dry-run-like step that only records what needs to change, while migrate is the step that actually executes those changes against the database; running makemigrations alone has no effect on the database itself.

**Exam Tip:** This exact distinction — "makemigrations creates the plan, migrate executes the plan" — is one of the highest-yield exam points in this entire unit. Expect it in short answer, medium answer, and possibly viva form.

## 8. Migration File Structure

When `makemigrations` is run, Django creates a numbered Python file inside the app's `migrations/` folder, such as `0001_initial.py`.

### 8.1 Example Migration File (Simplified)

```python
from django.db import migrations, models

class Migration(migrations.Migration):

    initial = True

    dependencies = []

    operations = [
        migrations.CreateModel(
            name='Student',
            fields=[
                ('id', models.AutoField(auto_created=True, primary_key=True, serialize=False)),
                ('name', models.CharField(max_length=100)),
                ('age', models.IntegerField()),
                ('email', models.EmailField(max_length=254)),
            ],
        ),
    ]
```

### 8.2 Key Parts of a Migration File

| Part | Purpose |
|---|---|
| `dependencies` | Lists other migrations that must be applied before this one (ensures correct order) |
| `operations` | List of actual changes to apply — CreateModel, AddField, AlterField, DeleteModel, etc. |
| `initial = True` | Marks this as the first migration for the app |

**Important Note for Exam:** Migration files are plain Python files and are meant to be committed to version control (like Git) along with the rest of the project code, since they represent the history of the database schema.

## 9. Meta Class Basics

**Definition:** The Meta class is an inner class defined inside a Django model that provides metadata (configuration options) about the model, without adding any actual database field.

### 9.1 Syntax

```python
class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()

    class Meta:
        ordering = ['name']
        verbose_name = 'Student Record'
        verbose_name_plural = 'Student Records'
```

### 9.2 Common Meta Options

| Option | Purpose |
|---|---|
| `ordering` | Specifies the default order in which records are returned from queries |
| `verbose_name` | A human-readable singular name for the model (used in the admin interface) |
| `verbose_name_plural` | A human-readable plural name for the model (Django would otherwise just add "s") |
| `db_table` | Allows specifying a custom name for the database table (instead of Django's default naming) |

**Important Note for Exam:** By default, Django names a model's database table using the pattern `appname_modelname` in lowercase (for example, `students_student`); the `db_table` Meta option overrides this default naming.

## 10. Hands-On: Creating a Model and Inspecting the Table

This section ties the entire lecture together as a practical walkthrough.

### 10.1 Step 1: Define the Model

In `students/models.py`:

```python
from django.db import models

class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField(default=18)
    email = models.EmailField(unique=True)
    date_of_admission = models.DateField(null=True, blank=True)

    class Meta:
        ordering = ['name']

    def __str__(self):
        return self.name
```

### 10.2 Step 2: Generate Migrations

```bash
python manage.py makemigrations
```

**Expected output (example):**
```
Migrations for 'students':
  students/migrations/0001_initial.py
    - Create model Student
```

### 10.3 Step 3: Apply Migrations

```bash
python manage.py migrate
```

**Explain:** This command also applies Django's own built-in migrations (for admin, auth, sessions, etc.) the first time it is run on a fresh project — this is why several lines of output appear, not just one referring to the `Student` model.

### 10.4 Step 4: Inspect the Resulting Table

Using the database shell:

```bash
python manage.py dbshell
```

Then, for SQLite (Django's default database):

```sql
.tables
.schema students_student
```

**Explain:** `students_student` is the auto-generated table name, following the `appname_modelname` pattern discussed in the Meta section above. This is a good moment to physically show students that a real table with real columns now exists, matching the fields defined in the model class.
