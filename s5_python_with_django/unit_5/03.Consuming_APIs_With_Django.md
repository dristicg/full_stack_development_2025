# Consuming APIs with Django


## 1. Why Consume APIs

**Definition:** Consuming an API refers to a program acting as a CLIENT — sending requests to someone else's (or one's own) API endpoint and processing the response — the exact reverse role of everything built across Day 1 and Day 2, where the Django project was the one PROVIDING an API.

### 1.1 Real-World Reasons to Consume an API

- Fetching data from a third-party service — weather data, payment processing, maps, currency conversion.
- Service-to-service communication — one internal system (e.g., a notifications service) calling another (e.g., a user service).
- A Django view that needs to display data pulled from the project's own DRF API, rather than querying the database directly — useful in larger systems where the API layer is the single source of truth.

**Important Note for Exam:** Day 1 and Day 2 were about the Django project acting as a SERVER (providing data to others). Day 3 flips this — the Django project now acts as a CLIENT (requesting data from somewhere else). Both roles use the exact same HTTP concepts from Chapter 2, Day 1 — only the direction of "who is making the request" changes.

---

## 2. The requests Library

**Definition:** `requests` is a widely used third-party Python library that provides a simple interface for making HTTP requests (GET, POST, PUT, DELETE, etc.) from Python code, commonly used to consume external APIs.

### 2.1 Installation

```bash
pip install requests
```

**Important Note for Exam:** `requests` is NOT part of Django, and is not the same as Django's `request` object (the one passed into every view). This distinction is a common point of confusion — `request` (Django, lowercase, singular) represents an incoming HTTP request to a Django view; `requests` (the library, plural) is used to SEND outgoing HTTP requests to other servers.

### 2.2 Basic Usage Outside Django (Conceptual Warm-Up)

```python
import requests

response = requests.get('https://api.example.com/data/')
print(response.status_code)
print(response.json())
```

## 3. Making GET Calls to an External API

### 3.1 Example — Calling a Public API from a Django View

```python
import requests
from django.shortcuts import render

def weather_view(request):
    response = requests.get('https://api.example.com/weather?city=Ahmedabad')
    data = response.json()
    context = {'weather': data}
    return render(request, 'students/weather.html', context)
```

**Explain each piece:**
- `requests.get(url)` — sends a GET request (exactly the same HTTP method from Chapter 2, Day 1) to the given URL, and returns a `Response` object (note: this is `requests`' own `Response` class, unrelated to DRF's `Response` class from Days 1–2, despite the shared name).
- `response.json()` — parses the response body (assumed to be JSON text) into a Python dictionary or list, ready to use like any other Python data.
- The resulting `data` is passed into `context` and rendered through a template, exactly like any other Django view from Chapter 2, Day 4 onward — the only difference is where the data originally came from (an external API call, instead of the local database).

### 3.2 Checking response.status_code

```python
response = requests.get('https://api.example.com/weather?city=Ahmedabad')
if response.status_code == 200:
    data = response.json()
else:
    data = None
```

**Explain:** `response.status_code` gives back the exact same HTTP status codes taught in Chapter 2, Day 1 (and reused with DRF's `status` module in Day 2) — checking it before trusting `response.json()` is standard practice, since a failed request (404, 500, etc.) may not return valid JSON at all.

## 4. POSTing Data to an API

### 4.1 Example — Sending Data to an API

```python
import requests

def create_remote_student(request):
    payload = {
        'name': 'Amit Sharma',
        'age': 20,
        'email': 'amit@example.com',
    }
    response = requests.post('https://api.example.com/students/', json=payload)
    return render(request, 'students/api_result.html', {'result': response.json()})
```

**Explain:**
- `requests.post(url, json=payload)` — the `json=` argument automatically converts the Python dictionary into JSON text and sets the correct `Content-Type: application/json` header — no manual JSON encoding needed.
- This is the client-side mirror of Day 2's server-side POST handling: there, `request.data` was READ on the server; here, `json=payload` is what gets SENT from the client.

### 4.2 Sending Form-Encoded Data Instead of JSON

```python
response = requests.post('https://api.example.com/students/', data=payload)
```

**Important Note for Exam:** `requests.post(url, data=payload)` sends form-encoded data (like a traditional HTML form submission, Chapter 4), while `requests.post(url, json=payload)` sends JSON. Many modern REST APIs (including DRF APIs, by default) expect JSON — using `data=` instead of `json=` against a JSON-only API is a common real-world bug, worth demonstrating deliberately if time allows.

## 5. Handling API Errors and Response Codes

### 5.1 Why Error Handling Matters

- An external API might be temporarily down, rate-limited, or reject the request due to invalid data — a Django view calling it must handle these cases gracefully rather than crashing.

### 5.2 Practical Error Handling Pattern

```python
import requests

def weather_view(request):
    try:
        response = requests.get('https://api.example.com/weather?city=Ahmedabad', timeout=5)
        response.raise_for_status()
        data = response.json()
        error = None
    except requests.exceptions.RequestException as e:
        data = None
        error = str(e)

    context = {'weather': data, 'error': error}
    return render(request, 'students/weather.html', context)
```

**Explain each new piece:**
- `timeout=5` — sets a maximum wait time (in seconds) for the external server to respond; without a timeout, a slow or unresponsive external API could leave the Django view hanging indefinitely.
- `response.raise_for_status()` — automatically raises an exception if the response's status code indicates an error (4xx or 5xx), avoiding the need to manually check `if response.status_code == 200:` every time.
- `requests.exceptions.RequestException` — a base exception class covering network errors, timeouts, and bad status codes together, caught here in one `except` block.

**Important Note for Exam:** This is the exact same defensive mindset already applied in earlier chapters — just as a view should never assume `request.POST.get('field')` will always contain valid data (Chapter 4's validation), a view calling an external API should never assume the external service will always respond successfully. Both require explicit error handling rather than optimistic assumptions.

## 6. Hands-On: A Django View Consuming the Project's Own DRF API

This is the most instructive example, since it closes the loop within a single project — the Django project acts as both the API provider (from Days 1–2) and the API consumer (today), calling itself.

### 6.1 The View

```python
import requests
from django.shortcuts import render

def student_list_from_api(request):
    response = requests.get('http://127.0.0.1:8000/api/students/')
    if response.status_code == 200:
        students = response.json()
    else:
        students = []
    return render(request, 'students/student_list_from_api.html', {'students': students})
```

**Explain:** `http://127.0.0.1:8000/api/students/` is the exact same ViewSet-powered endpoint built in Day 2 — this view is simply a regular Django view that happens to fetch its data via an HTTP call to the project's own API, rather than querying `Student.objects.all()` directly.

### 6.2 The Template

```html
{% extends 'students/base.html' %}
{% block title %}Students (via API){% endblock %}
{% block content %}
    <h1>Students (Fetched via API)</h1>
    <ul>
    {% for student in students %}
        <li>{{ student.name }} — Age: {{ student.age }}</li>
    {% empty %}
        <li>No students found, or the API is unavailable.</li>
    {% endfor %}
    </ul>
{% endblock %}
```

**Explain:** Because `response.json()` already returned a list of plain Python dictionaries, the template loops over it exactly like any other list of objects — `{{ student.name }}` works via Django's dot-notation lookup (Chapter 2, Day 4), even though `student` here is a dictionary, not a `Student` model instance.

### 6.3 Trace the Complete Flow

1. Browser sends GET request to `/students-from-api/` (a regular Django URL, unrelated to the `/api/` prefix).
2. Django routes to `student_list_from_api`.
3. Inside the view, `requests.get('http://127.0.0.1:8000/api/students/')` sends a SECOND, separate HTTP request — this time from the Django server itself, acting as a client, to its own API endpoint.
4. That second request is handled entirely independently by the `StudentViewSet` built in Day 2 — URL routing, the ViewSet, the serializer, all run exactly as they would for any other client.
5. The API responds with JSON; `response.json()` parses it back into Python data.
6. This data is passed into `context`, and `render()` produces the final HTML page — sent back as the response to the ORIGINAL browser request from Step 1.

**Say this to the class:** "Isme do alag-alag HTTP request-response cycles chal rahe hain — ek jo browser se view tak aayi, aur ek jo view ne khud apni hi API ko bheji. Yeh dikhata hai ki ek Django project simultaneously client aur server, dono ban sakta hai."
