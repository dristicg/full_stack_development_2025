# DRF Introduction, Setup & Serializers

## 1. What is a REST API

**Definition:** A REST API (Representational State Transfer Application Programming Interface) is a web API that follows REST architectural principles, allowing different software systems to communicate over HTTP by exchanging structured data (typically JSON), using standard HTTP methods to represent operations on resources.

### 1.1 Recap — Building Blocks Already Known

Everything a REST API needs has already been covered in earlier chapters:

| Already Known From | Now Used As |
|---|---|
| HTTP methods (Chapter 2, Day 1) | The verbs an API uses: GET, POST, PUT, PATCH, DELETE |
| HTTP status codes (Chapter 2, Day 1) | How an API reports success/failure: 200, 201, 400, 404, etc. |
| URL structure and routing (Chapter 2, Day 3) | How API endpoints are addressed |
| Views returning structured data | The same request-in, response-out pattern, just returning JSON instead of HTML |

**Important Note for Exam:** A REST API is not a completely new concept — it reuses the same HTTP fundamentals from Chapter 2. The key difference is that a normal Django view (as built through Chapters 2–4) typically returns HTML for a human to read in a browser, while a REST API returns structured data (JSON) for another program to read and process.

## 2. REST Principles

**Definition:** REST (Representational State Transfer) is an architectural style for designing networked applications, defined by a set of constraints that a system should follow to be considered "RESTful."

### 2.1 Key REST Principles

| Principle | Meaning |
|---|---|
| **Statelessness** | Each request from a client must contain all the information needed to process it; the server does not store client session state between requests (this directly echoes HTTP's own stateless nature from Chapter 2, Day 1) |
| **Resource-Based** | Everything is treated as a "resource" (e.g., a student, a course), each identified by a unique URL |
| **Standard HTTP Methods** | GET (read), POST (create), PUT/PATCH (update), DELETE (remove) — mapped consistently onto resources |
| **Representation** | A resource is exchanged as a "representation" of its state — typically JSON — not the actual server-side object itself |
| **Uniform Interface** | Consistent, predictable URL patterns and behavior across all endpoints |

### 2.2 Example — Resource-Based URLs

| Action | HTTP Method | URL |
|---|---|---|
| List all students | GET | `/api/students/` |
| Get one student | GET | `/api/students/1/` |
| Create a student | POST | `/api/students/` |
| Update a student | PUT | `/api/students/1/` |
| Delete a student | DELETE | `/api/students/1/` |

**Important Definition (Quotable):** In REST, the URL identifies WHAT resource is being acted on (e.g., /api/students/1/ identifies student #1), while the HTTP method identifies WHAT ACTION to perform on it — the same URL can mean different things depending on whether it receives a GET, PUT, or DELETE request.

## 4. Serializers — Introduction

**Definition:** A serializer in Django REST Framework is a class that converts complex data — such as Django model instances or QuerySets — into JSON (a process called serialization), and can also convert incoming JSON data back into Python data structures for validation and saving (a process called deserialization).

### 4.1 Why Serializers Are Needed

- A Django `Student` object is a Python object, living in memory — it cannot be sent over HTTP directly. It must first be converted into a text-based format like JSON.
- Serializers do for JSON conversion what Forms (Chapter 4) do for HTML form data — validating and converting between raw submitted data and proper Python/model objects.

**Important Definition (Quotable):** Serialization is the process of converting a Python object (like a model instance) into a format that can be easily transmitted, such as JSON; deserialization is the reverse process — converting received JSON data back into Python objects, typically to validate and save it.

### 4.2 Where Serializers Are Defined

By convention, serializers are written in a file named `serializers.py`, created manually inside the relevant app — the same manual-file-creation pattern already seen for `urls.py` (Chapter 2, Day 3) and `forms.py` (Chapter 4, Day 1).

## 5. ModelSerializer

**Definition:** ModelSerializer is a DRF class that automatically generates a serializer's fields based on a specified Django Model, in a way directly analogous to how ModelForm (Chapter 4, Day 1) automatically generates form fields from a Model.

### 5.1 Basic Syntax

```python
# students/serializers.py
from rest_framework import serializers
from .models import Student

class StudentSerializer(serializers.ModelSerializer):
    class Meta:
        model = Student
        fields = ['id', 'name', 'age', 'email', 'department']
```

**Explain, drawing the direct parallel to ModelForm:**

| ModelForm (Chapter 4) | ModelSerializer (Today) |
|---|---|
| `class Meta: model = Student` | `class Meta: model = Student` |
| `fields = [...]` | `fields = [...]` |
| Converts HTML form data ↔ model instance | Converts JSON data ↔ model instance |
| `form.is_valid()` | `serializer.is_valid()` |
| `form.save()` | `serializer.save()` |

**Important Note for Exam:** This parallel between ModelForm and ModelSerializer is one of the highest-yield points in this entire chapter — both use a Meta class with `model` and `fields`, both have an `is_valid()`/`save()` pattern, and understanding one makes the other far easier to learn.

### 5.2 fields = '__all__' and exclude

Exactly as with ModelForm:

```python
class StudentSerializer(serializers.ModelSerializer):
    class Meta:
        model = Student
        fields = '__all__'
```

```python
class StudentSerializer(serializers.ModelSerializer):
    class Meta:
        model = Student
        exclude = ['id']
```

## 6. Converting Model Instances to/from JSON

### 6.1 Serializing (Model → JSON) — Shell Demonstration

```python
python manage.py shell
```

```python
from students.models import Student
from students.serializers import StudentSerializer

student = Student.objects.get(id=1)
serializer = StudentSerializer(student)
serializer.data
```

**Expected output (example):**
```python
{'id': 1, 'name': 'Amit Sharma', 'age': 20, 'email': 'amit@example.com', 'department': 1}
```

**Explain:** `serializer.data` gives a Python dictionary — this is not yet JSON text, but it is now in a format DRF can easily convert into actual JSON text for an HTTP response.

### 6.2 Serializing a QuerySet (Multiple Objects)

```python
students = Student.objects.all()
serializer = StudentSerializer(students, many=True)
serializer.data
```

**Important Note for Exam:** The `many=True` argument is compulsory when serializing more than one object (a QuerySet) — without it, DRF assumes a single object is being serialized and will raise an error when given a QuerySet instead.

### 6.3 Deserializing (JSON → Model) — Shell Demonstration

```python
data = {'name': 'Priya Patel', 'age': 21, 'email': 'priya@example.com'}
serializer = StudentSerializer(data=data)
serializer.is_valid()
serializer.save()
```

**Explain the parallel to ModelForm one more time:** `is_valid()` → `save()` is exactly the same two-step pattern from Chapter 4, Day 1 — the only difference is the input source (a Python dict representing JSON, instead of `request.POST`).

## 7. Building a First GET Endpoint (List + Detail)

### 7.1 The View — Using @api_view Decorator

```python
# students/views.py (or a separate api_views.py, per course convention)
from rest_framework.decorators import api_view
from rest_framework.response import Response
from .models import Student
from .serializers import StudentSerializer

@api_view(['GET'])
def student_list_api(request):
    students = Student.objects.all()
    serializer = StudentSerializer(students, many=True)
    return Response(serializer.data)


@api_view(['GET'])
def student_detail_api(request, student_id):
    student = get_object_or_404(Student, pk=student_id)
    serializer = StudentSerializer(student)
    return Response(serializer.data)
```

**Explain each new piece:**
- `@api_view(['GET'])` — a decorator marking this function as a DRF API view, and restricting it to only accept GET requests (a request with any other method receives an automatic 405 Method Not Allowed response).
- `Response(serializer.data)` — DRF's `Response` class, used instead of Django's regular `HttpResponse`/`render()`; it automatically converts the given data into proper JSON and sets the correct `Content-Type` header.

### 7.2 URL Configuration

```python
# students/urls.py
from .views import student_list_api, student_detail_api

urlpatterns = [
    # ... existing patterns ...
    path('api/students/', student_list_api, name='student_list_api'),
    path('api/students/<int:student_id>/', student_detail_api, name='student_detail_api'),
]
```

**Explain:** This is the exact same `path()` syntax from Chapter 2, Day 3 — API URLs are configured no differently than regular view URLs; only the view's return type (JSON via `Response`, instead of HTML via `render()`) differs.

## 8. Testing via the Browsable API

**Definition:** The browsable API is a feature of Django REST Framework that automatically provides a human-friendly, interactive HTML interface for testing API endpoints directly in a web browser, without needing a separate tool.

### 8.1 Using It

```bash
python manage.py runserver
```

Visit `http://127.0.0.1:8000/api/students/` directly in the browser.

**Explain what appears:** instead of raw JSON text, DRF renders a styled HTML page showing the JSON data, along with clickable options to try different HTTP methods (if the view supports them) — genuinely useful for testing during development, without needing a tool like Postman.

**Important Note for Exam:** The browsable API is a development convenience only — actual client applications (a mobile app, a frontend JavaScript app, another server) consume the raw JSON response, not this HTML page. Requesting the same URL with `Accept: application/json` (as a real client would) returns pure JSON instead of the browsable HTML.
