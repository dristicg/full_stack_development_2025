# Deployment Basics

## 1. Production Readiness

**Definition:** Production readiness refers to the set of configuration changes and practices required to safely run a Django project on a live, public server, as opposed to the local development server (`runserver`) used throughout the course so far.

### 1.1 DEBUG — Recap and Why It Matters Now

Recall from Chapter 2, Day 5: `DEBUG` is a Boolean setting controlling whether Django shows detailed technical error pages.

**Important Note for Exam:** `DEBUG = False` is COMPULSORY in production. Deploying with `DEBUG = True` exposes source code details, file paths, and configuration values to anyone who triggers an error on the live site — this is one of the most commonly tested "what could go wrong" deployment questions.

### 1.2 ALLOWED_HOSTS — Recap and Why It Matters Now

Recall from Chapter 2, Day 5: `ALLOWED_HOSTS` is a list of permitted hostnames. In development, an empty list works fine because Django auto-allows `localhost`/`127.0.0.1` when `DEBUG=True`. In production, with `DEBUG=False`, this list MUST explicitly include the live domain, or Django will refuse every request.

```python
ALLOWED_HOSTS = ['my-student-portal.onrender.com']
```

### 1.3 Environment Variables

**Definition:** An environment variable is a value stored outside of the codebase, in the operating system or hosting platform's configuration, and read by the application at runtime — used to keep sensitive or environment-specific values (like secret keys or database credentials) out of the source code itself.

**Why this matters:** `SECRET_KEY` (Chapter 2, Day 2) should never be hardcoded and committed to source control in a real deployment — anyone with access to the code repository would then have the key used for cryptographic signing.

**Reading an environment variable in settings.py:**

```python
import os

SECRET_KEY = os.environ.get('SECRET_KEY')
DEBUG = os.environ.get('DEBUG', 'False') == 'True'
```

**Explain:** `os.environ.get('SECRET_KEY')` reads the value from the environment the project is running in — on a local machine, this might be unset (requiring a fallback for development); on the hosting platform, it is configured separately through that platform's dashboard, never written directly into `settings.py`.

**Important Definition (Quotable):** Environment variables allow the exact same codebase to behave differently in different environments (development vs production) without changing any code — a secret key, a database URL, or a debug flag can all be swapped simply by changing what the hosting environment provides, rather than editing and redeploying settings.py.

### 1.4 requirements.txt

**Definition:** `requirements.txt` is a plain text file listing every Python package a project depends on, along with their exact versions, allowing the same set of dependencies to be installed on any other machine — including a hosting platform's server.

**Generating it:**

```bash
pip freeze > requirements.txt
```

**Example content:**

```
Django==5.0.6
djangorestframework==3.15.1
requests==2.31.0
gunicorn==22.0.0
```

**Explain:** When a hosting platform deploys the project, it reads `requirements.txt` and runs `pip install -r requirements.txt` to recreate the exact same package environment that exists locally — without this file, the platform would have no way of knowing which packages to install.

**Important Note for Exam:** `requirements.txt` must be kept up to date every time a new package is installed locally (by re-running `pip freeze > requirements.txt`) — a common real-world deployment failure is a missing or outdated `requirements.txt` causing an `ImportError` on the live server for a package that works fine locally.

### 1.5 gunicorn — Production Web Server (Brief Mention)

**Definition:** Gunicorn (Green Unicorn) is a production-grade WSGI HTTP server for running Python web applications, used in place of Django's own development server (`runserver`) when deploying to production.

**Explain, connecting directly to Chapter 2, Day 5:** Recall that `runserver` is explicitly documented as unsuitable for production — single-threaded, not security-reviewed for public traffic. Gunicorn is what actually runs the Django project on the live server, using the same `wsgi.py` file (Chapter 2, Day 2) that has existed in the project since its very first `startproject` command.

```bash
pip install gunicorn
```

## 2. Step-by-Step Deployment (Render)

### 2.1 Prerequisites

- Project code pushed to a GitHub repository.
- `requirements.txt` present and up to date.
- A `Procfile` or Render's build/start command configured (see Step 2.4).

### 2.2 Create a Render Account and New Web Service

1. Sign up at Render, connect the GitHub account.
2. Click "New" → "Web Service."
3. Select the repository containing the Django project.

### 2.3 Configure Build Settings

| Setting | Value |
|---|---|
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn studentportal.wsgi:application` |

**Explain the Start Command:** `studentportal.wsgi:application` refers directly back to `studentportal/wsgi.py` (Chapter 2, Day 2) — `application` is the WSGI-compatible object defined inside that file, which gunicorn uses as the entry point to run the whole project.

### 2.4 Set Environment Variables on Render

In Render's dashboard, under "Environment," add:

| Key | Value |
|---|---|
| `SECRET_KEY` | (a securely generated production secret key) |
| `DEBUG` | `False` |
| `ALLOWED_HOSTS` | The Render-provided domain, e.g. `my-student-portal.onrender.com` |

**Explain:** This is exactly the mechanism described in Section 1.3 — these values are never written into `settings.py` directly; the platform injects them at runtime.

### 2.5 Database Consideration

**Important Note for Exam:** SQLite (used throughout this course for local development, Unit 3, Day 1) is a file-based database — it does NOT persist reliably on most modern hosting platforms, since the underlying filesystem may be temporary/ephemeral. For a real production deployment, a hosted database (such as Render's own PostgreSQL offering) should be used instead, with the connection configured via an environment variable (e.g., `DATABASE_URL`) rather than SQLite's `BASE_DIR / 'db.sqlite3'` setup.

### 2.6 Deploy

Click "Create Web Service" — Render pulls the code, runs the build command, then the start command, and the project becomes live at a generated URL.

## 3. Static Files in Production

**Definition:** Static files (CSS, JavaScript, images) are NOT automatically served by Django in production the way they conveniently are in development — a separate, explicit setup is required to collect and serve them correctly.

### 3.1 STATIC_ROOT and collectstatic

```python
# settings.py
STATIC_URL = '/static/'
STATIC_ROOT = BASE_DIR / 'staticfiles'
```

```bash
python manage.py collectstatic
```

**Explain:** `collectstatic` gathers every static file from across all apps (recall Chapter 2, Day 2's `django.contrib.staticfiles`, present in `INSTALLED_APPS` since the very first project setup) into one single folder (`STATIC_ROOT`), ready to be served efficiently in production — this command is typically run automatically as part of the platform's build step.

### 3.2 WhiteNoise (Common Solution, Brief Mention)

A commonly used package, `whitenoise`, allows Django itself to serve static files efficiently in production without needing a separate, dedicated static file server — a simple, popular choice for smaller deployments exactly like this course project.

```bash
pip install whitenoise
```

```python
MIDDLEWARE = [
    'django.middleware.security.SecurityMiddleware',
    'whitenoise.middleware.WhiteNoiseMiddleware',
    # ... rest of MIDDLEWARE, unchanged from Chapter 4, Day 4 ...
]
```

**Explain, connecting to Chapter 4, Day 4:** This is a direct, practical application of the `MIDDLEWARE` list and the "order matters" rule taught in Chapter 4 — `WhiteNoiseMiddleware` is deliberately placed near the top, right after `SecurityMiddleware`, following WhiteNoise's own documented recommendation.

## 4. Post-Deployment Checks

Once deployed, verify the following, in order:

| Check | What to Confirm |
|---|---|
| Homepage loads | `/` returns 200, no error page |
| DEBUG is actually off | Deliberately visit a broken URL — confirm a generic error page appears, NOT a detailed traceback |
| Static files load | CSS/styling appears correctly, not a plain unstyled page |
| Admin panel works | `/admin/` loads and login succeeds |
| API endpoints work | `/api/students/` (Day 1–2's ViewSet) returns correct JSON on the live URL |
| Forms submit correctly | Add/Edit Student forms (Chapter 4) successfully create/update data on the live database |

**Explain the DEBUG check specifically:** this is the single most important production security check — a good habit to build is deliberately trying to break something right after deployment, specifically to confirm `DEBUG=False` is actually taking effect, rather than assuming the environment variable was set correctly.

## 5. Common Deployment Errors

| Error | Likely Cause | Fix |
|---|---|---|
| `DisallowedHost` error | Live domain not included in `ALLOWED_HOSTS` | Add the exact deployed domain to `ALLOWED_HOSTS` |
| `ModuleNotFoundError` on the live server (but works locally) | Package missing from `requirements.txt` | Re-run `pip freeze > requirements.txt` locally, commit, redeploy |
| Site loads but has no styling | Static files not collected/served | Run `collectstatic`, confirm WhiteNoise (or equivalent) is configured |
| 500 Internal Server Error, no detail shown | Expected behavior with `DEBUG=False` — check the platform's own log viewer for the actual traceback | Read the hosting platform's server logs, not the browser, to diagnose |
| Data disappears after redeploys | Still using SQLite in production | Switch to a persistent hosted database (e.g., PostgreSQL) |
| `SECRET_KEY` missing / server won't start | Environment variable not set on the platform | Add `SECRET_KEY` under the platform's environment variable settings |

**Important Note for Exam:** A recurring exam theme in this section is that production errors are deliberately LESS informative than development errors (because `DEBUG=False` hides details from the public) — this means real debugging in production always requires checking the hosting platform's server logs, not the browser page itself.
