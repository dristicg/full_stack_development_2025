# Building APIs — POST, Validation & ViewSets

## 1. Building a POST Endpoint

**Definition:** A POST endpoint, in the context of a REST API, is a view that accepts data submitted by a client and uses a serializer to validate that data and create a new object in the database.

### 1.1 Syntax

```python
from rest_framework.decorators import api_view
from rest_framework.response import Response
from rest_framework import status
from .models import Student
from .serializers import StudentSerializer

@api_view(['GET', 'POST'])
def student_list_api(request):
    if request.method == 'GET':
        students = Student.objects.all()
        serializer = StudentSerializer(students, many=True)
        return Response(serializer.data)

    elif request.method == 'POST':
        serializer = StudentSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)
```

**Explain, connecting directly back to Chapter 4's form-handling pattern:**
- `@api_view(['GET', 'POST'])` — now the same view accepts both methods, branching with `if request.method ==`, exactly the same structural pattern used in every function-based view handling both GET and POST since Chapter 2, Day 3.
- `StudentSerializer(data=request.data)` — this is deserialization: raw incoming data is passed in, ready for validation.
- `serializer.is_valid()` then `serializer.save()` — identical two-step sequence to `form.is_valid()` / `form.save()` from Chapter 4, Day 1.
- If invalid, `serializer.errors` is returned instead — the JSON-API equivalent of displaying `form.errors` in an HTML template (Chapter 4, Day 2), except here the errors themselves ARE the response, since there's no template to render them into.

## 2. request.data

**Definition:** `request.data` is DRF's equivalent of Django's `request.POST`, but more general — it correctly parses incoming data regardless of content type (JSON, form data, multipart file uploads), whereas `request.POST` only reliably handles standard HTML form submissions.

### 2.1 request.POST vs request.data — Comparison Table

| Aspect | request.POST (Django) | request.data (DRF) |
|---|---|---|
| Origin | Standard Django | Django REST Framework |
| Handles JSON body | No (only form-encoded data) | Yes |
| Handles form-encoded data | Yes | Yes |
| Typical Use | Regular HTML form views (Chapter 4) | API views |

**Important Note for Exam:** A common exam question asks why `request.data` is used instead of `request.POST` inside a DRF view — the answer must mention that real API clients (mobile apps, JavaScript frontends) typically send JSON in the request body, which `request.POST` cannot parse, but `request.data` can.

## 3. DRF Status Codes

**Definition:** `rest_framework.status` is a DRF module providing named constants for standard HTTP status codes, allowing status codes to be written descriptively (e.g., `status.HTTP_201_CREATED`) instead of as raw numbers.

### 3.1 Commonly Used DRF Status Constants

| Constant | Numeric Value | Meaning (Recap from Chapter 2, Day 1) |
|---|---|---|
| `status.HTTP_200_OK` | 200 | Request succeeded |
| `status.HTTP_201_CREATED` | 201 | A new resource was successfully created |
| `status.HTTP_204_NO_CONTENT` | 204 | Request succeeded, no content to return (common after DELETE) |
| `status.HTTP_400_BAD_REQUEST` | 400 | Malformed or invalid request data |
| `status.HTTP_404_NOT_FOUND` | 404 | Resource does not exist |
| `status.HTTP_405_METHOD_NOT_ALLOWED` | 405 | HTTP method not permitted on this endpoint |

**Explain:** These are the exact same status codes taught in Chapter 2, Day 1 — DRF simply gives them readable names instead of requiring the developer to remember and type raw numbers like `201`.

**Important Note for Exam:** Using `status.HTTP_201_CREATED` instead of writing `201` directly is a stylistic best practice in DRF code, but numerically they are identical — an exam answer using either form should be considered correct, as long as the correct code is chosen for the situation (e.g., 201 for successful creation, not 200).

## 4. APIView Class Structure

**Definition:** APIView is DRF's base class for writing class-based API views, directly analogous to Django's own `View` class (Chapter 4, Day 4), but with DRF-specific behavior such as automatic content negotiation and built-in handling of `request.data`.

### 4.1 Syntax

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from .models import Student
from .serializers import StudentSerializer

class StudentListAPIView(APIView):
    def get(self, request):
        students = Student.objects.all()
        serializer = StudentSerializer(students, many=True)
        return Response(serializer.data)

    def post(self, request):
        serializer = StudentSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)
```

### 4.2 URL Configuration

```python
from .views import StudentListAPIView

urlpatterns = [
    path('api/students/', StudentListAPIView.as_view(), name='student_list_api'),
]
```

**Explain the direct parallel to Chapter 4, Day 4's View class:** same `get()`/`post()` method-splitting structure, same compulsory `.as_view()` call in `urls.py` — the only real difference is that `APIView` methods work with `request.data` and return DRF's `Response` object, instead of `render()`/`HttpResponse`.

### 4.3 @api_view vs APIView — Comparison Table

| Aspect | @api_view (Function-Based) | APIView (Class-Based) |
|---|---|---|
| Structure | Single function, branches on request.method | Class with separate get()/post()/etc. methods |
| Matches Which Chapter 2/4 Pattern | Function-based views (Chapter 2) | Class-based View (Chapter 4, Day 4) |
| Best For | Simple, small endpoints | Endpoints needing more structure or shared logic across methods |

## 5. PUT and DELETE Endpoints

### 5.1 Detail View Supporting GET, PUT, and DELETE

```python
@api_view(['GET', 'PUT', 'DELETE'])
def student_detail_api(request, student_id):
    student = get_object_or_404(Student, pk=student_id)

    if request.method == 'GET':
        serializer = StudentSerializer(student)
        return Response(serializer.data)

    elif request.method == 'PUT':
        serializer = StudentSerializer(student, data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    elif request.method == 'DELETE':
        student.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)
```

**Explain:**
- `StudentSerializer(student, data=request.data)` — passing BOTH an existing instance AND new data is DRF's equivalent of ModelForm's `instance=student` pattern (Chapter 4, Day 1) used for editing; it tells the serializer to update this specific object rather than create a new one.
- DELETE returns `status.HTTP_204_NO_CONTENT` with no body — there is nothing meaningful to send back once an object no longer exists.

**Important Note for Exam:** A very common exam point is recognizing that `PUT` in REST corresponds to Chapter 2, Day 1's "PUT updates/replaces an existing resource completely" — this is the exact same HTTP method definition taught at the very start of the syllabus, now finally put into practical use.

## 6. ViewSets — Introduction

**Definition:** A ViewSet is a DRF class that combines the logic for a set of related views (typically list, create, retrieve, update, destroy) into a single class, reducing the repetitive GET/POST/PUT/DELETE branching seen in APIView into just a few short methods, or often no extra code at all.

### 6.1 Why ViewSets Are Useful

- The `student_list_api` and `student_detail_api` views above, together, implement all five standard REST operations (list, create, retrieve, update, delete) — but require two separate views, each with manual branching and duplicated `get_object_or_404` logic.
- A ViewSet consolidates this into ONE class, and — when combined with a Router (Section 7) — needs almost no boilerplate code at all for standard CRUD.

### 6.2 ModelViewSet — The Most Common Case

```python
from rest_framework import viewsets
from .models import Student
from .serializers import StudentSerializer

class StudentViewSet(viewsets.ModelViewSet):
    queryset = Student.objects.all()
    serializer_class = StudentSerializer
```

**Explain:** This single class — just two lines inside it — provides ALL FIVE standard operations:

| Action | HTTP Method + URL | Automatically Provided By ModelViewSet |
|---|---|---|
| List | GET `/api/students/` | Yes |
| Create | POST `/api/students/` | Yes |
| Retrieve | GET `/api/students/1/` | Yes |
| Update | PUT `/api/students/1/` | Yes |
| Partial Update | PATCH `/api/students/1/` | Yes |
| Delete | DELETE `/api/students/1/` | Yes |

**Important Definition (Quotable):** ModelViewSet is to APIView what a generic Class-Based View (Chapter 4, Day 4) is to a plain View class — it trades some direct control for a dramatic reduction in repetitive code, by assuming the standard CRUD pattern is exactly what's needed.

## 7. Routers

**Definition:** A Router is a DRF class that automatically generates the URL patterns for a ViewSet, mapping standard REST conventions (list/create at the base URL, retrieve/update/delete at a detail URL with an ID) without the developer needing to write each `path()` entry manually.

### 7.1 Syntax

```python
# students/urls.py
from rest_framework.routers import DefaultRouter
from .views import StudentViewSet

router = DefaultRouter()
router.register('students', StudentViewSet, basename='student')

urlpatterns = [
    # ... existing non-API patterns ...
]

urlpatterns += router.urls
```

**Explain:** `router.register('students', StudentViewSet)` alone generates every URL pattern that would otherwise need to be written by hand — `api/students/`, `api/students/<id>/`, with all the correct HTTP methods mapped to each, matching the table in Section 6.2 exactly.

### 7.2 ViewSet + Router — Full Comparison to Manual Approach

| Aspect | Manual @api_view Approach (Day 1–2 Start) | ViewSet + Router |
|---|---|---|
| Number of View Functions/Classes | 2 (list view, detail view) | 1 (single ViewSet class) |
| Number of URL Patterns Written | 2, written manually | 0 — router generates them |
| Lines of Branching Logic | Significant (if/elif for each method) | None, for standard CRUD |
| Best For | Learning exactly what each operation does | Real projects, once the pattern is understood |

**Important Note for Exam:** This progression — plain function view, to `@api_view` with manual branching, to `APIView` class, to `ModelViewSet` with a Router — mirrors exactly why each step exists: each layer trades a bit of explicit control for a reduction in repeated code, once the underlying pattern is well understood. A good exam answer recognizes this is a deliberate teaching progression, not four unrelated ways of doing the same thing.

## 8. Hands-On: Converting an Existing API into a ViewSet

This section takes the `student_list_api` / `student_detail_api` pair built across Day 1 and the start of Day 2, and converts them into the ViewSet + Router pattern, showing the "before and after" directly.

### 8.1 Before (Two Separate Views)

```python
@api_view(['GET', 'POST'])
def student_list_api(request):
    # ...

@api_view(['GET', 'PUT', 'DELETE'])
def student_detail_api(request, student_id):
    # ...
```

```python
urlpatterns = [
    path('api/students/', student_list_api, name='student_list_api'),
    path('api/students/<int:student_id>/', student_detail_api, name='student_detail_api'),
]
```

### 8.2 After (ViewSet + Router)

```python
# students/views.py
from rest_framework import viewsets
from .models import Student
from .serializers import StudentSerializer

class StudentViewSet(viewsets.ModelViewSet):
    queryset = Student.objects.all()
    serializer_class = StudentSerializer
```

```python
# students/urls.py
from rest_framework.routers import DefaultRouter
from .views import StudentViewSet

router = DefaultRouter()
router.register('students', StudentViewSet, basename='student')

urlpatterns = [
    # ... existing non-API urlpatterns stay unchanged ...
]

urlpatterns += router.urls
```

**Explain to the class, side by side:** "Jo humne pehle do views aur do manual URL patterns mein likha tha, ab ek single class aur ek `router.register()` line mein ho gaya. Behavior bilkul same hai — GET, POST, PUT, DELETE sab kaam karte hain — bas code bahut kam ho gaya."

### 8.3 Testing

```bash
python manage.py runserver
```

Visit `http://127.0.0.1:8000/api/students/` — the browsable API now shows a form for POST directly on the same page, and following a link to `/api/students/1/` shows GET, PUT, and DELETE options all on one page, automatically.
