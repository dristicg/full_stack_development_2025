# Introduction to Chatbots and Conversational AI

## 1. What is a "Chatbot"?

### 1.1 Simple Meaning

A **chatbot** is a computer program that **holds a conversation with a person** -- by typing, or by speaking -- and helps them get something done, such as ordering food, tracking a parcel, or finding an answer.

**Conversational AI** is the wider set of technologies that makes such conversations feel natural. It combines **Natural Language Processing (NLP)** to understand the words, **machine learning** to learn from examples, a **dialogue manager** to remember the conversation, and (for voice) **speech recognition** and **speech synthesis**.

A computer, at its core, only understands **numbers**. A chat is made of **free-flowing human language, with context built up message by message**. A chatbot is the system that **reads each message, remembers what has already been said, decides what to do, and writes a reply**.

### 1.2 Everyday Analogy

Imagine a good **waiter at a restaurant**. You say, *"I'd like a pizza."* The waiter **listens and works out what you want**. They **remember** everything your table has ordered so far. They **decide what to ask next** ("Which size?"). When needed, they **walk to the kitchen** to place the order or check something. Finally, they **speak back to you politely**. A chatbot does the same five jobs, one after the other, for every message.

### 1.3 Chatbot, Voice Assistant, Conversational AI, and LLM

These words are often mixed up. Here is how they differ:

| Term | Meaning | Example |
| :-- | :-- | :-- |
| **Chatbot** | A program that holds a text (or voice) conversation | The help chat on a shopping website |
| **Voice Assistant** | A chatbot that also listens and speaks | The assistant on a phone or a smart speaker |
| **Conversational AI** | The wider technology that makes natural conversation possible (NLP, machine learning, dialogue management, speech) | The "engine" under chatbots and voice assistants |
| **Large Language Model (LLM)** | A very large neural network trained on huge amounts of text that can write new text; the "brain" of many modern chatbots | The model that writes the replies in a modern chat assistant |

### 1.4 Why Is Conversation Hard for Computers?

| Challenge | Example | Why It Is Hard |
| :-- | :-- | :-- |
| **Many Ways to Say One Thing** | *"I want a pizza"*, *"pizza please"*, *"can I get one pizza?"* | The goal is the same, but the words are different every time |
| **Missing Details** | *"Make it medium."* | Make **what** medium? The bot must remember the earlier messages |
| **Typos and Slang** | *"ordr a piza pls"* | The text does not match any clean, expected wording |
| **Ambiguity** | *"I need to cancel."* | Cancel an order, a booking, or a subscription? |
| **Going Off-Topic** | Asking a pizza bot, *"Who won the match yesterday?"* | The bot must notice that the question is outside its job |
| **Mixed Languages** | *"mera order kahan hai?"* (Hindi in English letters) | Real users mix languages and spellings freely |

### 1.5 Where Are Chatbots Used?

| Application | What the Chatbot Does |
| :-- | :-- |
| **Customer Support** | Answers common questions and passes hard cases to a human |
| **Banking and Insurance** | Shows balances, explains charges, and guides people through forms |
| **Online Shopping** | Tracks orders, handles returns, and recommends products |
| **Booking and Ordering** | Books tickets, tables, and appointments, or takes food orders |
| **Education** | Answers a student's questions and explains topics step by step |
| **Workplace Help Desks** | Answers staff questions about leave, IT problems, and policies |
| **Voice Assistants** | Sets alarms, plays music, and controls smart-home devices by voice |

### 1.6 A Short History

| Year | Milestone | Why It Matters |
| :-: | :-- | :-- |
| **1966** | **ELIZA** | An early program that matched keywords and rephrased the user's own words; it felt like a conversation, but it understood nothing |
| **2011** | **Siri** | Brought a voice assistant to everyday phones |
| **2014** | **Amazon Alexa** | Put a voice assistant in a smart speaker for the home |
| **2022** | **ChatGPT** | A public chatbot built on a large language model; it made LLM-based chatbots widely used |

## 2. The Big Picture -- How a Chatbot Handles One Message

Every time you send a message, it travels through a short **pipeline**. This note walks through each stage in detail.

```
THE CHATBOT PIPELINE (ONE MESSAGE IN, ONE REPLY OUT)

   USER MESSAGE (typed text, or speech that was turned into text)
              |
              v
   [ STAGE 1 ]  UNDERSTANDING (NLU)
                Find the INTENT (what the user wants) and the
                ENTITIES (the key details in the message)
              |
              v
   [ STAGE 2 ]  DIALOGUE MANAGER  <----->  [ BACKEND ]
                Remember the conversation     Databases, order
                so far and decide what        systems, and documents
                to do next                    that hold the real facts
              |
              v
   [ STAGE 3 ]  RESPONSE GENERATION (NLG)
                Turn the decision into a reply in everyday language
              |
              v
   CHATBOT REPLY (text, or text turned into speech)
```

| Stage | Input | Output |
| :-- | :-- | :-- |
| **1. Understanding (NLU)** | The user's message | An intent and a list of entities |
| **2. Dialogue Manager** | Intent, entities, and the conversation so far | The updated memory and the next action |
| **3. Response Generation (NLG)** | The chosen action | A reply written in everyday language |

The waiter from Section 1.2 maps onto these stages exactly:

| What the Waiter Does | What the Chatbot Does | Stage |
| :-- | :-- | :-- |
| Listens and works out what you want | Finds the intent and entities | Understanding |
| Remembers what your table has ordered so far | Keeps the conversation state | Dialogue Manager |
| Decides what to ask next | Chooses the next action | Dialogue Manager |
| Walks to the kitchen to place or check the order | Calls the backend system | Backend |
| Speaks back politely | Writes the reply | Response Generation |

> **Note:** In a modern chatbot built on a large language model, one model may do several of these jobs at once. The three stages above are still the clearest way to understand **what has to happen** inside any chatbot.

## 3. Types of Chatbots

### 3.1 Simple Meaning

Chatbots differ mainly in **how they decide what to say**. There are three basic types, and many real products combine them.

```
                         +---------------------+
                         |  TYPES OF CHATBOTS  |
                         +----------+----------+
                                    |
          +-------------------------+-------------------------+
          |                         |                         |
          v                         v                         v
+-------------------+     +-------------------+     +-------------------+
|  RULE-BASED BOTS  |     | INTENT-BASED BOTS |     |  GENERATIVE BOTS  |
+-------------------+     +-------------------+     +-------------------+
 follows fixed rules       ML finds the intent       an LLM writes a new
   keywords, menus         uses a ready answer       reply, word by word

                  HYBRID bots mix two or more of these.
```

### 3.2 Everyday Analogy

- A **rule-based bot** is like a **vending machine**: press button 3 and you always get the same snack. It is predictable, but it cannot cope with anything not on the buttons.
- An **intent-based bot** is like a **trained receptionist with a folder of ready answers**: whatever words you use, they work out which page of the folder fits and read it out.
- A **generative bot** is like a **very well-read person who answers in their own words**: flexible and fluent, but sometimes confidently wrong.

### 3.3 Rule-Based Bots

A rule-based bot follows **fixed if-then rules**: menus, buttons, or keywords. If the user does exactly what the designer expected, it works well.

```
                   +-----------------------------------------+
                   | BOT: Welcome! Type 1 to order a pizza,  |
                   | or 2 for opening hours.                 |
                   +-----------------------------------------+
                                        |
                +-----------------------+-----------------------+
                | user types 1                                  | user types 2
                |                                               |
                v                                               v
    +-----------------------+                       +-----------------------+
    | BOT: Which size       |                       | BOT: We open          |
    | would you like?       |                       | 11 AM to 11 PM.       |
    +-----------------------+                       +-----------------------+
```

What happens when the user does **not** follow the menu?

```
User types :  "can I get a pizza?"
The bot looks for "1" or "2" ......... no match
BOT        :  "Sorry, I did not understand. Please type 1 or 2."
```

The user's goal was perfectly clear to a human, but the bot **only matches exact patterns**, so it fails. Rule-based bots are cheap and fully predictable, but **brittle**.

### 3.4 Intent-Based Bots

An intent-based bot uses **machine learning to find the user's intent**, whatever words they use, and then gives a **ready-made answer or starts a prepared flow**.

| What the User Types | Intent the Bot Finds |
| :-- | :-- |
| *"I want a pizza"* | `order_pizza` |
| *"Can I order a pizza?"* | `order_pizza` |
| *"pizza please"* | `order_pizza` |
| *"get me a large pizza"* | `order_pizza` |

The intent finder is a **classification model** trained on many example sentences, each labeled with its intent -- this is **supervised learning** (see the Machine Learning note). Its weakness: it only knows the intents it was trained on, so a request outside that list is misunderstood or rejected.

### 3.5 Generative Bots

A generative bot uses a **large language model (LLM)** to **write a brand-new reply, word by word**, instead of picking a ready answer. It can discuss almost any topic and handle unusual wording, but it can also make mistakes and is harder to control. Section 7 explains how it works.

### 3.6 Hybrid Bots

Most real business chatbots are **hybrids**. For example, a food-ordering bot may use a language model or an intent finder to **understand** the user, **fixed rules** to make sure every needed detail is collected and the order is confirmed, and a **backend system** to get real prices and place the real order. The worked example in Section 9 is this kind of bot.

### 3.7 Comparing the Types

| Type | How It Decides the Reply | Strength | Weakness |
| :-- | :-- | :-- | :-- |
| **Rule-Based** | Fixed rules, keywords, and menus | Predictable and cheap | Fails when the wording is unexpected |
| **Intent-Based** | A trained model finds the intent; a ready answer is used | Understands many wordings | Limited to the intents it was trained on |
| **Generative** | An LLM writes a new reply | Flexible and fluent on many topics | Can state wrong things; harder to control |
| **Hybrid** | A mix of the above, plus backend systems | Flexible **and** controlled | More parts to build and maintain |

## 4. Understanding the User (NLU)

### 4.1 Simple Meaning

**Natural Language Understanding (NLU)** is the part of NLP that works out **what a message means**. It finds two things:

- **Intent** -- *what the user wants to do* (order a pizza, change the order, say yes).
- **Entities** -- *the key details* inside the message (the size, the topping, the address).

### 4.2 Everyday Analogy

Imagine reading a letter with a **sticky note** and a **highlighter**. On the sticky note you write the **one-line goal** of the letter ("wants to order a pizza") -- that is the **intent**. With the highlighter you mark the **important facts** ("large", "paneer", the address) -- those are the **entities**.

### 4.3 Intents and Entities in Action

Here are the messages from our pizza-ordering example (Section 9):

| User Message | Intent | Entities Found |
| :-- | :-- | :-- |
| *"Hi, I want to order a pizza"* | `order_pizza` | none |
| *"Large, with paneer"* | `inform` | size = `large`, topping = `paneer` |
| *"Actually make it medium"* | `change_order` | size = `medium` |
| *"12 Green Park Road"* | `inform` | address = `12 Green Park Road` |
| *"Yes"* | `confirm` | none |

Here is how the entities are picked out of one message:

```
"Large, with paneer"
 ^^^^^       ^^^^^^
 size        topping
```

### 4.4 Confidence and Fallback

The intent finder does not just name an intent; it gives a **confidence score** for each possible intent. If even the best score is **too low**, the bot should not guess. It uses a **fallback**: it says it did not understand, and steers the user back to what it can do.

Example: the user types *"Who won the cricket match yesterday?"* to the pizza bot. The scores are (illustrative numbers):

| Possible Intent | Confidence |
| :-- | :-: |
| `order_pizza` | 0.28 |
| `inform` | 0.19 |
| `greet` | 0.11 |
| all other intents together | 0.42 |

The best score, **0.28**, is below the bot's **threshold of 0.60**, so the bot does **not** act on it. It replies: *"Sorry, I can only help with pizza orders. Would you like to order one?"*

### 4.5 An Important Warning -- Ambiguous Messages

Sometimes the message really does have **more than one meaning**. *"I need to cancel."* could mean cancel an order, a booking, or a subscription. A good bot **asks a short clarifying question** ("Do you want to cancel your order or your subscription?") instead of guessing, because a wrong guess could cancel the wrong thing.

## 5. Remembering the Conversation (Dialogue Management)

### 5.1 Simple Meaning

A conversation is more than single messages: each message depends on the ones before it. The **dialogue manager** is the part of the chatbot that:

- keeps the **state** -- what the bot already knows so far, and
- chooses the **next action** -- what the bot should do now (ask a question, confirm, place the order, hand over to a human).

### 5.2 Everyday Analogy

Think of the waiter's **notepad**. As you speak, they fill it in: *size: large, topping: paneer*. When you say, *"Actually make it medium,"* they **cross out "large" and write "medium"**. When the notepad is complete, they read it back to you and then take it to the kitchen. The dialogue manager's **state** is that notepad.

### 5.3 Slots and Slot Filling

A **slot** is a **blank that the bot must fill before it can act**. For a pizza order the slots are the **size**, the **topping**, and the **delivery address** (the quantity is taken as 1 unless the user says otherwise -- a **default**). The bot keeps asking until **every slot is filled**. This is called **slot filling**.

```
THE ORDER FORM THE BOT IS FILLING IN (state after Turn 2 of the example)

   SIZE      [x]  large
   TOPPING   [x]  paneer
   ADDRESS   [ ]  (still empty)      <-- ask for this next
```

A correction simply **replaces** the old value in the slot, as the notepad example showed.

### 5.4 Remembering the Context

People use short words that only make sense with earlier messages:

| What the User Says | What the Bot Must Work Out |
| :-- | :-- |
| *"Make it medium."* | **It** = the pizza in the current order |
| *"Add extra cheese to that."* | **That** = the pizza discussed a moment ago |
| *"Yes."* | Yes to **which question**? The last one the bot asked |

Without memory of the earlier turns, *"Yes."* would mean nothing.

### 5.5 Choosing the Next Action

The dialogue manager follows a **policy** -- a set of rules (or a learned model) that maps the current state to the next action:

| Situation | Next Action |
| :-- | :-- |
| Some slots are still empty | Ask for the **next missing slot** |
| All slots are filled, but not yet confirmed | Read the details back and ask for confirmation |
| The user confirmed | Call the backend to **place the order** |
| The intent is unclear or confidence is low | Ask a clarifying question, or use the fallback |
| The user asks for a person, or the bot keeps failing | **Hand over to a human** |

### 5.6 Confirm Before Acting

Placing an order, moving money, or cancelling a booking are actions that are **hard to undo**. A careful bot therefore **reads the details back and waits for a clear "yes"** before it acts. This one habit prevents many costly mistakes.

## 6. Creating the Reply (Response Generation)

### 6.1 Simple Meaning

**Natural Language Generation (NLG)** is the step that turns the bot's decision into **a sentence a person can read**. The decision *"ask for the address"* becomes *"What is your delivery address?"*

### 6.2 Everyday Analogy

Think of **writing letters**. A **form letter with blanks** ("Dear ___, your order of ___ is ready") is quick and always correct. A **letter picked from a folder of ready-made letters** is safe and polished. A **letter written fresh by a skilled writer** is the most flexible -- but it could contain a slip. Chatbots can write replies in all three ways.

### 6.3 Three Ways to Produce a Reply

| Method | How It Works | Example Reply |
| :-- | :-- | :-- |
| **Template** | A fixed sentence with blanks that are filled from the bot's state | *"Changed to a {size} {topping} pizza."* becomes *"Changed to a medium paneer pizza."* |
| **Retrieved** | The bot picks the best-matching ready-made answer | The stored answer to *"What are your opening hours?"* |
| **Generated** | An LLM writes a new reply from scratch | A fresh explanation written for this exact question |

### 6.4 Real Facts Come from the Backend

A bot should **not make up facts such as prices, stock, or order status**. It should **look them up** in the company's systems (the **backend**) and then put the result into the reply.

```
User      :  "Where is my order?"
Bot       :  looks up the order in the order system
Backend   :  status = "out for delivery"
Bot       :  "Your order is out for delivery."
```

### 6.5 Good Reply Habits

- **Keep replies short.** Long walls of text are hard to read in a chat window.
- **Ask one question at a time**, as the pizza bot does.
- **Say what the bot just understood** ("Changed to a medium paneer pizza") so the user can spot a mistake at once.

## 7. How Modern (LLM) Chatbots Work

### 7.1 Simple Meaning

A **large language model (LLM)** is a very large neural network that has learned from an enormous amount of text. Its basic skill is simple: **given some text, predict what word (or word-piece) most likely comes next**. A chatbot built on an LLM writes its whole reply by predicting **one piece at a time**. The pieces are **tokens**, as described in the NLP note.

### 7.2 Everyday Analogy

You have seen **autocomplete on a phone keyboard** suggesting the next word. An LLM is like that idea scaled up enormously: it has read far more text, and it considers the **whole conversation so far** rather than just the last word or two.

### 7.3 Predicting the Next Word

The model gives **every possible next word a probability**. These numbers are illustrative:

```
Text so far:  "The cat sat on the ____"

mat           45%  ##################
sofa          20%  ########
floor         15%  ######
roof           5%  ##
other words   15%  ######

(each # = 2.5%)
```

The model usually picks a **likely** word, but not always the single top one; it chooses among the likely words with a little randomness. That is why asking the same question twice can give **differently worded** answers. After a word is chosen, it is added to the text and the model predicts again:

```
"The cat sat on the"          -> predicts "mat"
"The cat sat on the mat"      -> predicts "."
"The cat sat on the mat."     -> predicts "end of reply" -> STOP
```

### 7.4 How an LLM Chatbot Is Trained

```
HOW MANY MODERN CHATBOTS ARE TRAINED

   [ STAGE A ]  PRE-TRAINING
                Read a huge amount of text and learn to predict
                the next word
              |
              v
   [ STAGE B ]  INSTRUCTION TUNING
                Learn from example requests paired with good answers,
                so the model follows instructions instead of just
                continuing the text
              |
              v
   [ STAGE C ]  FEEDBACK TUNING
                People compare answers; the model is nudged toward the
                answers that people prefer
              |
              v
   A CHATBOT THAT CAN FOLLOW REQUESTS IN A CONVERSATION
```

### 7.5 Memory Is Re-Sent History

In a basic setup, the model **does not keep the conversation inside itself between requests**. Instead, the chat application **sends the earlier messages again with every new message**. This is how the model "remembers" that the pizza was large and paneer when the user says *"Actually make it medium."*

```
EVERYTHING SENT TO THE MODEL TO WRITE THE REPLY FOR TURN 3
+--------------------------------------------------------------------------------+
| Instructions : You are a friendly pizza-ordering helper.                       |
| User         : Hi, I want to order a pizza                                     |
| Bot          : Sure! What size would you like -- small, medium, or large?      |
| User         : Large, with paneer                                              |
| Bot          : Large paneer pizza -- got it. What is your delivery address?    |
| User         : Actually make it medium            <-- the newest message       |
+--------------------------------------------------------------------------------+
```

The amount of text a model can read at one time is limited; it is called the **context window**. In a very long conversation, older parts may need to be shortened or dropped, and the bot can then **forget** early details.

### 7.6 Hallucination and How to Reduce It

An LLM writes text that is **likely and fluent**, not text that has been **checked as true**. So it can produce a confident, well-written statement that is **wrong**. This is called a **hallucination**.

One popular fix is **retrieval-augmented generation (RAG)**: first **look up** the real information, then **let the model write the answer from it**.

```
RETRIEVAL-AUGMENTED GENERATION (RAG)

   USER QUESTION   "What is your refund policy?"
              |
              v
   [ 1. SEARCH ]   Look through the company's own documents
              |
              v
   [ 2. PICK ]     Take the few most relevant passages
              |
              v
   [ 3. ASK ]      Give the model the question AND those passages
              |
              v
   [ 4. ANSWER ]   The model writes a reply based on the passages
```

### 7.7 An Important Warning -- Fluent Does Not Mean Correct

A smooth, friendly reply is **not proof that it is right**. For anything that matters -- prices, medical or legal facts, orders -- a good chatbot **gets the facts from a trusted source** (the backend or documents), **confirms before acting**, and **hands over to a human** when it is unsure.

## 8. Voice Chatbots

A voice assistant is a chatbot with **two extra parts around it**: one to **listen** and one to **speak**.

```
HOW A VOICE ASSISTANT WORKS

   USER SPEAKS
              |
              v
   [ SPEECH RECOGNITION (ASR) ]   speech -> text
              |
              v
   [ CHATBOT BRAIN ]              understand, remember, decide,
              |                   and write the reply (as text)
              v
   [ TEXT-TO-SPEECH (TTS) ]       text -> speech
              |
              v
   USER HEARS THE REPLY
```

- Many voice assistants first wait for a **wake word**, using a small program that listens only for that phrase.
- Speech recognition is described in the Speech Recognition note. Its mistakes **pass straight into the chatbot**: if *"light"* is heard as *"right"*, the chatbot receives the wrong text and may answer the wrong question.

## 9. Full Worked Example -- Ordering a Pizza, Start to Finish

**The scenario:** a customer orders a pizza from a bot called **PizzaPal**. This is a **hybrid bot** (Section 3.6): it understands free-form messages, fills in slots by rules, and places the order through the backend.

### 9.1 The Whole Conversation

```
   User : Hi, I want to order a pizza
   Bot  : Sure! What size would you like -- small, medium, or large?

   User : Large, with paneer
   Bot  : Large paneer pizza -- got it. What is your delivery address?

   User : Actually make it medium
   Bot  : Changed to a medium paneer pizza. What is your delivery address?

   User : 12 Green Park Road
   Bot  : Please confirm: 1 medium paneer pizza to 12 Green Park Road.
          Shall I place the order?

   User : Yes
   Bot  : Done! Your order is placed and should arrive in about 30 minutes.
```

(The delivery time is made up for the example.)

### 9.2 One Turn Under the Microscope -- Turn 3

Here is what happens inside the bot when the user types *"Actually make it medium"*:

```
USER MESSAGE   "Actually make it medium"
              |
              v   Step 1: UNDERSTAND (NLU)
   intent = change_order        (confidence 0.91)
   entity = size: medium
              |
              v   Step 2: LOOK AT THE STATE (what does the bot remember?)
   size = large  |  topping = paneer  |  address = (empty)
              |
              v   Step 3: UPDATE THE STATE (the new size replaces the old one)
   size = medium |  topping = paneer  |  address = (empty)
              |
              v   Step 4: DECIDE THE NEXT ACTION
   Address is still empty -> confirm the change, then ask for the address
              |
              v   Step 5: WRITE THE REPLY (fill the blanks of a template)
   "Changed to a {size} {topping} pizza. What is your delivery address?"
              |
              v
   "Changed to a medium paneer pizza. What is your delivery address?"
```

### 9.3 The Bot's Memory After Each Turn

| Turn | User Says | Intent | Entities Found | Size | Topping | Address | Bot's Action |
| :-: | :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| **1** | *"Hi, I want to order a pizza"* | `order_pizza` | none | empty | empty | empty | Ask for the size |
| **2** | *"Large, with paneer"* | `inform` | size, topping | `large` | `paneer` | empty | Ask for the address |
| **3** | *"Actually make it medium"* | `change_order` | size | `medium` | `paneer` | empty | Confirm the change; ask for the address |
| **4** | *"12 Green Park Road"* | `inform` | address | `medium` | `paneer` | `12 Green Park Road` | All slots full; ask for confirmation |
| **5** | *"Yes"* | `confirm` | none | `medium` | `paneer` | `12 Green Park Road` | Place the order through the backend |

### 9.4 What Each Step Did

| Stage | Action | Why It Was Needed | Result in the Example |
| :-- | :-- | :-- | :-- |
| **Understanding** | Find intent and entities | The bot must know what the user wants and the key details | `change_order`, size = `medium` |
| **Memory** | Keep the state between turns | Messages such as *"make it medium"* and *"Yes"* only make sense with the earlier turns | The bot knew **it** was the paneer pizza |
| **Slot Filling** | Ask for the missing slot | The order cannot be placed with blanks | The bot asked for the address |
| **Confirmation** | Read the details back | Placing an order is hard to undo | The user said *"Yes"* only after seeing the order |
| **Backend** | Place the order in the order system | The real world only changes when the system is told | The order was placed |
| **Response Generation** | Write each reply | The user needs a clear, friendly answer | Short replies, one question at a time |

### 9.5 A Side Trip -- When the User Goes Off-Topic

Suppose that at the address step the user types *"Who won the cricket match yesterday?"*

```
USER MESSAGE   "Who won the cricket match yesterday?"
              |
              v   Step 1: UNDERSTAND (NLU)
   best intent = order_pizza, confidence 0.28   (threshold is 0.60)
              |
              v   Step 2: DECIDE
   Confidence is too low -> use the FALLBACK
   The state is NOT changed (the order is still medium / paneer / no address)
              |
              v   Step 3: WRITE THE REPLY
   "Sorry, I can only help with pizza orders. What is your delivery address?"
```

The bot stays polite, **does not guess**, and **keeps the order safe** so the user can continue where they left off.

### 9.6 The Final Form

The chat began as **free-flowing language**. By the end, the bot had turned it into **one neat, structured record** that the order system can use:

```
ORDER
   item     : 1 pizza
   size     : medium
   topping  : paneer
   address  : 12 Green Park Road
   status   : placed
```

## 10. Measuring How Good a Chatbot Is

### 10.1 Common Measures

| Measure | What It Tells You |
| :-- | :-- |
| **Task Completion Rate** | The share of conversations where the user reached their goal |
| **Fallback Rate** | How often the bot had to say it did not understand |
| **Hand-Off Rate** | How often a conversation had to go to a human |
| **Intent Accuracy** | How often the intent finder picks the correct intent (a classification score) |
| **User Satisfaction (CSAT)** | How happy users say they are, for example in a rating after the chat |
| **Response Time** | How quickly the bot replies |

### 10.2 A Worked Example

Suppose PizzaPal handled **1,000 conversations** in a week (made-up numbers):

| Outcome | Conversations | Share |
| :-- | :-: | :-: |
| Order completed by the bot | 780 | **78%** |
| Handed over to a human | 100 | **10%** |
| User gave up (abandoned) | 120 | **12%** |
| **Total** | **1,000** | **100%** |

The team reads the **abandoned** conversations to find where users got stuck, adds the missing intents, and improves the wording of the questions. A chatbot is **never finished**: it is measured and improved continuously.

> **Note:** For generative bots, teams also check **how often the bot states something false** (the hallucination rate) by having people review samples of real answers.

***

## 11. Limitations and Safety

| Limitation | Explanation | Example |
| :-- | :-- | :-- |
| **Hallucination** | A generative bot can write fluent text that is false | A bot invents a discount that does not exist |
| **Losing Context** | Memory is limited; early details can be forgotten in long chats | The bot forgets the address given 40 messages ago |
| **Misunderstanding** | Unusual wording, typos, or mixed languages can confuse the intent finder | *"mera order kahan hai?"* is not recognized |
| **Out-of-Scope Requests** | A bot only handles what it was built for | A pizza bot asked about cricket |
| **Bias** | The bot can pick up unfair patterns from its training text | Replies that treat groups of people differently |
| **Privacy and Security** | Chats may hold personal details, and tricky messages may try to make a bot ignore its instructions | A user pastes an address or phone number into the chat |
| **No Real Feelings** | A bot can sound caring, but it does not feel anything | A friendly reply to an upset customer is still produced by software |

Good practice is to **tell users they are talking to a bot**, **offer a way to reach a human**, **confirm before important actions**, and **protect personal data**.

## 12. Summary

| Concept | One-Line Summary |
| :-- | :-- |
| **Chatbot** | A program that holds a conversation to help a person get something done |
| **Conversational AI** | The wider technology (NLP, machine learning, dialogue management, speech) behind natural conversation |
| **Why It Is Hard** | There are many ways to say one thing, details are missing, and context builds up across messages |
| **The Pipeline** | Message -> Understanding (NLU) -> Dialogue Manager (with Backend) -> Response Generation -> Reply |
| **Rule-Based Bot** | Follows fixed rules and menus; predictable but brittle |
| **Intent-Based Bot** | A trained model finds the intent and uses a ready answer |
| **Generative Bot** | An LLM writes a new reply word by word |
| **Hybrid Bot** | Mixes understanding models, fixed rules, and backend systems |
| **Intent** | What the user wants to do |
| **Entity** | A key detail inside the message, such as a size or an address |
| **Confidence and Fallback** | If the best intent score is too low, the bot does not guess; it asks or redirects |
| **State and Slot Filling** | The bot's memory of what it knows, and its habit of asking until every blank is filled |
| **Confirmation** | Reading the details back before an action that is hard to undo |
| **Response Generation (NLG)** | Turning the bot's decision into a reply, by template, retrieval, or generation |
| **LLM** | A large model that writes text by predicting the next word-piece, one at a time |
| **Context Window** | The limited amount of text a model can read at one time |
| **Hallucination** | A fluent but false statement written by a generative model |
| **RAG** | Look up real information first, then let the model write the answer from it |
| **Voice Assistant** | A chatbot with speech recognition in front and text-to-speech behind |
| **Key Limitation** | Bots can misunderstand, forget, or state falsehoods, so they need facts from trusted sources, confirmation, and a human fallback |
