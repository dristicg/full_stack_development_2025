# Forward & Backward Chaining Technique
## 1. The Rule-Based Technique (If–Then Rule) — Foundation

### 1.1 Simple Meaning

The **Rule-Based Technique** is one of the core techniques in AI Knowledge Representation. It **stores and uses human expertise**, represented as knowledge through **If–Then rules**, in order to **deduce new information** that wasn't explicitly stated before.

### 1.2 Everyday Analogy

Think of a **doctor's diagnostic checklist**. A doctor doesn't memorize every possible disease-symptom pair individually — they follow rules like *"IF fever AND cough AND breathlessness THEN suspect respiratory infection."* Given a patient's actual symptoms (the facts), the doctor **applies the rule** to arrive at a **new conclusion** (the diagnosis) that wasn't written down anywhere as a raw fact — it was *deduced*.

### 1.3 The 3 Components of a Rule-Based System

| # | Component | Role |
| :-- | :-- | :-- |
| **(i)** | **Knowledge Base** | Translates available facts/knowledge into **FOL (First Order Logic / Predicate Logic)** format so the system can understand how a given fact relates to others |
| **(ii)** | **Inference Engine** *(the "Core Inference Technique")* | The main/core part of the system — takes the available **facts** and applies the available **rules** (written in FOL) to arrive at a **conclusion**. Facts themselves come **from the human side** — they are the starting knowledge already provided to the system |
| **(iii)** | **Working Memory (Storage)** | Stores the **entire trail of states** produced from the initial state through to the current state, all the way until the goal state is (or isn't) reached |

```
RULE-BASED SYSTEM — HOW THE 3 PARTS FIT TOGETHER

   ┌────────────────┐      ┌──────────────────┐      ┌──────────────────┐
   │ KNOWLEDGE BASE │      │  INFERENCE ENGINE│      │  WORKING MEMORY  │
   │ (rules in FOL) │◄────►│ (applies rules to│◄────►│ (facts + all     │
   │                │      │  facts to deduce)│      │  derived facts)  │
   └────────────────┘      └──────────────────┘      └──────────────────┘

   Example rule in FOL:
     "If it is raining, then take an umbrella"
        Raining(x) → Take(Umbrella)
```

The **Inference Engine** doesn't have just one way of working — it can search **forward** (from facts toward a goal) or **backward** (from a goal toward the facts). These are exactly the two techniques covered next.

***

## 2. Forward Chaining

### 2.1 Simple Meaning

**Forward Chaining** is a **data-driven** reasoning technique. It **produces/takes a decision based on the available data** in order to **generate the goal state**. It **starts from the initial state** (the known facts) and keeps applying rules **forward**, step by step, until the goal state is reached — though it's entirely possible that the goal state is *never* reached if the available facts and rules simply don't lead there.

### 2.2 Everyday Analogy

Imagine you're assembling a piece of furniture using only the parts you have on your table (the facts). You keep checking the instruction manual (the rules): *"if you have these two parts, you can combine them into this sub-assembly."* You keep combining whatever you can, one step forward at a time, **without knowing in advance** exactly what the finished product will look like — you just keep building forward until either the final product **emerges naturally**, or you run out of combinable parts.

```
FORWARD CHAINING — CORE IDEA

   [Known Facts] ──apply matching rule──► [New Derived Fact]
        │                                         │
        └──────── added to Working Memory ────────┘
                            │
                 repeat with the NOW LARGER
                    set of known facts
                            │
                            ▼
                keep going until the GOAL
              appears among derived facts
             (or no more rules can fire)
```

***

## 3. Backward Chaining

### 3.1 Simple Meaning

**Backward Chaining** is a **goal-driven** reasoning technique. It **deduces/takes a decision by starting from the goal state** and moving **backward**, breaking the goal into smaller sub-goals, until it either successfully reaches facts that are already known in the **initial state** (proving the goal), or fails to (disproving/unable to prove the goal).

### 3.2 Everyday Analogy

Imagine you're trying to prove you're eligible for a scholarship (the goal). Instead of checking every fact about yourself one by one, you work backward: *"To be eligible, I need a GPA above 8 AND a recommendation letter."* Then you check each of those two requirements individually, breaking them down further if needed, **only chasing exactly what's relevant to proving eligibility** — never wasting time verifying unrelated facts about yourself that have nothing to do with the scholarship rule.

```
BACKWARD CHAINING — CORE IDEA

                    [GOAL]
                       │
         find a rule whose THEN-part = GOAL
                       │
         ┌─────────────┴─────────────┐
         ▼                           ▼
   [Sub-goal 1]                [Sub-goal 2]
   (must also be proved,     (must also be proved,
    recursively, the same     recursively, the same
    way, until it matches     way, until it matches
    a known fact)             a known fact)
```

***

## 4. Forward Chaining vs. Backward Chaining — Comparison

| Aspect | **Forward Chaining** | **Backward Chaining** |
| :-- | :-- | :-- |
| **Driven By** | **Data** (known facts) | **Goal** (hypothesis to prove) |
| **Direction** | Initial state → Goal state | Goal state → Initial state |
| **Also Known As** | Data-driven reasoning | Goal-driven reasoning |
| **Explores** | **All** rules whose conditions are currently satisfied — even ones irrelevant to a specific goal | **Only** rules that could lead to proving the specific goal — ignores irrelevant rules entirely |
| **Efficiency for a Single Query** | Can be wasteful — derives many facts that may never be needed | **Highly efficient** — never wastes time on rules that don't lead toward the goal |
| **Best Used When** | You want to derive **all possible conclusions** from a set of facts (e.g. monitoring/alerting systems) | You want to answer **one specific question** (e.g. "Is X true?") |
| **Real-World Examples** | Expert systems for monitoring (e.g. fault-detection, sensor-driven diagnosis systems like CLIPS-based systems) | Query-answering / logic-programming systems (e.g. Prolog), medical diagnosis "is it disease X?" systems |

## 5. Worked Examples

Two fully worked examples are provided for **each** technique — all four use the same step-by-step style: **stating the goal/facts → tracing each iteration → drawing the derivation diagram → stating the conclusion.**

***

### 5.1 FORWARD CHAINING — Example 1: "Is Colonel a Criminal?"

#### Step 1: The Knowledge Base (Facts + Rules in FOL)

**Facts (Working Memory):**
```
F1: American(Colonel)
F2: Enemy(Nono, America)
F3: Owns(Nono, M1)
F4: Missile(M1)
```

**Rules:**
```
R1: Missile(y) → Weapon(y)
R2: Missile(y) ∧ Owns(Nono, y) → Sells(Colonel, y, Nono)
R3: American(p) ∧ Weapon(q) ∧ Sells(p, q, r) ∧ Enemy(r, America) → Crime(p)
```

**Target Goal:** `Crime(Colonel)` — is Colonel a criminal?

#### Step 2: The Forward Chaining Trace

**Iteration 1 — Scan all rules for ones whose conditions are already fully satisfied by the known facts.**
`R1: Missile(y) → Weapon(y)` — with `y = M1`, the condition `Missile(M1)` matches **Fact 4**.  Rule fires.
→ **New derived fact:** `Weapon(M1)` — added to Working Memory.

**Iteration 2 — Re-scan, now including the newly derived fact.**
`R2: Missile(y) ∧ Owns(Nono, y) → Sells(Colonel, y, Nono)` — with `y = M1`, both `Missile(M1)` (Fact 4) and `Owns(Nono, M1)` (Fact 3) are known.  Rule fires.
→ **New derived fact:** `Sells(Colonel, M1, Nono)` — added to Working Memory.

**Iteration 3 — Re-scan again.**
`R3: American(p) ∧ Weapon(q) ∧ Sells(p,q,r) ∧ Enemy(r,America) → Crime(p)` — with `p=Colonel, q=M1, r=Nono`: `American(Colonel)` (Fact 1) , `Weapon(M1)` (derived in Iteration 1) , `Sells(Colonel,M1,Nono)` (derived in Iteration 2) , `Enemy(Nono,America)` (Fact 2)  — **all four conditions satisfied**. Rule fires.
→ **New derived fact:** `Crime(Colonel)` — this **is the goal!**

**Iteration 4 — Check Working Memory for the goal.**
`Crime(Colonel)` is now present. **Stop — goal reached.**

#### Step 3: Derivation Diagram

```
 [American(Colonel)]  [Missile(M1)]   [Owns(Nono,M1)]   [Enemy(Nono,America)]
        │                   │  \             │                    │
        │                   │   \            │                    │
        │                   ▼    ╲           ▼                    │
        │           R1:Weapon(M1)  ╲   R2:Sells(Colonel,M1,Nono)  │
        │                   │       ╲        │                    │
        │                   │        ╲       │                    │
        └───────────────────┴─────R3──┴──────┴────────────────────┘
                                     │
                                     ▼
                             Crime(Colonel)
                                     │
                                     ▼
                              GOAL REACHED ✓ (True)
```

#### Conclusion

By purely **moving forward from the facts**, applying whichever rule's conditions happened to be satisfied, the engine derived `Crime(Colonel) = True` after 3 rule-firings — without ever being "told" in advance that this was the target. This is the hallmark of Forward Chaining: it explores **everything derivable**, and the goal simply happens to show up along the way.

### 5.2 FORWARD CHAINING — Example 2: Rice Crop Fertilizer Recommendation

#### Step 1: The Knowledge Base (Facts + Rules in FOL)

**Facts (Working Memory):**
```
F1: Short(Rice_Crop) ∧ Yellow_Leaves(Rice_Crop)
F2: Monsoon_Season()
```

**Rules:**
```
R1: Short(x) ∧ Yellow_Leaves(x) → Lacks_Nitrogen(x)
R2: Lacks_Nitrogen(x) → Use_Rich_Nitrogen_Fertilizer(x)
R3: Monsoon_Season() ∧ Lacks_Nitrogen(x) → Use_Urea(x)
```

**Target Goal:** `Use_Urea(Rice_Crop)` — should the farmer use urea fertilizer?

#### Step 2: The Forward Chaining Trace

**Iteration 1 — Scan for a rule whose conditions are already satisfied.**
`R1: Short(x) ∧ Yellow_Leaves(x) → Lacks_Nitrogen(x)` — with `x = Rice_Crop`, both conditions match **Fact 1**.  Rule fires.
→ **New derived fact:** `Lacks_Nitrogen(Rice_Crop)`.

**Iteration 2 — Re-scan with the new fact included.**
Two rules now qualify simultaneously:
- `R2: Lacks_Nitrogen(x) → Use_Rich_Nitrogen_Fertilizer(x)` — condition met.  Fires.
  → **New derived fact:** `Use_Rich_Nitrogen_Fertilizer(Rice_Crop)` *(this happens, but it is not our target goal — a side-effect of forward chaining exploring everything it can)*.
- `R3: Monsoon_Season() ∧ Lacks_Nitrogen(x) → Use_Urea(x)` — both `Monsoon_Season()` (Fact 2) and `Lacks_Nitrogen(Rice_Crop)` (just derived) are known.  Fires.
  → **New derived fact:** `Use_Urea(Rice_Crop)` — **this is the goal!**

**Iteration 3 — Check Working Memory for the goal.**
`Use_Urea(Rice_Crop)` is present. **Stop — goal reached.**

#### Step 3: Derivation Diagram

```
[Short(Rice_Crop)]   [Yellow_Leaves(Rice_Crop)]   [Monsoon_Season()]
         \                    /                         │
          ▼                  ▼                          │
           R1: Lacks_Nitrogen(Rice_Crop)                │
             /                          \               │
            ▼                            \              │
  R2: Use_Rich_Nitrogen_                  \             │
    Fertilizer(Rice_Crop)                  │            /
   (derived, but NOT the                   ▼           ▼
    target goal — a "wasted"        R3: Use_Urea(Rice_Crop)
    branch forward chaining                   │
    still explores)                           ▼
                                   GOAL REACHED ✓ (True)
```

#### Conclusion

Notice something important here, in direct contrast to backward chaining: forward chaining **also fired R2**, deriving `Use_Rich_Nitrogen_Fertilizer(Rice_Crop)` — a fact that is completely **irrelevant to our actual goal** `Use_Urea(Rice_Crop)`. Forward chaining doesn't know or care what the "goal" is while it's running; it simply fires **every rule whose conditions become true**, which means it can waste effort deriving facts nobody asked for. This is precisely the inefficiency that Backward Chaining (Section 5.3 and 5.4) is designed to avoid.

### 5.3 BACKWARD CHAINING — Example 1: Rice Crop Fertilizer (Same Knowledge Base as 5.2)

#### Step 1: The Target Goal

The system is asked to prove the hypothesis:
**Goal: `Use_Urea(Rice_Crop)`**

```
                    [Goal: Use_Urea(Rice_Crop)]
```

#### Step 2: The Backward Chaining Trace

**Iteration 1 — Find a rule that concludes the Goal.**
The inference engine searches the Knowledge Base for a rule where `Use_Urea(x)` is on the THEN side.
It finds **R3:** `Monsoon_Season() ∧ Lacks_Nitrogen(x) → Use_Urea(x)`.
To prove `Use_Urea(Rice_Crop)`, the engine sets the substitution `{x / Rice_Crop}` and sets up **two new sub-goals**:
- Prove **Sub-goal A:** `Monsoon_Season()`
- Prove **Sub-goal B:** `Lacks_Nitrogen(Rice_Crop)`

```
                   [Goal: Use_Urea(Rice_Crop)]
                              │
             ┌────────────────┴────────────────┐
             ▼                                  ▼
   [Sub-goal A: Monsoon_Season]     [Sub-goal B: Lacks_Nitrogen(Rice_Crop)]
```

**Iteration 2 — Resolving Sub-goal A.**
The engine checks if `Monsoon_Season()` is an **initial fact** in Working Memory.
**Result: Yes (Fact 2).** Sub-goal A is successfully proven! 

**Iteration 3 — Resolving Sub-goal B.**
The engine now needs to prove `Lacks_Nitrogen(Rice_Crop)`. It searches for a rule that concludes this.
It finds **R1:** `Short(x) ∧ Yellow_Leaves(x) → Lacks_Nitrogen(x)`.
To prove `Lacks_Nitrogen(Rice_Crop)`, it sets up **two more sub-goals**:
- Prove **Sub-goal C:** `Short(Rice_Crop)`
- Prove **Sub-goal D:** `Yellow_Leaves(Rice_Crop)`

```
                              [Sub-goal B: Lacks_Nitrogen(Rice_Crop)]
                                              │
                             ┌─────────────────┴─────────────────┐
                             ▼                                   ▼
                  [Sub-goal C: Short(Rice_Crop)]     [Sub-goal D: Yellow_Leaves(Rice_Crop)]
```

**Iteration 4 — Reaching the Initial State.**
The engine checks Working Memory for `Short(Rice_Crop)` and `Yellow_Leaves(Rice_Crop)`.
**Result: Yes** (Fact 1 states `Short(Rice_Crop) ∧ Yellow_Leaves(Rice_Crop)`).
Both **Sub-goal C** and **Sub-goal D** match our Initial State perfectly. 

#### Step 3: Full Proof Tree

```
                               [Goal: Use_Urea(Rice_Crop)]
                                           │  via R3
                        ┌──────────────────┴──────────────────┐
                        ▼                                     ▼
             [Sub-goal A: Monsoon_Season]          [Sub-goal B: Lacks_Nitrogen(Rice_Crop)]
                        │                                        │ via R1
                       (True)                     ┌──────────────┴──────────────┐
                        │                         ▼                             ▼
                 matches Fact 2         [Sub-goal C: Short(Rice_Crop)] [Sub-goal D: Yellow_Leaves(Rice_Crop)]
                    ── INITIAL STATE                    │                             │
                                                        (True)                       (True)
                                                        │                            │
                                                  matches Fact 1                  matches Fact 1
                                                 ── INITIAL STATE            ── INITIAL STATE
```

####  Conclusion

Because the initial facts match **all the leaves** of our goal tree, the engine unwinds the stack:
- `Short` + `Yellow_Leaves` proves `Lacks_Nitrogen`.
- `Lacks_Nitrogen` + `Monsoon_Season` proves `Use_Urea`.

The system successfully terminates and returns **True**.

Notice how **Rule 2** (`Use_Rich_Nitrogen_Fertilizer`) was **completely ignored** — unlike in Example 5.2 (Forward Chaining), where it fired and derived an irrelevant fact. Backward chaining is highly efficient precisely because it **never wastes time on rules that do not directly lead to the goal.**

### 5.4 BACKWARD CHAINING — Example 2: "Is Colonel a Criminal?" (Same Knowledge Base as 5.1)

#### Step 1: The Target Goal

**Goal: `Crime(Colonel)`** 

```
                        [Goal: Crime(Colonel)]
```

#### Step 2: The Backward Chaining Trace

**Iteration 1 — Find a rule that concludes the Goal.**
The engine searches for a rule where `Crime(p)` is on the THEN side. It finds **R3:**
`American(p) ∧ Weapon(q) ∧ Sells(p,q,r) ∧ Enemy(r,America) → Crime(p)`.
With `p = Colonel`, it sets up **four sub-goals**:
- Prove **Sub-goal A:** `American(Colonel)`
- Prove **Sub-goal B:** `Weapon(q)` *(q still unbound)*
- Prove **Sub-goal C:** `Sells(Colonel, q, r)` *(q, r still unbound)*
- Prove **Sub-goal D:** `Enemy(r, America)` *(r still unbound)*

```
                                [Goal: Crime(Colonel)]
                                          │ via R3
              ┌───────────────┬───────────────────┬───────────────┐
              ▼               ▼                   ▼               ▼
   [Sub-goal A:        [Sub-goal B:         [Sub-goal C:       [Sub-goal D:
    American(Colonel)]   Weapon(q)]           Sells(Colonel,     Enemy(r,America)]
                                                q, r)]
```

**Iteration 2 — Resolving Sub-goal A.**
The engine checks Working Memory for `American(Colonel)`.
**Result: Yes (Fact 1).** Sub-goal A is proven immediately! 

**Iteration 3 — Resolving Sub-goal B.**
`Weapon(q)` is **not** a raw fact — the engine searches for a rule concluding `Weapon(...)`.
It finds **R1:** `Missile(y) → Weapon(y)`. This creates a nested sub-goal:
- Prove **Sub-goal B1:** `Missile(y)`
The engine checks Working Memory: `Missile(M1)` **is Fact 4**, so it binds `y = M1`.
**Result: Yes.** `Weapon(M1)` is proven, which also means `q = M1` in the parent goal. 

**Iteration 4 — Resolving Sub-goal C.**
`Sells(Colonel, M1, r)` is **not** a raw fact (using `q = M1` from the previous step). The engine searches for a rule concluding `Sells(...)`.
It finds **R2:** `Missile(y) ∧ Owns(Nono, y) → Sells(Colonel, y, Nono)`. This creates two nested sub-goals:
- Prove **Sub-goal C1:** `Missile(M1)` → already proven True in Iteration 3! (reused, no extra work)
- Prove **Sub-goal C2:** `Owns(Nono, M1)` → checked against Working Memory → **Fact 3.** 
**Result:** `Sells(Colonel, M1, Nono)` is proven, binding `r = Nono`. 

**Iteration 5 — Resolving Sub-goal D.**
With `r = Nono` now bound, the engine checks Working Memory for `Enemy(Nono, America)`.
**Result: Yes (Fact 2).** Sub-goal D is proven directly! 

#### Step 3: Full Proof Tree

```
                                       [Goal: Crime(Colonel)]
                                                │  via R3
              ┌─────────────────┬───────────────┴────────────────┬─────────────────┐
              ▼                 ▼                                ▼                 ▼
   [Sub-goal A:        [Sub-goal B: Weapon(q)]        [Sub-goal C: Sells         [Sub-goal D:
    American(Colonel)]           │ via R1               (Colonel,q,r)]           Enemy(r,America)]
         │                       ▼                             │ via R2                  │
       (True)          [Sub-goal B1: Missile(y)]  ┌──────────────┴─────────┐     (True, with r=Nono)
         │                       │                ▼                        ▼                    │
   matches Fact 1             (True,          [Sub-goal C1:            [Sub-goal C2:        matches Fact 2
   ── INITIAL STATE          y=M1)             Missile(M1)]              Owns(Nono,M1)]      ── INITIAL STATE
                                │                    │                         │
                          matches Fact 4       (reused from B1,          matches Fact 3
                          ── INITIAL STATE      already True)            ── INITIAL STATE
```

#### Conclusion

Every sub-goal bottoms out at a fact already sitting in the **Initial State** (Facts 1–4), so the engine unwinds the recursion and confirms `Crime(Colonel) = True`.

The key efficiency lesson repeats here too: the engine **never once considered** any rule or fact that had nothing to do with proving `Crime(Colonel)` — it built exactly the sub-goal tree it needed, and no more. Compare this to Forward Chaining (Example 5.1), which would have derived `Weapon(M1)` and `Sells(Colonel,M1,Nono)` regardless of whether anyone ever asked about `Crime(Colonel)` at all.

## 6. Advantages & Disadvantages

| | **Forward Chaining** | **Backward Chaining** |
| :-- | :-- | :-- |
| **Advantages** | • Derives **all** conclusions reachable from the facts — useful when you don't know in advance what you're looking for<br>• Naturally suited to **monitoring/alerting** systems that react as new data streams in<br>• Simple to implement — no need to manage a stack of sub-goals | • **Highly efficient** for answering one specific query — ignores irrelevant rules entirely<br>• Naturally suited to **diagnosis/query-answering** systems<br>• Only explores what's relevant to the goal, minimizing wasted computation |
| **Disadvantages** | • Can be **wasteful** — derives many facts that are never actually needed<br>• Doesn't naturally focus on a specific question; better suited to "derive everything" than "answer this one thing" | • Can involve **repeated/redundant sub-goal proving** if not optimized (though reusable results, as shown in Example 5.4, can mitigate this)<br>• Less suited when you want to explore **all** possible conclusions rather than proving one specific hypothesis |

***

## 7. Summary — Points to Remember

| # | Concept | Key Fact |
| :-- | :-- | :-- |
| (i) | **Rule-Based Technique** | Stores human expertise as **If-Then rules**, with 3 components: Knowledge Base, Inference Engine, Working Memory |
| (ii) | **Forward Chaining** | **Data-driven** — starts from facts, fires whatever rules qualify, moves toward the goal (may explore irrelevant rules along the way) |
| (iii) | **Backward Chaining** | **Goal-driven** — starts from the goal, breaks it into sub-goals, only explores rules directly relevant to proving it |
| (iv) | **Key Trade-off** | Forward Chaining = broad but potentially wasteful; Backward Chaining = narrow and efficient, but only for single, specific queries |
| (v) | **Shared Foundation** | Both techniques operate over the **same** Knowledge Base (facts + rules in FOL) — they differ only in the **direction and strategy** of traversal |
