# Rule-Based Expert System
## 1. What is a "Rule-Based Expert System"?

### 1.1 Simple Meaning

A **Rule-Based Expert System** is a computer program designed to **mimic the decision-making ability of a human expert** in a specific, narrow domain (like medical diagnosis, loan approval, or car troubleshooting). It does this by storing the expert's knowledge as **If–Then rules**, and then using a dedicated reasoning component to **apply those rules to a specific situation's facts** in order to reach a conclusion — exactly the way a real expert would.

### 1.2 Everyday Analogy

Think of calling a **car mechanic helpline**. You describe your symptoms ("the engine won't start, but the headlights turn on fine"). The person on the phone isn't inventing a diagnosis from nothing — they're mentally running through a set of **learned rules** ("if lights work but engine doesn't crank, it's usually the starter motor"), matching those rules against **what you just told them** (the current facts of your situation), and arriving at a recommendation. A Rule-Based Expert System formalizes this exact process into software.

### 1.3 The 3 Main Components

Every Rule-Based Expert System is built from three core components that work together in a continuous loop:

| # | Component | One-Line Role |
| :-- | :-- | :-- |
| **1** | **Knowledge Base** | The **permanent storehouse** of domain knowledge — facts and If-Then rules |
| **2** | **Working Memory (Temporary Memory)** | The **short-term, per-session storage** of facts about the *current* case/problem being solved |
| **3** | **Inference Engine** | The **reasoning "brain"** that matches Working Memory against the Knowledge Base to derive new conclusions |

```
RULE-BASED EXPERT SYSTEM — HOW THE 3 COMPONENTS CONNECT

                        ┌──────────────────────┐
                        │        USER          │
                        └──────────┬───────────┘

                                   │  current problem / asks a query

     ┌───────────────────────────────────────────────────────┐
     │                    INFERENCE ENGINE                   │
     │   (reads rules from the Knowledge Base, reads/writes  │

     └────────────────────┬───────────────────┬──────────────┘
                          │                   │

                          ▼                   ▼
          ┌───────────────────────┐  ┌───────────────────────┐
          │    KNOWLEDGE BASE     │  │    WORKING MEMORY     │
```

## 2. Component 1 — The Knowledge Base

### 2.1 Definition

The **Knowledge Base** is the **permanent, long-term storehouse** of everything the expert system "knows" about its domain. It is built **once**, by a "knowledge engineer" working with a human expert, and it does **not change** while the system is running on a particular problem — it stays the same across every single user session.

It contains **two kinds of content**:

| Content Type | Meaning | Example |
| :-- | :-- | :-- |
| **Domain Facts** | General, background truths about the domain that are always valid | *"A car battery outputs 12V nominally."* |
| **If-Then Rules (Heuristics)** | Expert "rules of thumb" connecting conditions to conclusions | *"IF the headlights turn on but the engine does not crank, THEN suspect a starter motor problem."* |

### 2.2 Key Characteristics

- **Permanent** — it survives between sessions; a new user starting a new session sees the exact same Knowledge Base as the last user.
- **Domain-Specific** — a medical-diagnosis Knowledge Base is completely different from a car-troubleshooting one; the system cannot reason outside the domain it was built for.
- **Written in a formal structure** — typically as `IF <condition(s)> THEN <conclusion/action>` rules, so the Inference Engine can process them mechanically.

### 2.3 Small Example

```
KNOWLEDGE BASE (excerpt) — Car Troubleshooting Domain

  R1: IF Lights_Turn_On = Yes AND Engine_Cranks = No
      THEN Starter_Motor_Problem = Likely

  R2: IF Lights_Turn_On = No
      THEN Battery_Dead = Likely

  R3: IF Engine_Cranks = Yes AND Engine_Starts = No
      THEN Fuel_System_Problem = Likely
```

Notice: the Knowledge Base only **stores** these rules — it does not, by itself, know anything about *your specific car*. That information belongs to Working Memory, covered next.

***

## 3. Component 2 — Working Memory (Temporary Memory)

### 3.1 Definition

**Working Memory** (also called **Temporary Memory**) is the **short-term storage area** that holds the **facts relevant to the current, specific problem** being solved right now. Unlike the Knowledge Base, its contents are created **fresh at the start of every session** and **discarded once the session ends** — it holds no memory of any *previous* user's case.

### 3.2 Key Characteristics

- **Temporary / Session-Specific** — exists only for the duration of one consultation; wiped clean afterward.
- **Starts small, grows during reasoning** — begins with just the facts the user provides, and the Inference Engine **adds newly derived facts** to it as rules fire (this is exactly what was shown happening in `04. forward_and_backward_chaining_technique.md`, where "new derived facts" were added to Working Memory with each iteration).
- **This is where the "state" of the current problem lives** — if you ask two different users the same question at the same time, each gets their **own independent** Working Memory.

### 3.3 Small Example

At the **start** of a session, before any reasoning happens, Working Memory for one particular user's car might contain only:

```
WORKING MEMORY (at the start of the session)

  Lights_Turn_On   = Yes     (user-reported fact)
  Engine_Cranks    = No      (user-reported fact)
```

By the **end** of the session, after the Inference Engine has fired rule R1 from Section 2.3, Working Memory will have **grown**:

```
WORKING MEMORY (after inference)

  Lights_Turn_On          = Yes     (user-reported fact)
  Engine_Cranks           = No      (user-reported fact)
  Starter_Motor_Problem   = Likely  (NEWLY DERIVED — added by the Inference Engine)
```

This growth — starting from raw user facts and accumulating derived facts — is the whole point of Working Memory: it's the **live workspace** where the Knowledge Base's general rules get turned into a **specific** conclusion for **this** case.

***

## 4. Component 3 — The Inference Engine

### 4.1 Definition

The **Inference Engine** is the **reasoning component** — the "brain" of the expert system. Its job is to **repeatedly compare** the facts currently sitting in Working Memory against the conditions of the rules sitting in the Knowledge Base, **fire** any rule whose conditions are satisfied, and **write the newly derived conclusion back into Working Memory** — continuing this process until no more rules can fire, or a specific goal is reached.

### 4.2 The Inference Cycle (How It Actually Works, Step by Step)

The Inference Engine doesn't just fire rules randomly — it follows a repeating **3-phase cycle**, often called the **Match–Resolve–Act cycle**:

```
THE INFERENCE CYCLE

        ┌────────────────────────────────────────────────┐
        │                                                │
        ▼                                                │
  ┌───────────┐        ┌────────────────┐        ┌───────────┐
  │   MATCH   │──────► │     RESOLVE    │──────► │    ACT    │
  └───────────┘        └────────────────┘        └───────────┘
  Compare every         If MORE THAN ONE          Fire the chosen
  rule's conditions      rule matches, pick        rule: write its
  against the CURRENT    just one using a          conclusion into
  Working Memory —       "conflict resolution"     Working Memory
  collect the set of     strategy (e.g. rule          │
  ALL matching rules     priority, specificity,       │
  (the "conflict set")   or most-recently-used        │
                          fact)                       │
        ▲                                             │
        └─────────────────────────────────────────────┘
              loop back to MATCH with the now-
              UPDATED Working Memory, and repeat
              until no rule matches (or the goal
              is found)
```

| Phase | What Happens |
| :-- | :-- |
| **Match** | Scan the Knowledge Base and find **every** rule whose `IF` conditions are currently true in Working Memory. This set of candidate rules is called the **"conflict set."** |
| **Resolve** | If the conflict set has **more than one** rule in it, a **conflict resolution strategy** decides which single rule fires first — common strategies include firing the **highest-priority** rule, the **most specific** rule (most conditions), or the rule matching the **most recently added** fact. |
| **Act** | **Fire** the chosen rule — its `THEN` conclusion is written as a **new fact into Working Memory.** The cycle then restarts from Match, since Working Memory has changed. |

### 4.3 Direction of Reasoning

As covered in the previous document, the Inference Engine can run this cycle in **two directions**:

| Direction | Behavior |
| :-- | :-- |
| **Forward Chaining** | Starts the Match phase from the **known facts**, working toward whatever conclusion emerges |
| **Backward Chaining** | Starts from a **specific goal**, and only matches rules that help prove that exact goal |

(See `04. forward_and_backward_chaining_technique.md` for fully worked, step-by-step examples of both.)

## 5. The 3 Components Compared

| Aspect | **Knowledge Base** | **Working Memory** | **Inference Engine** |
| :-- | :-- | :-- | :-- |
| **Lifespan** | Permanent — persists across all sessions | Temporary — created fresh, discarded after each session | Persistent as a *program*, but its working state resets each cycle |
| **Contains** | Domain facts + If-Then rules | Facts specific to the current problem (user input + derived facts) | No data of its own — it's the *process* that connects the other two |
| **Changes During a Session?** |  No — stays fixed |  Yes — grows as new facts are derived | Runs the Match–Resolve–Act cycle repeatedly |
| **Analogy** | A doctor's medical textbook | A doctor's notes on *this one* patient, for *this one* visit | The doctor's own reasoning process |

## 6. Fully Worked Example — "Car Won't Start" Expert System

### 6.1 The Knowledge Base (built once, permanent)

```
R1: IF Lights_Turn_On = Yes AND Engine_Cranks = No
    THEN Starter_Motor_Problem = Likely

R2: IF Lights_Turn_On = No
    THEN Battery_Dead = Likely

R3: IF Engine_Cranks = Yes AND Engine_Starts = No
    THEN Fuel_System_Problem = Likely

R4: IF Starter_Motor_Problem = Likely AND Battery_Voltage = Normal
    THEN Recommend = "Check Starter Motor / Solenoid"
```

### 6.2 Working Memory — Start of Session (user-provided facts via the User Interface)

```
Lights_Turn_On   = Yes
Engine_Cranks    = No
Battery_Voltage  = Normal
```

### 6.3 The Inference Engine's Cycle, Traced Step by Step

**Cycle 1 — Match:**
Scan all 4 rules against the current Working Memory.
- `R1` conditions (`Lights_Turn_On=Yes`, `Engine_Cranks=No`) → **both match.**  In conflict set.
- `R2` condition (`Lights_Turn_On=No`) → does **not** match (we have `Yes`). 
- `R3` condition (`Engine_Cranks=Yes`) → does **not** match (we have `No`). 
- `R4` condition (`Starter_Motor_Problem=Likely`) → not yet known in Working Memory. 

Conflict set = `{ R1 }` — only one rule, so **Resolve** is trivial.

**Cycle 1 — Act:**
Fire `R1`. **New fact added to Working Memory:** `Starter_Motor_Problem = Likely`.

```
WORKING MEMORY (after Cycle 1)
  Lights_Turn_On          = Yes
  Engine_Cranks           = No
  Battery_Voltage         = Normal
  Starter_Motor_Problem   = Likely   ← just derived
```

**Cycle 2 — Match:**
Re-scan all rules with the updated Working Memory.
- `R4` conditions (`Starter_Motor_Problem=Likely`, `Battery_Voltage=Normal`) → **both now match!**  In conflict set.
- (R1, R2, R3 either already fired or still don't match.)

Conflict set = `{ R4 }` — fire it.

**Cycle 2 — Act:**
Fire `R4`. **New fact added to Working Memory:** `Recommend = "Check Starter Motor / Solenoid"`.

```
WORKING MEMORY (after Cycle 2 — FINAL)
  Lights_Turn_On          = Yes
  Engine_Cranks           = No
  Battery_Voltage         = Normal
  Starter_Motor_Problem   = Likely
  Recommend               = "Check Starter Motor / Solenoid"   ← final conclusion
```

**Cycle 3 — Match:**
No rule's conditions are newly satisfied. Conflict set = `{ }` (empty). **The cycle halts.**

### 6.4 Diagram — The Full Reasoning Trace

```
   [Lights_Turn_On = Yes]   [Engine_Cranks = No]
              │                      │
              └───────────┬──────────┘
                          ▼
                     R1 fires
                          │
                          ▼
          [Starter_Motor_Problem = Likely] ─────┐
                                                │
                          [Battery_Voltage = Normal]
                                                │
                          ┌─────────────────────┘
                          ▼
                     R4 fires
                          │
                          ▼
        [Recommend = "Check Starter Motor / Solenoid"]
                          │
                          ▼
                OUTPUT TO USER ✓
```

### 6.5 Conclusion

Watch how each component played its exact role:
- The **Knowledge Base** never changed — the same 4 rules (R1–R4) sat there the whole time.
- **Working Memory** started with 3 facts and grew to 5, capturing everything specific to *this one car*.
- The **Inference Engine** ran the Match–Resolve–Act cycle **twice**, each time re-scanning the (now-updated) Working Memory against the (unchanging) Knowledge Base, until nothing new could be derived — at which point it stopped and returned the final recommendation.

## 7. Advantages & Disadvantages

| **Advantages** | **Disadvantages** |
| :-- | :-- |
| Separates **knowledge** (Knowledge Base) from **reasoning** (Inference Engine) — the same engine can work with a completely different Knowledge Base to become an "expert" in a new domain | **Knowledge acquisition bottleneck** — building a good Knowledge Base requires extensive time with a real human expert |
| Can **explain its reasoning** — since every conclusion traces back to specific rules that fired, the system can show *why* it reached a decision | **Brittle at the boundaries** — performs poorly on cases slightly outside what its rules anticipated |
| **Consistent** — never gets tired, distracted, or forgets a rule, unlike a human expert | **Doesn't learn** on its own — the Knowledge Base must be manually updated by a knowledge engineer as new expertise emerges |

## 8. Real-World Examples of Rule-Based Expert Systems

| System | Domain | Notable For |
| :-- | :-- | :-- |
| **MYCIN** | Medical diagnosis (bacterial infections) | One of the earliest and most influential expert systems (1970s), used backward chaining |
| **DENDRAL** | Chemistry (molecular structure identification) | One of the first expert systems ever built, pioneered the Knowledge Base + Inference Engine split |
| **CLIPS** | General-purpose expert system shell | A widely used forward-chaining rule engine, still taught and used today |
| **XCON (R1)** | Computer configuration (for DEC) | One of the first expert systems used commercially at large scale |
