# Semantic Network & Frame / Slots

# PART 1 — SEMANTIC NETWORK

## 1. What is a "Semantic Network"?

### 1.1 Simple Meaning

A **Semantic Network** is a way to represent **knowledge (human language / statements)** through **graphical notation**, which uses a **network of interconnected nodes** (real-world objects, entities, attributes) with an **arc** (edges which connect different nodes together to represent the relation between them).

It's essentially **a way to mimic how the human brain works** — building a **detailed mind-map** of a given complex piece of knowledge.

### 1.2 Everyday Analogy

Think of a **family tree** or a **mind-map** you'd sketch on paper — bubbles (people, places, things) connected by labeled lines (relations like "is married to," "is the parent of"). A Semantic Network is exactly this idea, formalized for AI: **objects become nodes, relationships become labeled arcs**, and the whole picture becomes something a machine can traverse and reason over.

```
SEMANTIC NETWORK — CORE IDEA

     [Node A] ────arc (relation)────► [Node B]
   (real-world object)             (real-world object)

   Together, many such node-arc-node triples build up a full
   graphical "mind-map" of complex, interconnected knowledge.
```

***

## 2. Building Blocks: Node & Arc

| Building Block | Meaning |
| :-- | :-- |
| **Node** | A **real-world object** (an entity, category, or attribute) |
| **Arc** | The **edge** connecting two nodes, representing the **relationship** between them |

### 2.1 Basic Worked Example

> **"Tree is a living thing."**
> **"Animal is a living thing."**

```
GRAPHICAL NOTATION

     (node)                        (node)
   ┌────────┐    is-a (arc)    ┌──────────────┐
   │  Tree  │─────────────────►│ Living Thing │
   └────────┘                  └──────────────┘

     (node)                       (node)
   ┌────────┐    is-a (arc)    ┌──────────────┐
   │ Animal │─────────────────►│ Living Thing │
   └────────┘                  └──────────────┘
```

This ties directly back to **Predicate Logic**: each "is-a" arc is really an implication in disguise —
```
∀x ( Tree(x)   → Living(x) )
∀x ( Animal(x) → Living(x) )
```

***

## 3. Classification of Nodes

| Node Type | Meaning | Example |
| :-- | :-- | :-- |
| **(i) Generic Node** | Represents a **category / class** of objects | `Animal`, `Tree`, `Living Thing` |
| **(ii) Individual Node (Instance)** | Represents **one specific member** of a category | `Cat`, `Dog` (instances of Animal), `Oak` (instance of Tree) |

### 3.1 Worked Hierarchy Example

```
                    ┌──────────────┐
              ┌────►│ Living Thing │◄────┐
        is-a  │     └──────────────┘     │  is-a
              │                          │
        ┌──────────┐                 ┌──────────┐
        │  Animal  │  (Generic)      │   Tree   │  (Generic)
        └──────────┘                 └──────────┘
          ▲      ▲                         ▲
    is-a  │      │  is-a              is-a │
        ┌─────┐ ┌─────┐                ┌───────┐
        │ Cat │ │ Dog │  (Individual)  │  Oak  │  (Individual)
        └─────┘ └─────┘                └───────┘

Predicate Logic translation of each is-a link:
  ∀x ( Tree(x)   → Living(x) )        "If x is a tree, x is a living thing"
  ∀x ( Animal(x) → Living(x) )        "If x is an animal, x is a living thing"
  ∀y ( Cat(y)    → Animal(y) )        "If y is a cat, y is an animal"
```

## 4. Full Worked Example — "Tom the Cat" Semantic Network

**Statements to represent:**
1. Tom is a cat
2. Tom caught a bird
3. Tom is owned by John
4. Tom is ginger in colour
5. Cats like cream
6. The cat sat on the mat
7. A cat is a mammal
8. A bird is a mammal
9. All mammals are animals
10. Mammals have fur

```
                                    ┌─────────┐
                                    │ animals │
                                    └────▲────┘
                                         │ are
                                    ┌────┴───────┐    have    ┌─────┐
                                    │  mammal    │───────────►│ fur │
                                    └─▲───────▲──┘            └─────┘
                                is_a  │       │ is_a
                        ┌─────────────┘       └───────────────┐
                   ┌────┴────┐                           ┌─────┴────┐
                   │   cat   │                           │  bird    │
                   └─┬──▲──┬─┘                           └─────▲────┘
              like   │  │  │ sat_on                            │
        ┌────────┐◄──┘  │  └──────►┌─────┐                     │
        │ cream  │      │          │ mat │                caught_a
        └────────┘    is_a         └─────┘                     │
                        │                                      │
                    ┌────┴────┐                                │
   in_colour  ┌─────┤   Tom   ├────────────────────────────────┘
┌──────────┐  │     └────┬────┘
│  ginger  │◄─┘          │ is_owned_by
└──────────┘             ▼
                     ┌────────┐
                     │  John  │
                     └────────┘
```

*(Reading the diagram: follow any arrow from source node → label → target node, e.g. `cat —is_a→ mammal` = "A cat is a mammal", `Tom —caught_a→ bird` = "Tom caught a bird".)*

### 4.1 Node & Arc Table

| Node | Type | Outgoing Arc (Label) | Points To |
| :-- | :-- | :-- | :-- |
| `mammal` | Generic | `are`, `have` | `animals`, `fur` |
| `cat` | Generic | `is_a`, `like`, `sat_on` | `mammal`, `cream`, `mat` |
| `bird` | Generic | `is_a` | `mammal` |
| `Tom` | Individual (Instance) | `is_a`, `in_colour`, `caught_a`, `is_owned_by` | `cat`, `ginger`, `bird`, `John` |
| `animals` | Generic | — (only a target) | — |
| `fur`, `cream`, `mat`, `ginger`, `John` | Attributes / Individuals | — (only targets) | — |

Notice the **arc itself carries the label** (`is_a`, `have`, `like`, `sat_on`, `caught_a`, `in_colour`, `is_owned_by`) — this is what's meant by a **"label arc"**: the relationship name is written directly on the edge so the graph reads like a sentence when traversed (`Tom → is_owned_by → John` = "Tom is owned by John").

***

## 5. Pros & Cons of Semantic Networks

| **Pros** | **Cons** |
| :-- | :-- |
| **(i) Easy to understand** — graphical notation is intuitive | **(i)** Must **travel/traverse the entire graph** to reach a conclusion — no shortcuts, which gets expensive as the graph grows large |
| **(ii) Conveys meaning** — transparent and accurate representation | |
| **(iii) Handles complex statements** well, even deeply interconnected ones | |

# PART 2 — FRAME & SLOTS

## 6. What is a "Frame"?

### 6.1 Simple Meaning

A **Frame** is a **mechanism used to represent knowledge** in a **structured and object-oriented manner**, through a **frame** which contains **slots** (a set of attributes).

### 6.2 Everyday Analogy

Think of a **frame like a form/template** — say, an employee ID card template. It has fixed fields ("Slots") like Name, Employee ID, Department, Photo. Every actual employee gets their **own filled-in copy** of that template — same structure (slots), different actual values. That's precisely how a Frame works: a **generic template (structure)**, filled in per **instance (actual object)**.

```
FRAME — CORE STRUCTURE

   ┌──────────────────────────────────────────────────────┐
   │                   FRAME  NAME                        │
   ├─────────────────┬──────────────────┬─────────────────┤
   │   Slot Name     │   Slot Type      │ Actual Content  │
   ├─────────────────┼──────────────────┼─────────────────┤
   │  attribute-1    │ fixed/dynamic/   │     value       │
   │                 │ pointer/procedure│                 │
   ├─────────────────┼──────────────────┼─────────────────┤
   │  attribute-2    │      ...         │     value       │
   └─────────────────┴──────────────────┴─────────────────┘
```

***

## 7. Types of Slots — Fully Explained (with small examples)

A **Slot** = one attribute inside a frame. Slots come in **5 main types**:

### (i) Fixed-Slot / Fixed-Value Slot

The value **never changes** once set — it's a constant property of that object.

> **Small Example:** In a `Car` frame, `Number-of-Wheels = 4` — this is fixed; a car doesn't gain or lose wheels during normal operation.

### (ii) Dynamic-Slot / Dynamic-Value Slot

The value **can change over time** — it needs to be updated/refreshed as real-world conditions change.

> **Small Example:** In a `Phone` frame, `Battery-Level = 72%` — this value keeps changing as the phone is used or charged.

### (iii) Pointer Slot

Used to **store the address of another frame** — this is how frames get **connected/linked together** into a network (instead of duplicating information, a frame just "points to" another frame that holds it).

> **Small Example:** In a `Student` frame, the slot `Enrolled-In` doesn't store a whole classroom's data again — it just **points to the `Classroom-101` frame**, wherever that lives.

### (iv) Procedure Slots — "Active" Slots That Run a Script

Unlike the above (which just *store* a value), a **Procedure Slot runs a script (a set of instructions)** automatically, **triggered by a specific event**. Based on *when* the procedure fires, there are **four types**:

| Trigger Type | Fires When... | Small Example |
| :-- | :-- | :-- |
| **If-Needed** | The slot's value is **requested/read**, but isn't stored directly — it's **computed on demand** by running a script | A `Weather` frame's `Current-Temperature` slot has no stored value; when *asked*, it runs a script that fetches the live temperature from a sensor |
| **If-Added** | A **new value is added** to the slot | A `Classroom` frame's `Enrolled-Students` slot — when a new student is **added**, it automatically **triggers a script** to update the total headcount |
| **If-Changed** *(also seen written "If-Change")* | An **existing value is modified/updated** | A `Classroom` frame's `Class-Teacher` slot — if the teacher is **changed**, it triggers a script to **notify the Principal's office** |
| **If-Deleted** *(also seen written "If-Delete")* | A value is **removed** from the slot | A `Classroom` frame's `Enrolled-Students` slot — when a student is **removed**, it triggers a script to **decrease the headcount and free up a seat** |

```
PROCEDURE SLOT — 4 TRIGGER TYPES

   Procedure ──┬──► If-Needed   (value requested → compute & return it)
               ├──► If-Added    (new value added → run script)
               ├──► If-Changed  (existing value modified → run script)
               └──► If-Deleted  (value removed → run script)
```

> **Why this matters (content extension):** Fixed and Dynamic slots are **passive** — they just hold data. Pointer slots are **connective** — they link frames together. Procedure slots are **active** — they make a frame *behave* like a small program, reacting to reads, additions, edits, and deletions automatically. This is what makes Frames genuinely "object-oriented": data (slots) + behavior (procedures) bundled together, just like a class in OOP.

***

## 8. Inheritance in Frames

Just like nodes in a Semantic Network split into **Generic** and **Individual**, Frames also come in two levels:

| Frame Level | Meaning |
| :-- | :-- |
| **Generic Frame (Class Frame)** | Defines the **template/structure** — the slots that *every* member of that category should have, often with **default values** |
| **Instance Frame** | A **specific, real object** that **inherits** all slots from its Generic Frame (via an implicit `is-a` pointer), and then fills them in with **actual values** — it can also **override** a default if its own case is different |

```
FRAME INHERITANCE

   GENERIC FRAME: "Vehicle"                        INSTANCE FRAME: "My-Car"
   ┌────────────────────────────┐                  ┌───────────────────────────────┐
   │ Slot: Wheels               │                  │ Wheels: 4                     │
   │   Default Value: 4         │                  │   (inherited, not overridden) │
   │                            │   ── is-a ──►    │                               │
   │ Slot: Fuel-Type            │                  │ Fuel-Type: "Electric"         │
   │   Default Value: "Petrol"  │                  │   (overridden from default    │
   │                            │                  │    "Petrol")                  │
   └────────────────────────────┘                  └───────────────────────────────┘
```

**Small Example:** A generic `Vehicle` frame might set a **default** `Wheels = 4`. Every *instance* frame (like `My-Car`) automatically **inherits** this without re-typing it — but a specific instance like `My-Motorbike` can **override** it to `Wheels = 2`. This inheritance + override mechanism is what lets Frame systems avoid repeating the same information over and over across many similar objects, while still allowing exceptions.

## 9. Detailed Worked Example — Connected Classroom Frames

Instead of one isolated frame, real Frame systems are built as a **network of connected frames** — generic frames define categories, instance frames represent real objects, and **pointer slots link them together** (this is where Frames and Semantic Networks overlap conceptually).

### 9.1 The Scenario

A school's system needs to represent: a **Classroom**, its **Teacher**, and its **Students** — all as separate but *connected* frames.

### 9.2 Frame Hierarchy & Connection Diagram

**Diagram A — The `is-a` inheritance hierarchy (Generic → Instance):**

```
     GENERIC FRAMES (templates / classes)

     ┌────────────┐          ┌────────────┐          ┌────────────┐
     │ CLASSROOM  │          │  TEACHER   │          │  STUDENT   │
     │ (generic)  │          │ (generic)  │          │ (generic)  │
     └─────┬──────┘          └─────┬──────┘          └─────┬──────┘
           │ is-a                  │ is-a                  │ is-a
           ▼                       ▼                       ▼
   ┌────────────────┐   ┌────────────────────┐   ┌────────────────┐
   │ CLASSROOM-101  │   │ TEACHER: Mr.Sharma │   │ STUDENT: Riya  │
   │  (instance)    │   │    (instance)      │   │  (instance)    │
   └────────────────┘   └────────────────────┘   └────────────────┘
```

**Diagram B — Pointer-slot connections between the instance frames:**

```
                   Class-Teacher
                  (pointer slot)
   ┌─────────────────┐ ───────────► ┌──────────────────────┐
   │ CLASSROOM-101   │              │ TEACHER: Mr. Sharma  │
   │  (instance)     │ ◄─────────── │    (instance)        │
   └───────┬─────────┘  Assigned-   └──────────────────────┘
           │             Classroom
           │             (pointer slot — points back)
           │ Enrolled-Students
           │ (pointer slot, list)
           ▼
   ┌──────────────────┐   Enrolled-In (pointer slot,
   │  STUDENT: Riya   │ ◄─── points back to CLASSROOM-101)
   │   (instance)     │
   └──────────────────┘
        ... (plus STUDENT: Aman, and 36 more student frames, all linked the same way)

   Arrows = POINTER SLOTS: each one stores the ADDRESS of another
   frame rather than copying its data — this is what turns separate
   frames into one connected network.
```

### 9.3 Generic Frame: `CLASSROOM`

| Slot Name | Slot Type | Meaning / Default |
| :-- | :-- | :-- |
| `Frame-Metadata` | Fixed-Slot | Stores the frame's own identifier format, e.g. `Class-ID: String` |
| `Capacity` | Fixed-Slot | Default seating capacity, e.g. `40` |
| `Located-In` | Pointer Slot | Points to a `Building` frame |
| `Class-Teacher` | Pointer Slot | Points to a `TEACHER` instance frame |
| `Enrolled-Students` | Pointer Slot (list) | Points to one or more `STUDENT` instance frames |
| `Current-Attendance` | Procedure (If-Needed) | Runs `CalculateAttendance()` script only when this value is *asked for* — not stored directly |
| `Add-Student` | Procedure (If-Added) | When a student is added to `Enrolled-Students`, runs `UpdateHeadcount()` |
| `Change-Teacher` | Procedure (If-Changed) | When `Class-Teacher` is modified, runs `NotifyPrincipalOffice()` |
| `Remove-Student` | Procedure (If-Deleted) | When a student is removed from `Enrolled-Students`, runs `FreeUpSeat()` |

### 9.4 Instance Frame: `CLASSROOM-101` (is-a `CLASSROOM` — inherits + fills real values)

| Slot Name | Slot Type | Actual Content |
| :-- | :-- | :-- |
| `Frame-Metadata` | Fixed-Slot | `Class-ID: "CS-101"` |
| `Capacity` | Fixed-Slot (inherited, not overridden) | `40` |
| `Located-In` | Pointer Slot | → points to `Building-A` frame |
| `Class-Teacher` | Pointer Slot | → points to `TEACHER: Mr. Sharma` instance frame |
| `Enrolled-Students` | Pointer Slot (list) | → points to `[STUDENT: Riya, STUDENT: Aman, ...]` (38 total) |
| `Current-Attendance` | Procedure (If-Needed) | *(no stored value)* → runs `CalculateAttendance()` when asked, returning e.g. `36/38 Present` |
| `Add-Student` | Procedure (If-Added) | Triggered when a new student frame is linked → runs `UpdateHeadcount()` |
| `Change-Teacher` | Procedure (If-Changed) | Triggered if `Class-Teacher` pointer is updated → runs `NotifyPrincipalOffice()` |
| `Remove-Student` | Procedure (If-Deleted) | Triggered when a student frame is unlinked → runs `FreeUpSeat()` |

### 9.5 Connected Frame: `TEACHER` (Generic → Instance)

**Generic Frame `TEACHER`:**

| Slot Name | Slot Type | Default / Meaning |
| :-- | :-- | :-- |
| `Frame-Metadata` | Fixed-Slot | `Teacher-ID: String` |
| `Subject-Specialization` | Dynamic-Slot | Can change if reassigned to teach a different subject |
| `Assigned-Classroom` | Pointer Slot | Points back to a `CLASSROOM` instance frame |
| `Years-of-Experience` | Dynamic-Slot | Increments yearly |

**Instance Frame `TEACHER: Mr. Sharma`** (is-a `TEACHER`):

| Slot Name | Actual Content |
| :-- | :-- |
| `Frame-Metadata` | `Teacher-ID: "T-045"` |
| `Subject-Specialization` | `"Computer Science"` |
| `Assigned-Classroom` | → points back to `CLASSROOM-101` (a **two-way pointer connection**) |
| `Years-of-Experience` | `7` |

### 9.6 Connected Frame: `STUDENT` (Generic → Instance)

**Generic Frame `STUDENT`:**

| Slot Name | Slot Type | Default / Meaning |
| :-- | :-- | :-- |
| `Frame-Metadata` | Fixed-Slot | `Roll-No: String` |
| `Attendance-Percentage` | Procedure (If-Needed) | Computed on demand from attendance records |
| `Enrolled-In` | Pointer Slot | Points to the `CLASSROOM` instance frame the student belongs to |
| `Grade-Level` | Fixed-Slot | e.g. Default `"10th"` |

**Instance Frame `STUDENT: Riya`** (is-a `STUDENT`):

| Slot Name | Actual Content |
| :-- | :-- |
| `Frame-Metadata` | `Roll-No: "S-238"` |
| `Attendance-Percentage` | *(no stored value)* → runs `CalcAttendancePercent(Riya)` when asked, e.g. returns `94%` |
| `Enrolled-In` | → points to `CLASSROOM-101` |
| `Grade-Level` | `"10th"` (inherited default, not overridden) |

### 9.7 Full Text-Format Representation of `CLASSROOM-101`

```
Frame Name: Classroom-101   (is-a: Classroom)

1. Slot: Frame-Metadata                        → Fixed-Slot
     Datatype: String (Class-ID)
     Value: "CS-101"

2. Slot: Capacity                               → Fixed-Slot (inherited)
     Datatype: Integer
     Value: 40

3. Slot: Class-Teacher                          → Pointer Slot
     Points-To: Frame("Teacher: Mr. Sharma")

4. Slot: Enrolled-Students                      → Pointer Slot (list)
     Points-To: [Frame("Student: Riya"), Frame("Student: Aman"), ...]
     Count: 38

5. Slot: Current-Attendance                     → Procedure (If-Needed)
     Script: CalculateAttendance()
       presentCount = CountPresent(Self.Enrolled-Students)
       totalCount   = Self.Capacity_Enrolled
       return presentCount + "/" + totalCount

6. Slot: Add-Student                            → Procedure (If-Added)
     Script: UpdateHeadcount()
       Self.Enrolled-Students.append(newStudentFrame)
       TriggerDAEMON: NotifyClassSizeChanged()

7. Slot: Change-Teacher                         → Procedure (If-Changed)
     Script: NotifyPrincipalOffice()
       oldTeacher = Self.Class-Teacher (previous value)
       SendNotification(Principal, "Teacher changed for CS-101")

8. Slot: Remove-Student                         → Procedure (If-Deleted)
     Script: FreeUpSeat()
       Self.Enrolled-Students.remove(studentFrame)
       Self.AvailableSeats += 1
```

### 9.8 How It All Connects — Walkthrough

1. **`Classroom-101`** is an *instance* of the generic **`Classroom`** frame — it inherits the slot *structure* (Capacity, Class-Teacher, etc.) but fills in its own real values.
2. Its `Class-Teacher` slot is a **pointer**, not a copy — it literally links to the **`Teacher: Mr. Sharma`** instance frame. That teacher frame, in turn, has an `Assigned-Classroom` pointer linking **back** to `Classroom-101` — a genuine **two-way connected network of frames**, just like the arcs in a Semantic Network.
3. Every student in `Enrolled-Students` is similarly a **pointer** to a separate **`Student`** instance frame (like `Student: Riya`), which itself points back via `Enrolled-In` — so the whole classroom, teacher, and student roster form one interlinked frame system rather than isolated, duplicated data.
4. When someone **asks** for `Current-Attendance`, nothing is pre-stored — the **If-Needed procedure** runs live and computes it.
5. When a **new student is linked in**, the **If-Added procedure** automatically fires to keep the headcount correct.
6. If the school **reassigns a new teacher**, the **If-Changed procedure** fires to notify the Principal's office.
7. If a **student leaves the class**, the **If-Deleted procedure** fires to free up their seat.

This single example demonstrates **all 5 slot types**, **generic-vs-instance inheritance**, and a **fully connected, pointer-linked frame network** — the complete Frame & Slot picture in one place.

## 10. Semantic Network vs. Frame & Slots — Quick Comparison

| Aspect | **Semantic Network** | **Frame & Slots** |
| :-- | :-- | :-- |
| **Structure** | Graph of nodes + labeled arcs | Structured, object-oriented template (frame) with attributes (slots) |
| **Best For** | Showing relationships between many objects visually | Representing a **single object's full set of properties**, including *active* behavior |
| **Can Store "Behavior"?** | Not directly |  Yes — via **Procedure Slots** (If-Needed / If-Added / If-Changed / If-Deleted) |
| **Connections Between Objects** | Via **arcs** | Via **Pointer Slots** |
| **Downside** | Must traverse the entire graph to reach a conclusion | Can become complex to manage with many interlinked frames and inherited overrides |
