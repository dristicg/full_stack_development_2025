# Script
## 1. What is a "Script"?

### 1.1 Simple Meaning

A **Script** is a **technique to represent knowledge**. It is a **structured way to prescribe a set of circumstances** which **might happen next, one from another** — in other words, it captures a **stereotyped, predictable sequence of events** for a familiar situation.

- **Similar to Frame** — because it also **uses Slots**.
- **One behaviour that makes it identical to Frame:** it contains **every piece of information about each slot**.

### 1.2 Everyday Analogy

Think about **going to a restaurant**. You already know, without anyone telling you, roughly what will happen: you'll be seated, given a menu, order food, eat, get a bill, pay, and leave. You don't need to think through this sequence from scratch every time — your brain has a **pre-built template** for "restaurant visits" that just needs the specific details (which restaurant, what food, how much money) slotted in. A **Script** is exactly this idea, formalized for AI: a **reusable, pre-defined event sequence** for a recurring type of situation.

```
SCRIPT — CORE IDEA

   "A stereotyped sequence of events, prescribing what
    circumstance is likely to happen next, one from another."

   Event 1 ──► Event 2 ──► Event 3 ──► Event 4 ──► Event 5
  (Entering)  (Ordering)   (Eating)    (Paying)    (Exiting)

   Just like a Frame has SLOTS holding an object's attributes,
   a Script has SLOTS holding every detail of an EVENT sequence.
```

### 1.3 A Bit of Background

Script Theory in AI comes from the work of **Roger C. Schank and Robert Abelson (1977)**, as part of a broader framework called **Conceptual Dependency (CD) Theory** — an attempt to represent the *meaning* of natural-language sentences and events using a small, fixed set of primitive actions (this is exactly where the "Symbols for Script" in Section 5 come from). Scripts were designed to let an AI system make **sensible inferences and fill in unstated details** — for example, if a story simply says *"John went to a restaurant and left a big tip,"* a system that "knows" the Restaurant Script can infer that John almost certainly *ate food* and *paid a bill*, even though the sentence never says so.

## 2. Classification — The 5 Components of a Script

| # | Component | Meaning |
| :-- | :-- | :-- |
| **(i)** | **Entry Condition** | Certain events/situations that **have to be true or occurred** before the script can begin |
| **(ii)** | **Roles** | **Living entities** who act as an actor within the entire situation/event |
| **(iii)** | **Props** | The **objects** that come under this term — the "things" used within the scenario |
| **(iv)** | **Track** | A specific **instance/variant** of the broader script |
| **(v)** | **Result** | The **outcome/conclusion** once the sequence of events has played out |

```
CLASSIFICATION OF SCRIPT

  Script ───┬──► (i)   Entry Condition   (must be true before script runs)
            ├──► (ii)  Roles             (living actors)
            ├──► (iii) Props             (objects involved)
            ├──► (iv)  Track             (which specific variant is running)
            └──► (v)   Result            (final outcome)
```

### 2.1 A Small, Standalone Example for Each Component

| Component | Small Example (Restaurant context) |
| :-- | :-- |
| **Entry Condition** | *"The customer is hungry"* — this must be true before the "visiting a restaurant" script even starts |
| **Roles** | *Owner, Customer, Waiter* — all living entities that act within the story |
| **Props** | *Food, money, table, menu* — objects the roles interact with |
| **Track** | *"Fast-food restaurant"* vs. *"Fine-dining restaurant"* vs. *"Cafeteria"* — each is a different **variant** of the same general "Restaurant" script, sharing the same Roles/Props/Entry-Condition template but differing in scene details |
| **Result** | *"Customer is no longer hungry, has less money; Owner has more money, less food"* — the final state after the script completes |

### 2.2 Clarifying "Track"

**Track** is often the most confusing of the five, because it isn't a single "thing" like Roles or Props — it's the **specific sub-type or variant of the overall script** being executed. The same broad "Restaurant" script can play out along **different tracks**:

```
SCRIPT: "Restaurant"
            │
    ┌───────┼────────────────┐
    ▼       ▼                ▼
 Fast-Food  Fine-Dining   Cafeteria/Self-Serve
   Track       Track            Track

  Each Track shares the same overall structure (Entry Condition,
  Roles, Props, Result) but differs in the DETAILS of the scenes
  — e.g. a Fast-Food Track skips "waiter brings menu" and instead
  has "customer orders directly at the counter."
```

## 3. Worked Example — "Visiting a Restaurant" Script (Full Pseudocode)

### 3.1 Header Fields

| Field | Content |
| :-- | :-- |
| **Script** | Visiting a restaurant |
| **Track** | Restaurant |
| **Roles** | Owner, Customer, Waiter |
| **Props** | Food, money, table, menu |
| **Entry Condition** | Customer is hungry · Customer has money · Owner has food |
| **Result** | Customer is not hungry · Customer has less money · Owner has more money, less food |

### 3.2 Scene-by-Scene Breakdown

| Scene | Description | Symbolic Tag |
| :-- | :-- | :-- |
| **Scene 1 — Entering** | Customer enters a restaurant · Customer searches/sees for an empty table · Customer takes the seat | `PTRANS` |
| **Scene 2 — Ordering food** | Customer calls the waiter · Customer asks the waiter for a menu · Customer orders a food | `SPEAK`, `ATTEND` |
| **Scene 3 — Eating food** | Waiter serves food to the customer · Customer eats the food | `PTRANS`, `INGEST` |
| **Scene 4 — Paying bill** | Customer gets the bill from the owner · Customer pays the bill | `MTRANS`, `ATRANS` |
| **Scene 5 — Exiting** | Customer exits from the restaurant | `PTRANS` |

### 3.3 Sentences Translated into Symbolic (CD) Form

| Human-Language Sentence | Symbolic Translation |
| :-- | :-- |
| "Customer entering into a restaurant" | `Customer PTRANS Customer into a restaurant` |
| "Customer searches for an empty table" | `Customer ATTEND for an empty table` |
| "Customer pays bill to an owner" | `Customer ATRANS bill to an owner` |
| "Customer eats the food" | `Customer INGEST Food` |

This is the essence of **Conceptual Dependency**: any sentence, in any human language, can be broken down into one of a small handful of **universal primitive actions** (Section 5) plus the objects/actors involved — which is exactly what makes Scripts *reusable* across different phrasings of the same underlying event.

### 3.4 A Second, Shorter Example (To Reinforce the Pattern)

> **Script: "Visiting a Doctor"**

#### 3.4.1 Header Fields

| Field | Content |
| :-- | :-- |
| **Script** | Visiting a doctor |
| **Track** | General Physician Visit |
| **Roles** | Doctor, Patient, Receptionist |
| **Props** | Appointment slip, prescription pad, stethoscope, medical file, medicine |
| **Entry Condition** | Patient is unwell · Patient has booked an appointment · Doctor is available at the clinic |
| **Result** | Patient has a prescription · Patient's symptoms have been assessed · Patient still needs to take medicine to fully recover |

#### 3.4.2 Scene-by-Scene Breakdown

| Scene | Description | Symbolic Tag |
| :-- | :-- | :-- |
| **Scene 1 — Entering & Check-in** | Patient enters the clinic · Patient walks up to the reception desk · Patient shows the appointment slip to the receptionist | `PTRANS` |
| **Scene 2 — Waiting** | Receptionist directs the patient to the waiting area · Patient waits until the doctor is free | `ATTEND` |
| **Scene 3 — Consultation** | Patient enters the doctor's cabin · Patient describes the symptoms to the doctor · Doctor listens carefully to the patient | `MTRANS`, `ATTEND` |
| **Scene 4 — Examination** | Doctor examines the patient using a stethoscope · Doctor checks the patient's medical file for history | `GRASP`, `CONC` |
| **Scene 5 — Diagnosis & Prescription** | Doctor thinks over the symptoms and forms a diagnosis · Doctor writes a prescription on the prescription pad | `CONC`, `MBUILD` |
| **Scene 6 — Exiting** | Patient collects the prescription from the doctor · Patient exits the clinic | `ATRANS`, `PTRANS` |

#### 3.4.3 Sentences Translated into Symbolic (CD) Form

| Human-Language Sentence | Symbolic Translation |
| :-- | :-- |
| "Patient entering into the clinic" | `Patient PTRANS Patient into the clinic` |
| "Patient describes symptoms to the doctor" | `Patient MTRANS symptoms to Doctor` |
| "Doctor listens to the patient" | `Doctor ATTEND Patient` |
| "Doctor examines the patient with a stethoscope" | `Doctor GRASP stethoscope` |
| "Doctor thinks about the diagnosis" | `Doctor CONC diagnosis` |
| "Doctor writes the prescription" | `Doctor MBUILD prescription` |
| "Patient receives the prescription from the doctor" | `Doctor ATRANS prescription to Patient` |
| "Patient exits the clinic" | `Patient PTRANS Patient out of the clinic` |

#### 3.4.4 Track Variants (Applying Section 2.2's Idea Here Too)

Just like the Restaurant script has multiple Tracks, "Visiting a Doctor" also branches into different Tracks depending on the type of visit:

```
SCRIPT: "Visiting a Doctor"
            │
    ┌───────┼──────────────────┐
    ▼       ▼                  ▼
 General   Emergency         Specialist
 Physician    Room             Referral
  Track       Track              Track

  Same overall structure (Entry Condition, Roles, Props, Result)
  but different scene details — e.g. the Emergency Room Track
  skips "Scene 2 — Waiting" and "check-in with appointment slip"
  entirely, replacing them with immediate triage.
```

Notice this follows the **exact same 5-component template** as the Restaurant script — this is precisely what makes Scripts powerful: once you understand the *shape* of a Script, you can represent almost any familiar, repeatable real-world scenario the same way.

## 4. Advantages & Disadvantages

| **Advantages** | **Disadvantages** |
| :-- | :-- |
| **(i)** Helps identify the **events which precede** one another | **(i)** It is **not generalized** — a script written for one situation doesn't transfer to a completely different one |
| **(ii)** **Every minute detail** is described | **(ii)** **Not usable to represent every kind of knowledge** — works well for stereotyped, repeatable event sequences, poorly for one-off or highly variable situations |
| **(iii)** We can **easily interpret** the entire script | |

## 5. Symbols for Script (Conceptual Dependency Primitives)

These 12 symbols are used to **describe a scene through symbols** — a small, fixed vocabulary of primitive actions that any event in a script can be tagged with.

| Symbol | Meaning | Example |
| :-- | :-- | :-- |
| **ATRANS** | Transfer of an **abstract relationship** (e.g. ownership, possession) | give |
| **PTRANS** | Transfer of the **physical location** of an object | go |
| **PROPEL** | Apply **physical force** to an object | push |
| **MOVE** | **Move a body part** | kick |
| **GRASP** | **Grab an object** by an actor | hold |
| **INGEST** | **Taking an object inside** the body of an animal | drink, eat |
| **EXPEL** | **Expel from an animal's body** | cry, spit |
| **MTRANS** | Transfer of **mental information** | tell |
| **MBUILD** | **Construct new information** | decide |
| **SPEAK** | **Produce sound** | say |
| **ATTEND** | **Focusing a sense organ** | listen |
| **CONC** | **Conceptualize** or think about an idea | think |

```
CD PRIMITIVES — GROUPED BY WHAT THEY MOVE

  PHYSICAL transfers:    PTRANS (location), PROPEL (force),
                          MOVE (body part), GRASP (grab)

  BODY-level actions:    INGEST (take in), EXPEL (expel out)

  MENTAL / ABSTRACT:      ATRANS (abstract/ownership transfer),
                          MTRANS (mental info transfer),
                          MBUILD (construct new info), CONC (think)

  COMMUNICATION:          SPEAK (produce sound), ATTEND (focus a sense organ)
```

## 6. Script vs. Frame vs. Semantic Network — Full Unit Comparison

| Aspect | **Semantic Network** | **Frame & Slots** | **Script** |
| :-- | :-- | :-- | :-- |
| **Represents** | Relationships between objects (a "mind-map") | A **single object's** full set of properties | A **sequence of events** over time |
| **Structure** | Nodes + labeled arcs | Frame name + slots (attributes) | 5 components: Entry Condition, Roles, Props, Track, Result |
| **Uses Slots?** | No |  Yes |  Yes — this is what makes it "similar to Frame" |
| **Time-Ordered?** | No — purely relational | No — describes a static snapshot |  Yes — scenes unfold in order, each preceding the next |
| **Best For** | Showing how many concepts relate to each other | Representing one object's attributes + behavior | Representing **stereotyped, repeatable real-world situations** |
| **Key Weakness** | Must traverse the entire graph to reach a conclusion | Can get complex with many interlinked/inherited frames | Not generalized; can't represent every kind of knowledge |

***

## 7. Summary — Points to Remember

| # | Concept | Key Fact |
| :-- | :-- | :-- |
| (i) | **Script Definition** | A structured technique to represent knowledge as a **predictable sequence of events** |
| (ii) | **Relation to Frame** | Similar to Frame because it **uses Slots** and stores **every piece of information about each slot** |
| (iii) | **5 Components** | Entry Condition, Roles, Props, Track, Result |
| (iv) | **Track ≠ a single value** | Track represents **which variant** of the overall script is playing out (e.g. Fast-Food vs. Fine-Dining) |
| (v) | **Origin** | Rooted in **Schank & Abelson's Conceptual Dependency Theory (1977)**, which is also where the 12 CD primitive symbols come from |
| (vi) | **Main Strength** | Captures fine-grained, ordered detail and lets a system **infer unstated events** in a familiar situation |
| (vii) | **Main Weakness** | **Not generalized** — doesn't scale to representing arbitrary or novel knowledge outside a predefined script |
