# Reasoning Under Uncertainty
## 1. What is "Reasoning Under Uncertainty"?

### 1.1 Simple Meaning

**Reasoning Under Uncertainty** is the process of drawing conclusions and making decisions when the available knowledge is **incomplete, noisy, or not 100% guaranteed to be true** — which is the case in almost every real-world situation. Instead of concluding "X is definitely true," the system concludes something like "**X is true with 87% confidence**," and still manages to act sensibly on that partial confidence.

This is fundamentally different from the crisp, black-and-white world of classical logic and rule-based systems (covered in `05__rule_based_expert_system.md`), where every fact is either strictly **True** or strictly **False**, and every rule either **fires** or **does not fire** — with nothing in between.

### 1.2 Why Plain Logic Breaks Down Here

A traditional `IF <condition> THEN <conclusion>` rule assumes the condition can always be checked and answered with a clean **Yes/No**. But real sensors, real experts, and real data rarely offer that certainty:

| Real-World Situation | Why It's Uncertain |
| :-- | :-- |
| A camera says "object detected ahead" | Could be fog, glare, a plastic bag, or a real obstacle — sensor is **noisy** |
| A doctor examines a patient's symptoms | The same symptom (e.g., fever) can point to **many different** possible diseases |
| A weather sensor reports "cloudy" | Doesn't guarantee rain — it only makes rain **more likely** |
| A loan applicant's data is provided | Some fields may be **missing**, and past repayment behavior is only a probabilistic indicator of future behavior |

**Reasoning under uncertainty gives us the mathematical tools (mainly probability and fuzzy degrees of truth) to still reach a usable conclusion despite this incompleteness.**

### 1.3 Everyday Analogy

Think of a **doctor examining a patient with a mild fever and a cough**. The doctor cannot say with 100% certainty "you have the flu" — many illnesses share these symptoms. Instead, the doctor mentally weighs the **likelihood** of each possible illness given the symptoms, and given how common each illness is in general, and settles on the **most probable** diagnosis (e.g., "very likely the flu, 80% chance"), while remaining open to being wrong. This weighing of likelihoods under incomplete information is exactly what Reasoning Under Uncertainty formalizes in software.

## 2. Making It Concrete — Automated Braking System Example

### 2.1 The Problem

Imagine a **self-driving car's automated emergency braking (AEB) system**. Its job: decide whether to slam the brakes, based on signals like:

- A **radar/camera** that reports "object detected ahead" (but this sensor is not perfectly reliable)
- The **road weather** condition (wet road → longer stopping distance)
- The car's **current speed**

None of these signals is perfectly certain. A rule like `IF Object_Detected = Yes THEN Apply_Brakes` (the rigid rule-based-system style from the previous document) would be a **disaster** here — it would slam the brakes on every false alarm (a plastic bag, a shadow, sensor glare), causing constant, dangerous, unnecessary braking.

### 2.2 Diagram — How Uncertainty Flows Through the Braking Decision

```
AUTOMATED BRAKING SYSTEM — REASONING UNDER UNCERTAINTY

  ┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
  │  Radar / Camera    │   │   Road Weather     │   │   Vehicle Speed    │
  │  "Object ahead?"   │   │   "Wet / Dry?"     │   │   "How fast?"      │
  └─────────┬──────────┘   └─────────┬──────────┘   └───────────┬────────┘
            │ uncertain              │ uncertain                │ known, but
            │ (sensor noise,         │ (partial                 │ stopping
            │  fog, glare,           │  visibility,             │ distance is
            │  false alarms)         │  patchy sensors)         │ probabilistic
            └────────────┬────────────┴─────────────┬───────────┘
                         ▼                          ▼
            ┌───────────────────────────────────────────────┐
            │        PROBABILISTIC REASONING MODULE         │
            │  Combines every piece of uncertain evidence   │
            │  into a single number:                        │
            │       P(Collision_Risk = High | Evidence)     │
            └────────────────────────┬──────────────────────┘
                                     ▼
                    ┌────────────────────────────────────┐
                    │           THRESHOLD DECISION       │
                    │  IF P(Collision_Risk = High) > 0.8 │
                    │        → APPLY BRAKES              │
                    │  ELSE                              │
                    │        → KEEP MONITORING           │
                    └────────────────────────────────────┘
```

Notice the key shift from the rule-based system's diagram in the previous document: instead of a clean **Match → Resolve → Act** cycle over Yes/No facts, we now have a **numeric confidence value** flowing through the pipeline, and a **threshold**, not a rigid condition, deciding the final action.

### 2.3 Why a Single "Detected" Signal Isn't Enough — A Bayesian Walkthrough

Suppose the radar has the following known reliability, established through testing:

| Quantity | Meaning | Value |
| :-- | :-- | :-- |
| **P(Object = Real)** | Prior probability that a genuine obstacle exists at any given instant (obstacles are rare) | 0.05 |
| **P(Object = None)** | Prior probability that there is no real obstacle | 0.95 |
| **P(Detected \| Object = Real)** | Probability radar fires "detected" when a real obstacle is actually there | 0.95 |
| **P(Detected \| Object = None)** | Probability radar **falsely** fires "detected" when nothing is there | 0.10 |

Using **Bayes' Theorem** (fully explained with its formula in Section 5.1), we can compute how much we should actually trust a single "Detected" alert:

```
P(Detected) = P(Detected|Real) x P(Real)  +  P(Detected|None) x P(None)
            = (0.95 x 0.05)              +  (0.10 x 0.95)
            = 0.0475                      +  0.095
            = 0.1425

P(Object = Real | Detected) = [ P(Detected|Real) x P(Real) ] / P(Detected)
                             = 0.0475 / 0.1425
                             ≈ 0.333   (≈ 33.3%)
```

**This is the entire point of reasoning under uncertainty**: even after the radar says "Detected!", there is only a **~33% chance** it is a real obstacle — because true obstacles are rare, so false alarms end up outnumbering true detections. A rigid rule-based system would have braked immediately at "Detected = Yes." A probabilistic reasoner instead treats this as **weak evidence** and combines it with more evidence (weather, speed, a second sensor) before crossing the braking threshold — exactly what Section 2.2's diagram shows happening inside the "Probabilistic Reasoning Module."

## 3. How Is This Different From a Rule-Based Expert System?

### 3.1 Side-by-Side Comparison

| Aspect | **Rule-Based Expert System** | **Reasoning Under Uncertainty** |
| :-- | :-- | :-- |
| **Nature of facts** | Strictly **binary** — a fact is True or False, nothing in between | **Probabilistic / graded** — a fact holds with a confidence value (e.g., 0.73) or a degree of truth |
| **Rule firing** | A rule **either fires or it doesn't**, based on exact condition matching | Evidence is **combined and weighed**; there is no single sharp "fires/doesn't fire" moment |
| **Core mechanism** | **Match–Resolve–Act** cycle over the Knowledge Base and Working Memory | **Probability theory** (Bayesian methods) or **degrees of membership** (Fuzzy Logic) |
| **Handling noisy/missing data** | Poor — an unknown or noisy fact simply cannot be matched against a crisp condition | Core strength — built specifically to handle noisy, missing, or conflicting evidence |
| **Conclusion produced** | A definite conclusion (e.g., `Starter_Motor_Problem = Likely`) | A **confidence-weighted** conclusion (e.g., `P(Starter_Motor_Problem) = 0.87`) |
| **Best suited for** | Domains where expert knowledge really is crisp and rules rarely conflict (e.g., tax-filing eligibility rules) | Domains that are inherently noisy or probabilistic by nature (e.g., diagnosis, sensor fusion, risk prediction) |
| **Typical formalism** | `IF <condition> THEN <conclusion>` | Bayes' Theorem, Bayesian Networks, Fuzzy Sets/Rules |

### 3.2 The One-Line Takeaway

A Rule-Based Expert System asks: **"Is this condition true or false?"**
Reasoning Under Uncertainty asks: **"Given everything I currently know, how confident should I be, and in what?"**

## 4. Two Major Ways to Implement Reasoning Under Uncertainty

There are two dominant, well-established approaches used to build systems that reason under uncertainty:

### 4.1 Approach 1 — Bayesian Theorem (Probability-Based)

**Bayesian reasoning** treats uncertainty as a matter of **probability** — a number between 0 and 1 representing how likely a statement is to be true, updated as new evidence arrives. It answers questions like *"Given this new evidence, how should I revise my belief?"* This is the approach used by the braking-system example above, and it is explored fully in Section 5.

### 4.2 Approach 2 — Fuzzy Logic (Degree-of-Truth-Based)

**Fuzzy Logic** takes a different philosophical stance: instead of modeling "randomness," it models **vagueness** in language and measurement itself. A statement can be **partially true** — for example, "the car's speed is high" might be **0.7 true** and **0.3 false** at the same time, rather than needing a hard 100 km/h cutoff.

| Concept | Meaning | Braking-System Example |
| :-- | :-- | :-- |
| **Linguistic Variable** | A variable described in words rather than crisp numbers | `Speed` = "Slow" / "Medium" / "Fast" |
| **Membership Function** | A curve that assigns a degree (0 to 1) of belonging to a linguistic label | At 85 km/h, `Speed` might be `0.6` "Fast" AND `0.4` "Medium" simultaneously |
| **Fuzzy Rule** | An If-Then rule written using linguistic terms | `IF Speed is Fast AND Road is Wet THEN Braking_Force is High` |
| **Defuzzification** | Converting the final fuzzy output back into one crisp actionable number | Converts "Braking_Force is 0.8 High" into an exact "72% brake pressure" |

### 4.3 Bayesian vs. Fuzzy — Quick Comparison

| Aspect | **Bayesian (Probability)** | **Fuzzy Logic** |
| :-- | :-- | :-- |
| **What it models** | Uncertainty about **which event occurred** | Vagueness in the **meaning of a term itself** |
| **Core question** | "How likely is this to be true?" | "To what degree is this true?" |
| **Updates with new evidence?** | Yes — this is its central strength (Bayes' Theorem) | Not inherently — fuzzy rules are typically static |
| **Needs prior probabilities?** | Yes | No — needs membership functions instead |
| **Typical use case** | Diagnosis, spam filtering, sensor fusion, risk scoring | Control systems (washing machines, AC thermostats, ABS braking) |

## 5. Bayesian Networks — Bayes' Theorem in Action

### 5.1 Bayes' Theorem — Definition and Formula

**Bayes' Theorem** is a formula that tells us how to **update the probability of a hypothesis** in light of new evidence. It is the mathematical backbone of the entire Bayesian approach to reasoning under uncertainty.

```
                    P(B | A) x P(A)
        P(A | B) = ─────────────────
                         P(B)
```

| Term | Name | Meaning |
| :-- | :-- | :-- |
| **P(A)** | **Prior Probability** | How likely `A` was believed to be true *before* seeing any new evidence |
| **P(B \| A)** | **Likelihood** | How likely we would observe evidence `B`, *assuming* `A` is true |
| **P(B)** | **Evidence (Marginal Probability)** | The overall probability of observing `B` at all, across every possible hypothesis |
| **P(A \| B)** | **Posterior Probability** | The **updated**, revised belief in `A`, now that evidence `B` has been observed |

`P(B)` is usually expanded using the **Law of Total Probability**, summing over every possible hypothesis `Ai`:

```
P(B) = P(B|A1) x P(A1)  +  P(B|A2) x P(A2)  +  ...  +  P(B|An) x P(An)
```

This is exactly the calculation performed for the braking-radar example in Section 2.3, where `A = Object`, `B = Detected`.

### 5.2 What Is a Bayesian Network?

A **Bayesian Network** (also called a **Belief Network**) is a way of scaling Bayes' Theorem up from **two** related events to an entire **web of many related, cause-and-effect events**. It is represented as a **Directed Acyclic Graph (DAG)**:

| Element | Meaning |
| :-- | :-- |
| **Node** | A random variable in the domain (e.g., `Cloudy`, `Rain`) |
| **Directed Edge (Arrow)** | A direct **influence/dependency** — an arrow from `A` to `B` means `A` is a cause/parent that affects `B`'s probability |
| **Conditional Probability Table (CPT)** | Attached to every node, listing `P(Node | its Parents)` — or just `P(Node)` if it has no parents |
| **Acyclic** | No path ever loops back on itself — cause always flows "downward," never circularly |

The huge advantage of a Bayesian Network is **conditional independence**: once you know a node's direct parents, that node no longer depends on anything else "further back" in the graph — which keeps the calculations manageable even for large networks.

### 5.3 Worked Network — The Classic "Cloudy / Sprinkler / Rain / WetGrass" Example

```
BAYESIAN NETWORK — "CLOUDY / SPRINKLER / RAIN / WETGRASS"

                    P(C=T)   P(C=F)
                     0.5      0.5
                        │
                 ┌─────────────┐
                 │   CLOUDY    │
                 └──────┬──────┘
                        │
           ┌────────────┴────────────┐
           ▼                         ▼
   ┌───────────────┐         ┌───────────────┐
   │   SPRINKLER   │         │     RAIN      │
   └───────┬───────┘         └───────┬───────┘
           │                         │
           └────────────┬────────────┘
                        ▼
                 ┌───────────────┐
                 │   WETGRASS    │
                 └───────────────┘

  Sprinkler CPT (depends on Cloudy)        Rain CPT (depends on Cloudy)
  ┌─────┬──────────┬──────────┐            ┌─────┬──────────┬──────────┐
  │  C  │ P(S=T)   │ P(S=F)   │            │  C  │ P(R=T)   │ P(R=F)   │
  ├─────┼──────────┼──────────┤            ├─────┼──────────┼──────────┤
  │  T  │  0.1     │  0.9     │            │  T  │  0.8     │  0.2     │
  │  F  │  0.5     │  0.5     │            │  F  │  0.2     │  0.8     │
  └─────┴──────────┴──────────┘            └─────┴──────────┴──────────┘

  WetGrass CPT (depends on BOTH Sprinkler and Rain)
  ┌─────┬─────┬──────────┬──────────┐
  │  S  │  R  │ P(W=T)   │ P(W=F)   │
  ├─────┼─────┼──────────┼──────────┤
  │  T  │  T  │  0.99    │  0.01    │
  │  T  │  F  │  0.90    │  0.10    │
  │  F  │  T  │  0.90    │  0.10    │
  │  F  │  F  │  0.00    │  1.00    │
  └─────┴─────┴──────────┴──────────┘
```

Reading this network like a story: **Cloudy** weather is the root cause. If it's cloudy, the **Sprinkler** is less likely to be turned on (why water the lawn if clouds might do it?), while **Rain** becomes more likely. Finally, the grass gets wet (**WetGrass**) if *either* the sprinkler ran *or* it rained — with the highest chance of wet grass when *both* happened.

### 5.4 Turning the Graph Into Numbers — The Joint Probability Formula

A Bayesian Network lets us compute the probability of **any full combination** of its variables by simply **multiplying each node's CPT entry together** — this is called the **Chain Rule for Bayesian Networks**:

```
P(C, S, R, W) = P(C) x P(S | C) x P(R | C) x P(W | S, R)
```

Each node contributes exactly one factor, conditioned only on **its own parents** — this is the conditional-independence shortcut mentioned in Section 5.2.

### 5.5 Medium-Level Worked Example — "Given the Grass Is Wet, Was It Cloudy?"

**The Query:** We walk outside and see the grass is wet (`W = T`). We didn't observe `Cloudy`, `Sprinkler`, or `Rain` directly. **What is `P(C = T | W = T)`** — how likely was it cloudy, given this one piece of evidence?

This requires **Inference by Enumeration**: summing the full joint probability over every value of the variables we don't know (`S` and `R`), for each possible value of `C`, then applying Bayes' Theorem exactly as defined in Section 5.1 (`A = Cloudy`, `B = WetGrass`).

**Step 1 — Compute `P(C=T, W=T)` by summing over all combinations of S and R:**

```
P(C=T,W=T) = P(C=T) x Σ [ P(S|C=T) x P(R|C=T) x P(W=T|S,R) ]   over all S,R

  S=T,R=T:  P(S=T|C=T)=0.1  x P(R=T|C=T)=0.8  = 0.08   x P(W=T|T,T)=0.99  = 0.0792
  S=T,R=F:  P(S=T|C=T)=0.1  x P(R=F|C=T)=0.2  = 0.02   x P(W=T|T,F)=0.90  = 0.0180
  S=F,R=T:  P(S=F|C=T)=0.9  x P(R=T|C=T)=0.8  = 0.72   x P(W=T|F,T)=0.90  = 0.6480
  S=F,R=F:  P(S=F|C=T)=0.9  x P(R=F|C=T)=0.2  = 0.18   x P(W=T|F,F)=0.00  = 0.0000
                                                                           ─────────
                                                                  Sum    =  0.7452

  P(C=T, W=T) = P(C=T) x 0.7452 = 0.5 x 0.7452 = 0.3726
```

**Step 2 — Compute `P(C=F, W=T)` the same way:**

```
  S=T,R=T:  P(S=T|C=F)=0.5  x P(R=T|C=F)=0.2  = 0.10   x P(W=T|T,T)=0.99  = 0.0990
  S=T,R=F:  P(S=T|C=F)=0.5  x P(R=F|C=F)=0.8  = 0.40   x P(W=T|T,F)=0.90  = 0.3600
  S=F,R=T:  P(S=F|C=F)=0.5  x P(R=T|C=F)=0.2  = 0.10   x P(W=T|F,T)=0.90  = 0.0900
  S=F,R=F:  P(S=F|C=F)=0.5  x P(R=F|C=F)=0.8  = 0.40   x P(W=T|F,F)=0.00  = 0.0000
                                                                           ─────────
                                                                  Sum    =  0.5490

  P(C=F, W=T) = P(C=F) x 0.5490 = 0.5 x 0.5490 = 0.2745
```

**Step 3 — Compute the total evidence `P(W=T)` (the denominator from Bayes' Theorem):**

```
P(W=T) = P(C=T,W=T) + P(C=F,W=T) = 0.3726 + 0.2745 = 0.6471
```

**Step 4 — Apply Bayes' Theorem to get the final posterior conclusion:**

```
                   P(C=T, W=T)       0.3726
P(C=T | W=T) =   ───────────────  = ────────  ≈  0.5758   →   ≈ 57.6%
                     P(W=T)          0.6471
```

### 5.6 Conclusion — What Just Happened

- We never directly observed whether it was **Cloudy** — only that the grass was wet.
- The Bayesian Network let us **combine every path of influence** (Cloudy → Sprinkler → WetGrass, and Cloudy → Rain → WetGrass) automatically, using nothing but the CPTs and the chain-rule formula from Section 5.4.
- The final answer, **≈57.6% chance it was cloudy**, is a genuine, mathematically justified **posterior belief** — an update from the original 50% prior, made purely because we observed the grass was wet.
- This is the deeper, multi-variable version of the exact same radar example from Section 2.3: **observe some evidence → revise your belief about a hidden cause → act on the revised, numeric confidence** — which is the essence of Reasoning Under Uncertainty.
