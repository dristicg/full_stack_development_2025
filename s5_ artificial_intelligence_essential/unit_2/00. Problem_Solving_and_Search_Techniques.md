## 1. Problem Solving using AI

### What is "Problem Solving" in AI?

In Unit 1, we saw that an **Intelligent Agent** perceives the world and decides on the best action. But **how** does the agent actually *decide*? For a huge number of tasks, the answer is: it treats the task as a **problem to be searched** — it looks at where it currently is, imagines the different paths it could take, and picks the path that leads to the goal in the best possible way.

**In the simplest words:** Problem solving in AI means turning a real-world goal ("get from home to college," "win this chess game," "arrange these tiles correctly") into a **precise, step-by-step search** through all the possible situations the agent could reach — until it finds one that satisfies the goal.

```
Real-World Goal:                      AI's View of the Same Goal:
──────────────────                     ──────────────────────────────
"I want to reach                       "Starting from State S0, which
 the airport"                           sequence of actions leads me
                                         to a State that satisfies
                                         'at the airport'?"
```

**Everyday Analogy:**
Think of a **maze**. You don't just wander randomly — you mentally imagine: *"If I turn left here, where do I end up? If that's a dead end, what if I'd turned right instead?"* You're exploring different **paths** through the maze in your head before committing to one. That is *exactly* what a search-based AI agent does, except it does this systematically and can compare thousands of paths in a way a human never could.

***

### Why Do We Need Problem Solving Agents?

Not every AI agent needs to "search" — a simple reflex agent (like a motion-sensor light) doesn't. But whenever a task requires **planning several steps ahead** to reach a goal, a **Problem-Solving Agent** is needed.

- A GPS app doesn't just guess a road — it **searches** through possible road combinations to find the shortest route.
- A chess engine doesn't just make a random legal move — it **searches** through possible future board positions to find the move that leads to victory.

### The 4-Step Process a Problem-Solving Agent Follows

```
STEP 1: GOAL FORMULATION
        "What do I actually want to achieve?"
                │
                ▼
STEP 2: PROBLEM FORMULATION
        "What are my states, actions, and costs?" (from Unit 1, Section 7)
                │
                ▼
STEP 3: SEARCH
        "Explore possible action sequences to find one that reaches the goal"
                │
                ▼
STEP 4: EXECUTION
        "Carry out the actions found by the search, one by one"
```

**Simple Example — Planning a Road Trip:**
1. **Goal Formulation:** "I want to reach Mumbai from Ahmedabad."
2. **Problem Formulation:** States = cities/junctions on the map, Actions = drive from one city to a connected city, Path Cost = total distance/time.
3. **Search:** Try out different combinations of highways and roads to see which sequence of cities gets you there.
4. **Execution:** Actually drive along the chosen route.

***

### Real-Life Example 1: Google Maps Navigation

When you type a destination into Google Maps, the app doesn't magically "know" the route. Internally, it treats every intersection/junction as a **state**, every road segment as an **action**, and it **searches** through millions of possible road combinations to find the one with the lowest path cost (shortest time/distance). This is a textbook AI problem-solving process happening silently in your pocket.

### Real-Life Example 2: A Robot Arm in a Warehouse

An Amazon warehouse robot arm that needs to pick up a box and place it on a shelf treats each possible arm position as a **state**. It **searches** through possible sequences of joint movements (actions) to find a path that moves the box from the shelf to the delivery cart **without hitting other objects** — exactly the same search process, just applied to physical movement instead of roads.

## 2. State Space Representation

### What is a "State"?

A **state** is simply a **complete snapshot** of the problem at one particular moment — enough information to tell you *exactly* where things stand, without needing to know the history of how you got there.

**Everyday Analogy:** Think of a state like a **screenshot of a video game**. If you paused a game and someone else picked up the controller, the screenshot alone tells them everything they need to know to keep playing — they don't need to have watched you play up to that point.

### What is the "State Space"?

The **State Space** is the set of **every single state that the agent could possibly reach**, starting from the initial state, by applying any valid sequence of actions. Put together, all these states and the actions connecting them form a giant **graph or tree** — this is what search algorithms actually explore.

```
                     ┌───────────────┐
                     │ INITIAL STATE │
                     └───────┬───────┘
                 ┌───────────┼───────────┐
                 ▼            ▼            ▼
            ┌────────┐   ┌────────┐   ┌────────┐
            │ State A|   │ State B│   │ State C│
            └────┬───┘   └────┬───┘   └────────┘
           ┌──────┴──────┐     │
           ▼             ▼     ▼
      ┌────────┐   ┌────────┐ ┌────────┐
      │ State D│   │ State E│ | State F│  ◄── GOAL STATE
      └────────┘   └────────┘ └────────┘

Each box = one possible situation (a "state")
Each arrow = one action that moves you from one state to the next
```

### The Building Blocks of a State Space (Recap + Extension)

| Term | Simple Meaning |
| :-- | :-- |
| **State** | One specific snapshot/situation of the problem |
| **Initial State** | The state the agent starts in |
| **Action(s)** | The set of moves available from a given state |
| **Successor / Transition Model** | Tells you which new state results from applying an action to the current state |
| **Goal State** | The state (or states) that satisfy what we're looking for |
| **Path** | A sequence of states connected by actions |
| **Path Cost** | A number representing how "expensive" (steps, time, distance) a path is |
| **State Space Graph/Tree** | The entire collection of states and the actions connecting them |

***

### Representing a State Space — Two Common Ways

**1. As a Tree** — Used when we don't mind revisiting the same situation multiple times (each repeated state gets its own separate node). Simpler to build, but can get **very large** if the same state is reachable through many different paths.

**2. As a Graph** — Used when we specifically **avoid revisiting** the same state twice (each unique situation is a single node, no matter how many paths lead to it). More memory-efficient, especially for problems where you can loop back to an earlier situation.

```
TREE VIEW (state "X" appears twice,                GRAPH VIEW (state "X" appears
 once under A and once under B):                    only once, both paths point to it):

        Start                                              Start
       /      \                                            /   \
      A        B                                          A     B
      |        |                                           \   /
      X        X   ← duplicate!                              X   ← single shared node
```

***

### Worked Example — State Space for a Simple "Water Jug Problem"

**Problem:** You have a 4-litre jug and a 3-litre jug, no markings on either. You need to measure out exactly **2 litres** of water using only these two jugs.

| Component | Description |
| :-- | :-- |
| **State** | A pair `(x, y)` — where `x` = water currently in the 4L jug, `y` = water currently in the 3L jug |
| **Initial State** | `(0, 0)` — both jugs empty |
| **Actions** | Fill 4L jug, Fill 3L jug, Empty 4L jug, Empty 3L jug, Pour 4L→3L, Pour 3L→4L |
| **Goal Test** | Is `x = 2` (or `y = 2`)? |
| **Path Cost** | 1 per action performed |

```
State Space (partial) for the Water Jug Problem
State = (x, y)   where x = water in the 4L jug, y = water in the 3L jug

    (0, 0)   both jugs empty
       │
       │  Fill 4L
       ▼
    (4, 0)   4L jug full, 3L jug empty
       │
       │  Pour 4L → 3L
       ▼
    (1, 3)   3L jug now full, 1L left in 4L jug
       │
       │  Empty 3L
       ▼
    (1, 0)   3L jug emptied out, 1L still in 4L jug
       │
       │  Pour 4L → 3L
       ▼
    (0, 1)   the 1L moved into the 3L jug, 4L jug now empty
       │
       │  Fill 4L
       ▼
    (4, 1)   4L jug full again, 3L jug still has 1L
       │
       │  Pour 4L → 3L
       ▼
    (2, 3)   ✅ GOAL — exactly 2 litres in the 4L jug
```

**Reading it in one line:** `(0,0) → (4,0) → (1,3) → (1,0) → (0,1) → (4,1) → (2,3)` — 6 actions total to reach the goal.

**How to read this trace, action by action:**

| # | Action | What happens physically | Resulting state |
| :-- | :-- | :-- | :-- |
| 1 | Fill 4L | Fill the empty 4L jug completely | `(4, 0)` |
| 2 | Pour 4→3 | Pour from 4L into 3L until 3L is full (3L used, 1L left in 4L) | `(1, 3)` |
| 3 | Empty 3L | Tip out the full 3L jug | `(1, 0)` |
| 4 | Pour 4→3 | Pour the remaining 1L from 4L into the empty 3L jug | `(0, 1)` |
| 5 | Fill 4L | Fill the 4L jug completely again | `(4, 1)` |
| 6 | Pour 4→3 | Pour from 4L into 3L (which already has 1L, so only 2L more fits) — 4L jug is left with exactly **2 litres** | `(2, 3)` ✅ **GOAL** |

This small example shows exactly how a real-world puzzle becomes a **state space**: every combination of water levels is a state, every jug operation is an action, and the search explores this space until it finds `(2, y)`.

***

### Real-Life Example 1: A Sudoku Solving App

Every partially-filled Sudoku grid is a **state**. Placing a number in an empty cell is an **action**. The **state space** is every possible way the grid could be filled in (validly or not) starting from the given puzzle. The app searches this space until it finds a state where the grid is **completely and validly filled** (the goal state).

### Real-Life Example 2: Rubik's Cube Solving Apps

Every twist of a Rubik's Cube produces a new arrangement of coloured squares — that arrangement is a **state**. Each possible twist (face + direction) is an **action**. Cube-solving apps and robots represent the **entire set of reachable cube arrangements** as a state space and search through it to find a path from the scrambled state back to the fully-solved state.

## 3. Uninformed Search Techniques

### What Does "Uninformed" Mean?

An **Uninformed Search** (also called **Blind Search**) is a search strategy that has **no extra information or "hint"** about how close a state is to the goal. It only knows what's *inside* the problem definition (the initial state, actions, and goal test) — nothing more.

**Everyday Analogy:** Imagine exploring an unfamiliar building **with the lights off**, having no map or floor directory — you can only feel your way through corridors as you physically reach them. That's an *uninformed* search. (Compare this to an *informed* search, covered later, where you'd have a floor map or a "warmer/colder" hint — like the A\* algorithm.)

We will study the two most fundamental uninformed techniques: **Breadth First Search (BFS)** and **Depth First Search (DFS)**.

***

## 3.1 Breadth First Search (BFS)

### What is BFS?

**Breadth First Search** explores the state space **level by level** — it fully examines every state at the *current* distance from the start before moving on to states that are one step further away. It uses a **Queue** (First-In-First-Out, FIFO) to keep track of which state to explore next.

**Everyday Analogy:** Imagine dropping a **stone into a pond**. The ripples spread outward evenly in **rings** — the closest ring is fully formed before the next, wider ring begins. BFS explores the state space in exactly this ripple-like, ring-by-ring pattern, always finishing everything at the current "distance" before going further out.

```
LEVEL 0:                     A
                            ╱   ╲
LEVEL 1:                  B       C
                        ╱   ╲       ╲
LEVEL 2:              D       E       F   ◄── GOAL

BFS visiting order:  A → B → C → D → E → F
(Explores ALL of Level 1 completely before touching Level 2)
```

### How BFS Works — Step by Step

1. Put the **start state** into a Queue.
2. Repeat until the Queue is empty:
   a. **Remove** the state at the **front** of the Queue.
   b. If it's the **goal**, stop — we found it!
   c. Otherwise, add all its **unvisited neighbours** to the **back** of the Queue.
3. If the Queue becomes empty without finding the goal, no solution exists.

### Key Property of BFS

Because it explores level by level, BFS is **guaranteed to find the shortest path** (fewest number of actions/edges) to the goal — **as long as every action has the same cost**. This is BFS's single biggest strength.

| Property | BFS Behaviour |
| :-- | :-- |
| **Data Structure Used** | Queue (FIFO) |
| **Completeness** | Yes — will always find a solution if one exists |
| **Optimality** | Yes — finds the shortest path, if all step-costs are equal |
| **Time Complexity** | O(b^d) — where *b* = branching factor, *d* = depth of the shallowest goal |
| **Space Complexity** | O(b^d) — must store **all** nodes at the current level, which can use a **lot** of memory |

***

### C++ Implementation of BFS

```cpp
#include <iostream>
#include <vector>
#include <queue>
using namespace std;

// Graph represented using an adjacency list
class Graph {
    int numVertices;
    vector<vector<int>> adjList;

public:
    Graph(int vertices) {
        numVertices = vertices;
        adjList.resize(vertices);
    }

    // Add an edge between two nodes (undirected graph)
    void addEdge(int u, int v) {
        adjList[u].push_back(v);
        adjList[v].push_back(u);
    }

    // Breadth First Search starting from 'start'
    void bfs(int start) {
        vector<bool> visited(numVertices, false);
        queue<int> q;

        visited[start] = true;
        q.push(start);

        cout << "BFS Traversal Order: ";
        while (!q.empty()) {
            int current = q.front();
            q.pop();
            cout << current << " ";

            // Visit all unvisited neighbours
            for (int neighbour : adjList[current]) {
                if (!visited[neighbour]) {
                    visited[neighbour] = true;
                    q.push(neighbour);
                }
            }
        }
        cout << endl;
    }
};

int main() {
    Graph g(6); // 6 nodes: 0 to 5
    g.addEdge(0, 1);
    g.addEdge(0, 2);
    g.addEdge(1, 3);
    g.addEdge(1, 4);
    g.addEdge(2, 5);

    g.bfs(0); // Start BFS from node 0
    return 0;
}
```

**Expected Output:**
```
BFS Traversal Order: 0 1 2 3 4 5
```

***

### Real-Life Example 1: Finding "Degrees of Separation" on Social Media

When LinkedIn shows you "2nd-degree connection" or Facebook suggests "people you may know," it is running BFS starting from **you** as the root node. It first explores all your **direct friends** (Level 1), then all of *their* friends who aren't already your friends (Level 2), and so on — exactly BFS's ripple pattern. This guarantees it finds the people with the **fewest hops** away from you first.

### Real-Life Example 2: GPS Navigation on an Unweighted Road Map

If all road segments are treated as **equal cost** (say, we only care about the *fewest number of turns/roads*, not distance), a navigation app can use BFS to guarantee the path found uses the **minimum number of road segments** to reach the destination — spreading outward from your current location just like ripples in a pond.

## 3.2 Depth First Search (DFS)

### What is DFS?

**Depth First Search** explores the state space by going as **deep as possible down one single path** before backtracking. It picks a neighbour, dives all the way down that branch, and only comes back to try a different branch once it hits a dead end. It uses a **Stack** (Last-In-First-Out, LIFO) — either explicitly, or implicitly through **recursion**.

**Everyday Analogy:** Imagine solving a **maze** by always choosing to go **straight down one corridor** as far as it goes. If you hit a dead end, you **backtrack** to the last junction and try the next unexplored corridor — you never explore two corridors "at once" like BFS's ripple; you fully commit to one path before abandoning it.

```
LEVEL 0:                     A
                            ╱   ╲
LEVEL 1:                  B       C
                        ╱   ╲       ╲
LEVEL 2:              D       E       F   ◄── GOAL

DFS visiting order:  A → B → D → (dead end, backtrack) → E → (dead end, backtrack) → C → F
(Dives all the way down one branch before trying the next one)
```

### How DFS Works — Step by Step

1. Put the **start state** on a Stack (or call it recursively).
2. Repeat until the Stack is empty:
   a. **Remove** the state at the **top** of the Stack.
   b. If it's the **goal**, stop — we found it!
   c. Otherwise, push all its **unvisited neighbours** onto the Stack.
3. If the Stack becomes empty without finding the goal, no solution exists.

### Key Property of DFS

DFS uses **far less memory** than BFS because it only needs to remember the states along the **current single path**, not every state at a given level. But its big weakness: it is **not guaranteed** to find the shortest path — it might dive very deep down a long, inefficient branch before ever trying a short one, and in an infinite state space it can even get "lost" forever down one endless path unless depth is limited.

| Property | DFS Behaviour |
| :-- | :-- |
| **Data Structure Used** | Stack (LIFO) / Recursion |
| **Completeness** | Only guaranteed in **finite** state spaces (can get stuck in infinite paths otherwise) |
| **Optimality** | No — does **not** guarantee the shortest path |
| **Time Complexity** | O(b^m) — where *b* = branching factor, *m* = maximum depth of the state space |
| **Space Complexity** | O(b·m) — much lower than BFS, since it only stores the current path |

***

### C++ Implementation of DFS

```cpp
#include <iostream>
#include <vector>
using namespace std;

// Graph represented using an adjacency list
class Graph {
    int numVertices;
    vector<vector<int>> adjList;

public:
    Graph(int vertices) {
        numVertices = vertices;
        adjList.resize(vertices);
    }

    // Add an edge between two nodes (undirected graph)
    void addEdge(int u, int v) {
        adjList[u].push_back(v);
        adjList[v].push_back(u);
    }

    // Recursive helper function for DFS
    void dfsUtil(int current, vector<bool> &visited) {
        visited[current] = true;
        cout << current << " ";

        for (int neighbour : adjList[current]) {
            if (!visited[neighbour]) {
                dfsUtil(neighbour, visited);
            }
        }
    }

    // Depth First Search starting from 'start'
    void dfs(int start) {
        vector<bool> visited(numVertices, false);
        cout << "DFS Traversal Order: ";
        dfsUtil(start, visited);
        cout << endl;
    }
};

int main() {
    Graph g(6); // 6 nodes: 0 to 5
    g.addEdge(0, 1);
    g.addEdge(0, 2);
    g.addEdge(1, 3);
    g.addEdge(1, 4);
    g.addEdge(2, 5);

    g.dfs(0); // Start DFS from node 0
    return 0;
}
```

**Expected Output:**
```
DFS Traversal Order: 0 1 3 4 2 5
```

***

### Real-Life Example 1: Solving a Maze Game

A maze-solving robot or game AI commonly uses DFS: it commits to one corridor, follows it all the way to its end, and only **backtracks** to try a different corridor once it truly hits a dead end. This mirrors exactly how a person might solve a maze on paper by tracing one path fully before erasing and trying another.

### Real-Life Example 2: File System / Folder Search on Your Computer

When your computer searches for a file by "diving into" a folder, then into its sub-folder, then into *that* sub-folder's sub-folder — going as deep as possible before moving to a sibling folder — it is following the DFS pattern. Tools like `find` (Linux) or Windows' file indexer commonly traverse folder trees this way.

## 4. BFS vs. DFS — Side-by-Side Comparison

| Aspect | BFS (Breadth First Search) | DFS (Depth First Search) |
| :-- | :-- | :-- |
| **Exploration Style** | Level by level (wide first) | Branch by branch (deep first) |
| **Data Structure** | Queue (FIFO) | Stack (LIFO) / Recursion |
| **Finds Shortest Path?** | Yes (if all step costs are equal) | Not guaranteed |
| **Memory Usage** | High — stores every node at current level | Low — stores only the current path |
| **Best Used When** | You need the **shortest/fewest-step** solution, and the state space isn't too wide | Memory is limited, or you just need **any** valid solution, not necessarily the shortest |
| **Real-World Analogy** | Ripples spreading outward in a pond | Exploring a maze corridor-by-corridor with backtracking |

```
VISUAL SUMMARY — same tree, two different visit orders

BFS (ring by ring):

          A
        ╱   ╲
      B       C
    ╱   ╲       ╲
  D       E       F

Visit order: A → B → C → D → E → F
(finish everything on one level before moving to the next)


DFS (branch by branch):

          A
        ╱   ╲
      B       C
    ╱   ╲       ╲
  D       E       F

Visit order: A → B → D → E → C → F
(go all the way down the left side first, then backtrack and try the right side)
```

**Key takeaway:** It's the *same tree* both times. BFS visits C (a Level-1 node) before D or E (Level-2 nodes) — it always finishes a level before going deeper. DFS visits D and E (deep down the left branch) before ever trying C — it always finishes a branch before trying a sibling. Both eventually reach every node, but in a very different order.

***

### Why Uninformed Search Matters

- BFS and DFS are the **foundation** on which almost every other search algorithm is built — later, more advanced techniques (like Uniform Cost Search, A\*, and Greedy Best-First Search, studied under **Informed Search**) simply add smarter ways of *choosing* which node to expand next, but they still rely on the same core idea of exploring a **state space**.
- Choosing the right search strategy has real consequences: using DFS when you actually need the shortest path (like in GPS routing) could give a technically "valid" but very **inefficient** route — showing why understanding these trade-offs is essential before applying search to a real-world problem.
